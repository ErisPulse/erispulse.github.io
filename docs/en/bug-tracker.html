Bug Tracker

This document records known bugs of the ErisPulse SDK and their repair status, arranged in chronological order by the time of repair version.

For Readers No software is perfect, and even the most careful developers leave small errors. This tracker includes only issues that have a practical impact on operation—those too minor to even reach the "minor" level are not included here. Although the number of "critical" items may seem high, the intention behind publicly recording these bugs is to make troubleshooting and backtracking smoother, not to create anxiety: problems that are visible, recorded, and fixed are proof that the project is constantly improving. Seeing this list should not cause anxiety; it is a troubleshooting tool, not a source of fear.

How to Read & Maintenance Conventions

  • Each bug record includes structured fields such as problem description, root cause analysis, affected version range, repair solution, etc. It is recommended to check the "affected version" before upgrading to see if it covers the version currently in use.
  • If you need to add a new bug entry, supplement content at the corresponding location, following the field specifications and severity/type classifications below.

Fixed Bugs

[BUG-001] Event handlers registered multiple times causing events to be processed multiple times

Issue: When registering multiple handlers using decorators like @message or @notice, the same event is triggered multiple times, leading to commands being executed multiple times and logs being duplicated.

Cause: The BaseEventHandler registers handlers to the adapter event bus without deduplication logic. Each decorator registers a handler once, resulting in multiple calls when events are dispatched.

Affected Versions: 2.2.0-dev.0 - 2.2.1-dev.0

Fixed Version: 2.2.1-dev.0

Fix: Optimized BaseEventHandler to ensure each event type is registered only once with the adapter, preventing repeated triggers.

Fix Date: 2025/08/18

Severity: 🔴 Critical

Type: Event System

[BUG-002] Init command adapter configuration path type error

Issue: When using the ep init command for interactive initialization, selecting a configuration adapter results in a type error:

Interactive initialization failed: unsupported operand type(s) for /: 'str' and 'str'

Cause: In version 2.3.7, when adjusting the configuration file path, the method parameter types were inconsistent. The _configure_adapters_interactive_sync method received a str type parameter but internally used the Path / operator to concatenate paths.

Affected Versions: 2.3.7 - 2.3.9-dev.1

Fixed Version: 2.3.9-dev.1

Fix: Changed the parameter type of the _configure_adapters_interactive_sync method from str to Path, passing Path objects directly when called.

Fix Date: 2026/03/23

Severity: 🟡 Moderate

Type: CLI

[BUG-003] Command events fail after restart

Issue: After calling sdk.restart(), commands registered via @command are not triggered, resulting in no robot response after sending a command.

Cause: After adapter.shutdown() clears the event bus, the _linked_to_adapter_bus status of BaseEventHandler is not reset to False, causing the _process_event method to consider it already linked to the adapter bus and skip re-linking.

Affected Versions: 2.2.x - 2.4.0-dev.2

Fixed Version: 2.4.0-dev.3

Fix: Added _linked_to_adapter_bus status tracking; after clear_handlers() disconnects the bus, the next register() automatically re-links, adapting to shutdown/restart scenarios.

Fix Date: 2026/04/09

Severity: 🔴 Critical

Type: Event System

[BUG-004] Lifecycle event handlers not cleaned up

Issue: After sdk.restart(), old lifecycle event handlers still exist and trigger repeatedly, causing the same event to be processed multiple times.

Cause: The lifecycle._handlers dictionary was never cleared in uninit(), resulting in old and new handlers coexisting after restart.

Affected Versions: 2.3.0 - 2.4.0-dev.2

Fixed Version: 2.4.0-dev.3

Fix: In the cleanup process of Uninitializer (after all events are submitted), clear lifecycle._handlers.

Fix Date: 2026/04/09

Severity: 🟡 Moderate

Type: Runtime

[BUG-005] Event.is_friend_add/is_friend_delete detail_type inconsistent with OB12 standard

Issue: Event.is_friend_add() checks detail_type == "friend_add", Event.is_friend_delete() checks detail_type == "friend_delete", but the OneBot12 standard defines detail_type values as "friend_increase" and "friend_decrease". This inconsistency with the values used in notice.py's on_friend_add/on_friend_remove decorators causes handlers registered via decorators to fail when triggered, as the corresponding is_friend_add()/is_friend_delete() methods return False.

Cause: wrapper.py uses non-standard naming, while notice.py uses the correct OB12 standard naming.

Affected Versions: Since implementation

Fixed Version: 2.4.2-dev.1

Fix: Changed is_friend_add()'s matching value from "friend_add" to "friend_increase", and is_friend_delete() from "friend_delete" to "friend_decrease".

Fix Date: 2026/04/13

Severity: 🟡 Moderate

Type: Event System

[BUG-006] adapter.clear() not cleaning _started_instances causing incorrect state after restart

Issue: The AdapterManager.clear() method clears _adapters, _adapter_info, handlers, and _bots, but omits _started_instances. If clear() is called while the adapter is running, _started_instances retains dangling references, causing incorrect state judgment after restart.

Cause: When _started_instances was introduced in 2.4.0-dev.1, it was not synchronized for cleanup in clear().

Affected Versions: 2.4.0-dev.1 - 2.4.2-dev.0

Fixed Version: 2.4.2-dev.1

Fix: Added self._started_instances.clear() in the clear() method.

Fix Date: 2026/04/13

Severity: 🟡 Moderate

Type: Adapter

[BUG-007] command.wait_reply() using deprecated asyncio.get_event_loop()

Issue: The CommandHandler.wait_reply() method uses asyncio.get_event_loop() to create futures and get timestamps, which has been deprecated since Python 3.10. In asynchronous contexts, asyncio.get_running_loop() should be used. This is inconsistent with wrapper.py's wait_for() method in the same file, which uses get_running_loop().

Cause: The old API was used during development, and the newly added wait_for() method used the correct API but did not retroactively fix the old code.

Affected Versions: 2.3.0-dev.0

Fixed Version: 2.4.2-dev.1

Fix: Replaced two instances of asyncio.get_event_loop() in command.py with asyncio.get_running_loop().

Fix Date: 2026/04/13

Severity: 🟢 Minor

Type: Event System

[BUG-008] Bot offline event submitted repeatedly during shutdown

Issue: When calling adapter.shutdown() to close all adapters, _update_bot_status() repeatedly submits Bot offline events during the shutdown process, causing the same batch of Bots to be marked offline multiple times and triggering multiple adapter.bot.offline lifecycle events.

Cause: The Bot status tracking system introduced in 2.4.0-dev.1 did not set a "shutting down" flag during shutdown(), so _update_bot_status() could not distinguish between normal offline and cascading offline during shutdown.

Affected Versions: 2.4.0-dev.1 - 2.4.2-dev.1

Fixed Version: 2.4.2-dev.1

Affected Versions: 2.11.0 - 2.11.2 (runtime.json instance control introduced with 2.11.0; earlier versions have no restart command)
Fixed Version: 2.12.0-dev.0
Fix Description: When epsdk restart detects the status file pid == 1 (characteristic of the main container process), it no longer terminates and restarts, but instead sends SIGUSR1 to the framework process, and the framework completes the component-level soft restart (using sdk.restart(): module and adapter hot reload pipeline, with the entry-point of the new adapter immediately effective in the running process); sdk.run() registers a SIGUSR1 handler to carry this channel. The entire process restart scenario is handled by container restart (docker restart / restart policy).
Regression Test: tests/unit/test_unit_cli_runtime.py::TestRestartContainerHot

Severity: 🔴 Critical (container deployment restart causes service interruption)
Type: CLI / Deployment

[BUG-051] Cross-account duplicate receipt (drop) mistakenly injures @mention messages, causing random message loss in multi-account deployment

[BUG-052] Concurrent storage first fetch deadlock freezes event loop, web site hangs and continuously reports "database is locked"

Issue: After a specific window (cold start first concurrent / after connection failure automatic rebuild first concurrent), the process experiences a persistent fault: all coroutines on that event loop freeze — web (including 404 error pages) is unresponsive, timers stop; storage writes on other loops / threads precisely wait for busy_timeout (default 5s) and report Failed to set storage item xxx: database is locked (all backend flavors of kv / ORM / transcript are hit), continuing until the process restarts. If a freeze occurs while there is an open transaction on the loop, its BEGIN IMMEDIATE never commits, holding the write lock indefinitely — this is the largest internal lock-holding source of database is locked in all scenarios.
Cause: The connection competition handling in SQLStorageBase._get_loop_resource has two defects: when ≥2 coroutines on the same loop concurrently fetch for the first time, they each create a connection, and the loser awaits destruction of the extra connection in the class-level threading.Lock critical section; other coroutines waiting for this lock execute synchronous blocking acquisition, directly freezing the event loop thread, and the destruction callback depends on the loop scheduling — the lock holder waits for the loop, and the loop is frozen by the lock, classic mutual deadlock.
Affected Versions: 2.10.0 (connection failure rapid failure refactoring introduced this connection competition structure) - 2.12.1-dev.1
Fixed Version: 2.12.1-dev.1
Fix Description: Connection competition is changed to be serialized by per event loop asyncio.Lock (coroutines yield rather than freeze the loop; the loser gets the serial lock and rechecks the resource table, and if hit, reuses — repeated connection creation no longer occurs); the resource table critical section only contains synchronous dictionary operations, and destruction is always executed outside the lock.
Fix Date: 2026/11/23
Reproduction Steps: Full framework topology reproduction (phases A1-A3/B) and independent WSL topology reproduction (locked at 5.01s exact throw) have been covered in the fix verification.
Regression Test: tests/unit/test_unit_storage.py::TestConcurrentFirstAcquire (concurrent first fetch completed within 15s + exactly one resource per loop)

Severity: 🔴 Critical (entire loop freezes + write loss, all backend flavors kv/ORM/transcript share the base)
Type: Storage

[BUG-053] Process hangs when storage connection is not closed (aiosqlite 0.22 connection threads are no longer daemon threads)

Issue: Processes that end without explicitly closing storage (or calling sdk.uninit()) — standalone scripts, cleanup after Ctrl+C interruption, test processes — do not exit after business code finishes, permanently stopping at the interpreter exit stage; reproduced on both Windows and Linux.
Cause: CPython exits by first executing threading._shutdown() (joining all non-daemon threads), then executing atexit callbacks. Since aiosqlite 0.22, connection worker threads are no longer marked daemon=True, and storage close hooks and inbox exit flush are registered in atexit: connection threads wait for closure, closure waits for join completion, mutual wait.
Affected Versions: All versions depending on aiosqlite ≥ 0.22 (no upper limit for aiosqlite>=0.20.0, default SQLite backend always occurs)
Fixed Version: 2.12.1-dev.1
Fix Description: The storage layer adds an exit hook sequence before thread recycling (registered via threading._register_atexit): exit flush dependent on storage (inbox buffer) → Synchronously stop all live connection worker threads (not via event loop) → Stop the bridging loop. The bounded waiting semantics of synchronous bridging are also closed: after timeout, write operations are not canceled (still completed in the background, failure warnings after the fact), transaction termination is guaranteed, and transaction start timeout throws StorageOperationError — previously queued writes are canceled and discarded, and transaction termination cancellation prevents connection and write lock release.
Fix Date: 2026/11/25
Regression Test: tests/unit/test_unit_storage.py::TestStorageExitHooks (hook order / single-step failure does not block / registration channel / SQLite connection not via event loop stops), ::TestSyncBridgeTimeoutSemantics (write not lost / failure after the fact / start timeout throws error / termination guaranteed)

Severity: 🔴 Critical (default SQLite backend always occurs, process cannot exit normally)
Type: Storage
