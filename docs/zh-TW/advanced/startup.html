啟動流程與手動控制

Tip

什麼時候需要讀這篇：需要手動驅動啟動鏈路、定製啟動順序或排查啟動失敗時。不需要則跳過，不影響其他功能的使用。

ErisPulse 的 await sdk.run() / await sdk.init() 把一整條啟動鏈路封裝成了「一行程式碼」。但當你需要完全自訂啟動流程（例如部分載入、動態註冊、熱插拔、注入自訂載入策略）時，就需要瞭解這條鏈路內部到底發生了什麼、以及如何手動驅動每一步。

本文把啟動鏈路拆解成獨立的環節，說明各自的職責、呼叫順序，並給出手動完整啟動的範例。

本文假設你已經跑通過第一個機器人，瞭解 sdk.run(keep_running=True/False) 兩種模式。本文聚焦於 init() 內部的鏈路拆解，以及 init()/init_task()/init_sync() 等更底層的進入點。

SDK 頂層進入點一覽

除了 run() 的兩種 keep_running 模式，SDK 還提供幾個更底層的初始化進入點，區別在於非同步性、回傳值、以及是否包裝例外：

進入點 非同步性 回傳值 例外處理 適用情境
await sdk.run(True) async，阻塞維持 None（關閉時自動 uninit） 模組/轉接器錯誤被攔截，不拖垮行程 純 bot 應用
await sdk.run(False) async，不阻塞 None（不自動卸載） 同上 初始化後執行自訂邏輯
await sdk.init() async，需 await bool 內部捕捉元件例外，失敗回傳 False 手動控制生命週期（配 uninit()）
sdk.init_task() async，回傳 Task 不阻塞 asyncio.Task 同 init() 並行執行其他初始化、或事件迴圈尚未執行
sdk.init_sync() 同步，阻塞目前執行緒 bool 同 init() 命令列腳本、無事件迴圈的同步進入點

常見誤區：await sdk.init() 並不等價於 await sdk.run(keep_running=False)。兩點不同：① init() 回傳 bool（失敗時回傳 False），run() 回傳 None；② init() 只做初始化、不自動卸載，run() 在事件迴圈結束時自動 uninit()。因此需要手動配對卸載或自訂生命週期時，用 init() + uninit()。

啟動鏈路總覽

sdk.init()（確切來說是其內部的 Initializer.init()）按以下順序拉起整個框架：

flowchart TD
    A[0. 準備環境<br/>設定載入 / 例外處理] --> B
    B[1. 並行發現與載入<br/>AdapterLoader.load / ModuleLoader.load<br/>內部呼叫 Finder.find_all] --> C
    C[2. 註冊轉接器<br/>AdapterLoader.register_to_manager] --> D
    D[3. 啟動轉接器<br/>adapter.startup] --> E
    E[4. 註冊模組<br/>ModuleLoader.register_to_manager] --> F
    F[5. 初始化模組<br/>ModuleLoader.initialize_modules<br/>實例化並掛載到 sdk] --> G
    G[6. 啟動路由伺服器<br/>router.start]

對應的核心元件：

層 元件 職責
發現 AdapterFinder / ModuleFinder 從已安裝套件的 entry-points 中發現轉接器/模組
載入 AdapterLoader / ModuleLoader 發現 + 匯入 + 讀取中繼資料 + 判斷啟用/停用，回傳物件清單
註冊 *Loader.register_to_manager 把物件登記到對應管理器
管理 sdk.adapter / sdk.module 維護轉接器/模組實例，提供啟停介面
初始化 ModuleLoader.initialize_modules 建立模組實例並掛載到 sdk（處理相依性拓撲排序）
路由 sdk.router HTTP / WebSocket 伺服器

重要：Finder 和 Loader 是兩層。Loader 內部已經持有一個 Finder（AdapterLoader 自帶 AdapterFinder，ModuleLoader 自帶 ModuleFinder）。絕大多數情境你只需要用 Loader，只有需要「只列出不匯入」時才會單獨用 Finder。

各環節詳解

1. 發現層：Finder

Finder 只負責「找到有哪些套件提供了轉接器/模組」，不匯入、不實例化。

from ErisPulse.finders import AdapterFinder, ModuleFinder

adapter_finder = AdapterFinder()
module_finder = ModuleFinder()

# 尋找所有已安裝的轉接器/模組 entry-points
adapter_entries = adapter_finder.find_all()    # list[EntryPoint]
module_entries = module_finder.find_all()      # list[EntryPoint]

# 依名稱尋找單個
entry = module_finder.find_by_name("MyModule")  # EntryPoint | None

每個 EntryPoint 可以 .load() 得到對應的類別，但通常不用你手動呼叫——Loader 會做。

2. 載入層：Loader

Loader 在 Finder 之上做了「匯入 + 讀中繼資料 + 判斷啟用/停用」。

from ErisPulse.loaders import AdapterLoader, ModuleLoader
from ErisPulse import sdk

adapter_loader = AdapterLoader()
module_loader = ModuleLoader()

# load() 內部：呼叫 finder.find_all() → 逐個處理 entry-point → 回傳三元組
adapter_objs, enabled_adapters, disabled_adapters = await adapter_loader.load(sdk.adapter)
module_objs, enabled_modules, disabled_modules = await module_loader.load(sdk.module)

load() 回傳的三元組：

回傳值 含義
objs (dict) 名稱 → 物件（轉接器類別 / 模組包裝物件）
enabled (list[str]) 被啟用的名稱（設定中未停用）
disabled (list[str]) 被停用的名稱

載入失敗時的診斷資訊

當某個模組/轉接器在載入或初始化階段拋出例外時，框架會跳過該元件並繼續載入其他元件，同時輸出使用者程式碼幀摘要，讓你在預設 INFO 層級下即可定位出錯位置，無需手動重開 DEBUG：

[ERROR] [ModuleLoader] 從 entry-point 載入模組 MyModule 失敗，已跳過: 'NoneType' object has no attribute 'platform'
  → MyModule/Core.py:42 in on_load
      adapter = sdk.platform
  → AttributeError: 'NoneType' object has no attribute 'platform'
  → 提示: 將日誌層級提高到 DEBUG 可查看完整堆疊；檢查模組 MyModule 的實作程式碼

診斷資訊透過 ErisPulse.runtime.diagnostics 模組產生，會自動過濾掉框架內部幀，只保留你的程式碼幀。如需在自訂載入邏輯中重複使用：

from ErisPulse.runtime import log_diagnostic

try:
    risky_init()
except Exception as e:
    log_diagnostic(e)  # 自動擷取使用者程式碼幀並寫入 ERROR 日誌

該模組還提供 extract_user_frame()（回傳結構化幀資訊）和 format_diagnostic_block()（回傳多行文字）兩個底層函式。

3. 註冊層：register_to_manager

把 Loader 產出的物件登記到管理器，讓 sdk.adapter / sdk.module 能識別它們。

# 註冊轉接器（回傳 bool，表示是否全部成功）
await adapter_loader.register_to_manager(enabled_adapters, adapter_objs, sdk.adapter)

# 註冊模組
await module_loader.register_to_manager(enabled_modules, module_objs, sdk.module)

註冊後，轉接器已登記到轉接器管理器、模組已登記到模組管理器，但都還未啟動/實例化。

4. 啟動轉接器

# 啟動所有已註冊的轉接器
await sdk.adapter.startup()
# 或指定平台
await sdk.adapter.startup("yunhu")
await sdk.adapter.startup(["yunhu", "telegram"])

註冊 ≠ 啟動。register_to_manager 只是登記；startup 才會呼叫轉接器的 start()，建立與平台的連線。

5. 初始化模組

模組比轉接器多一步——需要實例化並掛載到 sdk 上（這樣你才能 sdk.MyModule.xxx 呼叫）。這一步還處理模組間的相依性宣告與拓撲排序。

success = await module_loader.initialize_modules(
    enabled_modules, module_objs, sdk.module, sdk
)

實例化成功後，模組會出現在 sdk.<ModuleName> 上。

6. 啟動路由伺服器

await sdk.router.start(
    host="0.0.0.0",
    port=8000,
    ssl_certfile=None,
    ssl_keyfile=None,
)

路由伺服器負責接收轉接器的 Webhook / WebSocket 回呼。不啟動它，server 模式的轉接器無法收訊息。

完整手動啟動範例

下面這段程式碼等價於 await sdk.init() 的核心流程，但每一步都掌握在你手中，可以在任意環節插入自訂邏輯：

import asyncio
from ErisPulse import sdk
from ErisPulse.loaders import AdapterLoader, ModuleLoader

async def manual_startup():
    # 0. 準備環境（載入設定、註冊全域例外處理）
    #    _prepare_environment 是 init() 內部的前置步驟；手動流程也需先呼叫，
    #    否則 Loader 讀不到設定，會把所有轉接器/模組誤判為停用。
    if not await sdk._prepare_environment():
        print("環境準備失敗")
        return False

    # 1. 建立載入器（內部各自持有 Finder）
    adapter_loader = AdapterLoader()
    module_loader = ModuleLoader()

    # 2. 並行發現與載入（與 init() 內部一致用 gather）
    (adapter_objs, enabled_adapters, disabled_adapters), \
    (module_objs, enabled_modules, disabled_modules) = await asyncio.gather(
        adapter_loader.load(sdk.adapter),
        module_loader.load(sdk.module),
    )

    # 3. 註冊轉接器
    await adapter_loader.register_to_manager(
        enabled_adapters, adapter_objs, sdk.adapter
    )

    # 4. 啟動轉接器
    if enabled_adapters:
        await sdk.adapter.startup()

    # 5. 註冊模組
    await module_loader.register_to_manager(
        enabled_modules, module_objs, sdk.module
    )

    # 6. 初始化模組（實例化 + 掛載到 sdk）
    if enabled_modules:
        await module_loader.initialize_modules(
            enabled_modules, module_objs, sdk.module, sdk
        )

    # 7. 啟動路由伺服器
    await sdk.router.start(host="0.0.0.0", port=8000)

    print("手動啟動完成")
    return True

async def main():
    ok = await manual_startup()
    if ok:
        # 阻塞維持執行（手動流程不會自動阻塞）
        await asyncio.Event().wait()

if __name__ == "__main__":
    asyncio.run(main())

何時該手動啟動？

絕大多數情況下不需要手動啟動，await sdk.run() 已經把上面這些都做好了。手動啟動僅在這些情境才有價值：

  • 部分載入：只載入指定的轉接器/模組，跳過其他
  • 動態註冊：執行時根據條件註冊新的轉接器/模組
  • 自訂順序：需要打亂預設的載入順序（如先啟動某模組再啟動轉接器）
  • 注入策略：對 Loader 注入自訂的嚴格模式管理器、載入策略等
  • 除錯/診斷：在某個環節失敗時，手動驅動以定位問題

執行時細粒度控制

即使使用了 sdk.run() 完成啟動，你仍然可以在執行時單獨控制各子系統，而不必重啟整個 SDK：

轉接器熱啟停

# 熱重啟某個轉接器（修復連線，不影響其他平台）
await sdk.adapter.shutdown("yunhu")
await sdk.adapter.startup("yunhu")

# 執行中拉起一個新平台
await sdk.adapter.startup("telegram")

# 暫時下線某平台
await sdk.adapter.shutdown("telegram")

adapter.startup() 要求轉接器已被註冊到管理器。註冊發生在 init()/run() 內部，所以這是啟動之後的細粒度控制。

路由伺服器

# 暫時下線 webhook 伺服器
await sdk.router.stop()

# 重新啟動（例如換了連接埠）
await sdk.router.start(host="0.0.0.0", port=9000)

模組按需載入

# 手動載入一個（可能是懶載入的）模組
await sdk.load_module("MyModule")

優雅關閉

從 2.7.0 起，sdk.shutdown() 提供程式化優雅關閉：設定關閉事件，讓正在 await sdk.run(keep_running=True) 掛起的主迴圈回傳，進而觸發 uninit() 完成資源清理。

# 在任意協程中呼叫，觸發優雅退出（run() 掛起回傳並自動 uninit）
sdk.shutdown()

典型用途：

async def shutdown_after_idle():
    await asyncio.sleep(3600)
    sdk.shutdown()  # 閒置 1 小時後優雅退出

訊號處理：run() 內部會註冊 SIGTERM / SIGHUP 處理器，將系統訊號轉為優雅關閉——容器編排（Docker docker stop）或 systemd 停止服務時，行程會走完 uninit() 清理而非被強制終止。

  • Windows 不支援 loop.add_signal_handler，訊號處理器會自動跳過（仍可用 sdk.shutdown() 或 Ctrl+C 觸發關閉）
  • 反覆呼叫 sdk.shutdown() 是安全的（事件已設定後再次呼叫為無操作）

卸載流程

啟動的反向操作是 await sdk.uninit()，它按相反順序清理：

  1. 關閉所有轉接器（adapter.shutdown()）
  2. 卸載所有模組
  3. 清理所有事件處理器
  4. 清理管理器與 SDK 上的模組屬性

手動啟動情境下，記得在退出前呼叫 uninit() 保證優雅關閉：

try:
    await asyncio.Event().wait()   # 維持執行
finally:
    await sdk.uninit()

重啟

SDK 提供兩種重啟方式，都不需要你自己先解除安裝——框架會自行處理：

方式 呼叫 行為 適用場景
熱重啟 await sdk.restart() 同一行程內元件層程式碼級熱重載：全部模組走統一重載管線（整體語法預檢 / 快照回滾 / 身分核對），配接器先重新發現 entry-point（執行中新安裝/解除安裝的配接器即刻生效）再逐一程式碼級重載 pip 升級或安裝元件後讓程式碼生效、熱更新模組
硬重啟 await sdk.hard_restart() uninit() 後以結束代碼 42 結束行程，由外部監督者拉起全新行程 框架自身升級（升級後的框架程式碼只有新行程生效）、C 擴充模組副作用、懷疑資源洩漏 
# 熱重啟：元件層程式碼級熱重載（最常用；pip 新安裝的配接器也會被拉起）
await sdk.restart()

# 硬重啟：結束行程，交由外部監督者重啟（見下方「監督者指南」）
await sdk.hard_restart("sdk self-update")  # 可選 reason 供監督者顯示

兩點注意：

  1. 這兩個方法都用背景工作執行重啟，立即回傳 True 表示「重啟工作已排程」，而非「重啟已完成」。實際重啟在背景進行，避免中斷當前事件鏈路。
  2. hard_restart() 的原理是：卸載並將配置刷入磁碟後，以結束代碼 42（HARD_RESTART_EXIT_CODE）結束行程——它自身不會拉起新行程，必須由外部監督者偵測到結束代碼 42 後重新啟動。若直接以 python main.py 執行且無任何監督者，行程以代碼 42 結束後就結束了，不會自動重啟（框架會輸出警告提示）。

熱重啟的互斥與合併（2.11.1 起）：所有熱重載操作（單模組重載 / 全量重載 / 配接器重載 / 歸眠 / 新插件熱裝載）全程互斥——儲存風暴下連續觸發不會並發交叉，進行中的 restart 收到新請求時自動合併（請求落在普通重載持鎖期間同樣合併排隊），完成後至多補跑一輪。儲存含語法錯誤的檔案時，整輪重載會在卸載前被彙總式語法預檢拒絕（一次性列出全部錯誤檔案與行號），配接器層跳過本輪重載、restart 判定失敗，所有舊實例繼續服務；修復後再次 restart 即可。

什麼時候該用硬重啟？

熱重啟已經涵蓋了絕大多數場景（pip 升級/安裝元件、熱更新模組程式碼，含執行中新安裝的配接器）。以下場景才需要硬重啟：

  • 框架自身升級：升級 ErisPulse 本體後，新的框架程式碼只有全新行程才會生效（Python 不會重新 import 已載入的框架程式碼）。
  • 二進位函式庫（C 擴充模組）副作用：熱重啟在同一行程內進行，無法釋放 C 擴充模組、已開啟的檔案描述符、執行緒等行程級資源；硬重啟換一個全新行程，這些副作用隨之徹底清零。
  • 資源洩漏排查：懷疑存在記憶體或控制代碼洩漏時，硬重啟能拿到一個乾淨的環境。

Dashboard 管理面板裡的「框架重啟」功能，底層呼叫的就是 hard_restart()。

結束代碼 42 契約

硬重啟是跨行程協作：SDK 負責結束（代碼 42），監督者負責拉起。

角色 行為
SDK（被硬重啟時） uninit() → 將配置刷入磁碟 → 寫入硬重啟標記（原因 / PID，供監督者顯示）→ os._exit(42)
監督者 偵測到子行程結束代碼為 42 → 顯示硬重啟原因 → 重新啟動同一命令

sdk.is_supervised() 可查詢當前行程是否由監督者啟動（偵測環境變數 ERISPULSE_SUPERVISED）。CLI run 命令啟動子行程時會自動注入該標記；systemd / Docker 等外部監督者不會注入，is_supervised() 回傳 False，此時硬重啟後框架會輸出「未偵測到監督者」警告。

監督者指南

選擇適合你的監督者，讓硬重啟真正生效：

1. CLI run 命令（開發/簡單部署，推薦）

epsdk run main.py 內建監督循環：偵測子行程結束代碼，42 時立即重啟（並顯示硬重啟原因）；其它異常結束代碼按指數退避自動重試；Ctrl+C 會先優雅終止子行程（代碼 0 視為正常結束，不再拉起）。

epsdk run main.py

epsdk run --reload（開發熱重載模式，2.11.1 起）同樣走「監督行程 + 重載 worker 子行程」結構：worker 內儲存 .py 檔案即觸發元件級熱重載（不重啟整個框架）；硬重啟由監督行程重新拉起全新 worker，升級框架後新程式碼即刻生效。

2. systemd（Linux 伺服器）

RestartForceExitStatus=42 讓結束代碼 42 也觸發重啟（預設 on-failure 只對非零代碼生效）：

[Service]
ExecStart=/usr/bin/python3 /opt/mybot/main.py
Restart=on-failure
RestartForceExitStatus=42
RestartSec=2
User=mybot

3. Docker / docker-compose

容器內 PID 1 是應用程式行程，結束代碼 42 後容器結束——用 restart 策略讓它自動重啟：

services:
  bot:
    build: .
    restart: unless-stopped   # 任何結束（含 42）都重啟

4. PM2（Node 生態維運）

pm2 start main.py --name mybot --interpreter python3
# 42 被視為結束代碼，PM2 預設重啟；設定 restart_delay 防抖
pm2 set mybot.restart_delay 2000

5. supervisord

[program:mybot]
command=python3 /opt/mybot/main.py
autorestart=true
exitcodes=0,2,42    # 42 也視為「正常結束需重啟」

6. 純 Python 自訂監督者

import subprocess, sys, time

while True:
    p = subprocess.Popen([sys.executable, "main.py"])
    code = p.wait()
    if code == 42:          # 硬重啟請求
        time.sleep(0.5)
        continue
    if code == 0:           # 正常結束
        break
    time.sleep(3)           # 異常結束，退避重試

無監督者時的行為：直接以 python main.py 執行，呼叫 hard_restart() 後行程以代碼 42 結束、不會重啟。此時應接入上述任一監督者。
