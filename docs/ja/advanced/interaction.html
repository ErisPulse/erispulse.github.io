交互会話システム

Tip

この記事を読むのはいつか：wait_reply、多輪対話、定時リマインダー、セッション排他、およびトレースIDが必要な場合。不要な場合は飛ばしても、他の機能の使用には影響しません。

この記事を読んだ後でわかる：wait_replyの全パラメータの使い方とキャンセル理由、.got()による宣言的多輪対話チェーン、 セッションタイマー（remind / escalate）、多路待ち（expect / select）とセッション排他リース。

この記事で取り扱わない：多輪対話の分岐ステートマシンと再開/復元（Conversation 多輪対話を参照）； 受信箱の保持戦略のスイッチと実行時の上書き（会話受信箱を参照）。

Note

本章の内容はErisPulse 2.8.0+ が必要です。

ErisPulseは「ユーザーとの継続的な対話」をフレームワークレベルのインフラとして実装しています。1つのwait_replyから、定時リマインダー、多路待ち、セッション排他、再起動時の復元まで、すべては統一された インタラクティブセッションマネージャー（Core/Event/interaction.py、sdk.interaction）によってスケジュールされます。

{!--< tips >!--} 本文で取り扱う各機能には所有者（owner）が付いています：インタラクティブ待ち、リース、タイマーはすべて登録時のモジュール名を記録し、モジュールのアンロードまたはアダプターの停止時にフレームワークが自動的にクリーンアップし、待機側は即座に通知を受け取ります。これは、所有権システムがインタラクションの次元に拡張されたものです（所有権システムを参照）。 {!--< /tips >!--}

レプライ待ち：wait_reply

一言で：現在のコルーチンを中断して、対象ユーザーからの次のメッセージを待機し、一致すれば返信イベントを返し、タイムアウトまたはキャンセルされた場合はNoneを返します。pattern / regex / validatorで不適切な返信をフィルタリングできます。

wait_replyはインタラクティブセッションの基盤です。現在のコルーチンを中断し、ユーザーが次のメッセージで「返信」することを待ちます。

from ErisPulse.Core.Event import command

@command("ask")
async def ask_command(event):
    reply = await event.wait_reply(prompt="あなたの名前を入力してください:", timeout=30)
    if reply is None:
        await event.reply("タイムアウトしました")
        return
    await event.reply(f"こんにちは、{reply.get_text()}さん！")

パラメータ 説明 デフォルト
prompt 待機前に送信するプロンプトメッセージ None
timeout 待機のタイムアウト（秒） 60

reply = await event.wait_reply("金額を入力してください:", regex=r"\d+\s*元", timeout=30)

reply = await event.wait_reply(session=True, prompt="誰かが答えてくれますか？")

待ちとコマンドの境界（コマンド透過）

待機中に登録済みのコマンド（例：/cancel）が送信された場合、デフォルトではコマンドディスパッチャーに渡され、 レプライとして消費されません（設定項目ErisPulse.event.wait_reply.cmdpass、Trueにすると逆転する— メッセージはすべてレプライとして扱われる）。判定のテキスト口径はコマンドディスパッチャーと同じ：alt_messageが優先され、 存在しない場合はメッセージセグメントの結合（2.10.1以降、純粋なmessageセグメントアダプターでも同様に有効）。

待ちがいつキャンセルされるか

待ちが「タイムアウトするまで待つ」だけではない—以下の状況で待ちが即座に終了（wait_replyがNoneを返す）し、 呼び出し側がタイムアウトまで待つ必要がなくなります。

触発 キャンセル理由（InteractionCancelled.reason） 説明
所有モジュールがアンロード / 禁止 owner_unload 所有権のクリーンアップ：誰が登録した待ちも、誰が消えた時に一緒に回収される
アダプターが停止 / 再起動 platform_stop そのプラットフォームで中断された待ちはすべてキャンセルされる
同セッションで新しい待ち / リースに置き換えられた conflict 下記「セッション仲裁」を参照
レプライ者がブロックされた / 所有モジュールが解除された revoked レプライが一致した権限再確認：scopeの身元次元 + モジュール次元
ユーザーのレプライが一致した —— 正常経路、レプライイベントを返す

下層の例外はInteractionCancelled（InteractionError例外体系に属する）で、 wait_replyはそれをNoneを返すように変換しています。理由が必要な呼び出し側は、 sdk.interaction.register()の低層APIを使用できます。

レプライが一致する完全な判定チェーン

レプライメッセージが到着した際、インタラクションマネージャーは以下の順序で判定します（コマンドマッチの前に実行され、 対話の連続性が優先される—たとえメッセージが他の高優先度のプロセッサーに認知されたとしても、中断された対話は完了します）：

セッションキーが一致する（正確なuser次元 → セッションレベルの戻りにフォールバック）
  → pattern / regexテキストフィルター（一致しない場合は待機を続ける）
  → validator検証（失敗した場合は待機を続ける）
  → 権限再確認（scope身元次元 + ownerモジュール次元、失敗した場合は待ちを終了）
  → 待ち側をウォーキング + イベントを認領（mark_processed）

宣言的多輪対話：.got()チェーン（2.11+）

@commandは多輪対話コントローラーのプロキシを返し、.got()を使って段階的に収集ステップを宣言します。ステップ関数はパラメータ名に従って収集された値を受け取ります（コマンドエントリのパラメータも含む）、型はtype= / 注釈に従って自動解析されます。下層ではConversationにコンパイルされ、各ステップが1つの分岐、ジャンプは自動的にチェックポイントを保存します。再起動後、ユーザーのレプライは保存されたステップから継続されます（復元工場は装飾時に自動的に登録され、モジュールのアンロードに伴って自動的に登録解除されます）。

@command("weather")
async def weather(event):
    pass  # エントリ：最初の.gotのプロンプトが自動的に送信され、手動で質問する必要はありません

@weather.got("city", prompt="都市名を直接返信してください")
async def weather_city(event, city: str):
    await event.reply(f"{city}：晴れ、25℃")

@weather.got("days", prompt="何日間の予報ですか？", type=int, retry_prompt="数字を入力してください")
async def weather_days(event, city: str, days: int):
    await event.reply(f"{city} 未来 {days} 日間……")

パラメータ説明

パラメータ 説明
name 収集値の名前（後続のステップ関数のパラメータ名として注入される；プロセス内で一意、重複宣言は登録時にエラーを出す）
prompt このステップに入るときに自動的に送信される質問
timeout 単一ステップの待機タイムアウト（秒数または"90s" / "1h30m"の時長文字列、デフォルトは60s）
type 値の型（int / float / str…；解析失敗した場合はretry_promptを再送信し、最大max_retries回まで）
validator / pattern / regex レプライのフィルタリングと検証（wait_replyと同様の意味）
session セッションレベルの待ち（同じセッション内の誰でも一致する）
cmdpass コマンド通過三態（デフォルトでは/cancelなどのコマンドは待機中に通常通り実行される）

意味と境界

  • いずれかのステップがタイムアウト / 中断された場合 → 全体のプロセスが終了し、チェックポイントはクリアされます（wait_replyの意味と一致）。 ステップ関数内ではいつでもevent.reply(...)を使って中間結果を出力できます。
  • 同じユーザーは同時に1つの中断対話しか持てない—2番目のプロセスの待ちは前のものを上書きします （InteractionCancelled("conflict")）；排他を提示するには セッションリースを併用してください。
  • 収集された値はプロセス内にのみ存在します。再起動後に複雑なステータスを保持したい場合は、 Conversation（context + branch/goto + 手動チェックポイント）を使用してください。
  • @commandはプロキシオブジェクトを返します：呼び出しの動作、__name__、docstring、カスタム属性 は元の関数と完全に一致します；command.unregister(プロキシ)は自動的に展開されます。

セッションタイマー：remind / escalate

「タイムアウト」を戻り値から編集可能な原語にします。タイマーはインタラクティブセッションに紐づき、 モジュールのアンロード / アダプターの停止に伴って自動的にキャンセルされます。1セッションあたりのアクティブremindの上限は5個です。

remind：返信がなければリマインダー

@command("ticket")
async def ticket_command(event):
    await event.reply("チケットを提出しました。処理結果はここに通知されます")
    # 5分間返信がなければ優しくリマインダーを送信；ユーザーの返信はすべて自動的にキャンセルされます
    event.remind(300, "まだいますか？結果が出たらすぐにご連絡します")
    reply = await event.wait_reply(timeout=3600)
    ...
  • event.remind(delay, text=None, *, callback=None)：期限が来たら現在のセッションにtext （またはcallback(event)を実行、同期/非同期対応）を送信します。強制チェック：text と callbackはどちらか一方を指定しなければなりません（両方指定しない場合はValueErrorを送出）
  • 戻り値はReminderハンドル：reminder.cancel()で手動でキャンセル、reminder.expiredで状態を確認
  • ユーザーがこのセッションで返信した後は自動的にキャンセルされます—これが「リマインダー」の意味です： リマインダーはユーザーが沈黙しているときにのみ表示されます
  • Conversation内でも同様に使用できます：conv.remind(120, "まだ検討中ですか？")

escalate：期限に必ず届くアップグレード

event.escalate(1800, lambda e: notify_master(f"チケット30分未処理：{event.get_command_args()}"))

remindとの唯一の違いは：ユーザーの返信でキャンセルされない—アップグレードアクション（管理者に通知、人間への転送） は「タイムアウトに必ず届く」約束であり、cancel() / モジュールのアンロード / アダプターの停止でのみキャンセルされます。

remind escalate
到期行動 テキストを送信 / callbackを実行 callbackを実行
ユーザーの返信 自動的にキャンセル 影響を受けない
所有権のクリーンアップ（アンロード / プラットフォーム停止） キャンセル キャンセル
セッションごとの上限 5 なし（所有権のクリーンアップで補完）

多路待ち：expect + select

一言で：expectは期待を記述するだけで登録はせず、selectは複数の期待を統一して待機し、いずれかが先に一致したら返す (インデックス, レプライイベント)、一致しなかったら自動的にクリーンアップ。

複数の期待を同時に待機し、先着順—典型的な場面：管理者の承認を待っている間にユーザーの撤回を待つ、 多人数の協力による投票。

which, reply = await event.select(
    event.expect(pattern="同意*", user="10001"),
    event.expect(pattern="拒否*", user="10002"),
    event.expect(validator=lambda e: e.get_text() == "搁置", session=True),
    timeout=60,
)
if which is None:
    await event.reply("60秒以内に承認結果がありませんでした")
elif which == 0:
    await event.reply("承認しました")
elif which == 1:
    await event.reply("拒否しました")
  • event.expect(...)は期待の記述（待ちの登録はしない）を構築します：pattern / regex / validator / user（返信者を限定）/ session（誰でも返信可能）がサポートされます
  • event.select(*expectations, timeout=60)：一括して登録 → いずれかが一致したら返す (インデックス, レプライイベント) → 一致しなかった待ちは自動的にクリーンアップ；すべてがタイムアウトしたら(None, None)を返す。強制チェック：少なくとも1つのexpectationを渡さなければ、ValueErrorを送出
  • 一致したイベントはフレームワークによって認領（mark_processed）され、他のプロセッサーによって重複消費されることはありません

{!--< tips >!--} selectは多スレッドasyncio.waitによる手動編集と比べて：期待が一致しなかった場合の自動クリーンアップ、 一致したイベントの自動認領、権限再確認と所有権のクリーンアップがすべて有効—Futureを自分で管理する必要はありません。 {!--< /tips >!--}

Note

2.10.1以降、selectは集約待ち：すべての期待を1つの項目に統合し、独自の一致判定を行う、 同キーの多路待ち（同じuserに異なるpatternを2つ設定するなど）は互いにキャンセルされず、 いずれかのルートが先に一致したら返す。返信テキストの判定口径はalt_messageが優先され、 メッセージセグメントが戻る（コマンドディスパッチャーと同じ）。

境界説明：event.wait_for(...)はアダプターイベントの総線に直接接続され、中間件や detail_type条件フィルタリング（身元認証はディスパッチャーのエントリでカバー）は経由しない。 完全なパイプラインが必要な待ちの場合はwait_reply / selectを使用してください。

セッション排他：acquire / hold / get_owner_of

所有権が「リソース」から「セッション」へと移行—「このユーザーが現在誰に占有されているか」が第一のクエリになります。

# クエリ：このセッションは誰と対話中ですか？（空きならNoneを返す）
owner = sdk.interaction.get_owner_of(event)
if owner and owner != "MyModule":
    return  # 他のモジュールが対話中なので、干渉しない

# 排他リース：セッションを独占（deny戦略、占有中ならNoneを返す）
lease = sdk.interaction.acquire(event)          # デフォルトTTLは1時間、ttl=で渡すことも可能
if lease is None:
    return  # 既に占有されています
try:
    ...  # 独占対話
finally:
    lease.release()

コンテキストマネージャー形式（取得失敗時はSessionOccupiedErrorを送出）：

with sdk.interaction.hold(event) as lease:
    ...  # 終了時に自動リリース

リースはrenew(ttl)で更新可能；TTLは惰性で期限切れ—期限切れのリースは次回アクセス時に自動的にクリーンアップされます。

Conversation.resume()が対話を復元する際、フレームワークは自動的にリースを取得します（Conversation 多輪対話の「復元即占有」を参照）— 復元された対話は天然にセッションを保持し、他のモジュールは挿入できません。

セッション受信箱：event.history

保持戦略（7日間 / 条数上限）と実行時の上書きAPI、リスクと監査はセッション受信箱の専門記事を参照してください。

各セッションの最近のメッセージストリームを統一的に記録（ユーザーとロボットの両方）し、AIコンテキスト、 重複防止、行動分析系モジュールの共有事実のベースとして使用します—各モジュールは個別に履歴を保存する必要がありません。

messages = await event.history(20)   # 現在のセッションで最近20件、時系列昇順
for m in messages:
    print(m["role"], ":", m["text"])  # role: "user" / "bot"
  • 自動記録：入力メッセージ（role=user）+ ロボットの出力テキスト（role=bot）
  • ストレージ：独立したSQLiteテーブル、保持戦略 = 各セッションの上限（デフォルト50）+ グローバルTTL（デフォルト7日）
  • 書き込み方法：メモリバッファ + バックグラウンドバッチ書き込み（遅延最大1秒）、クエリインターフェースは未書き込みのバッファ行を自動的に結合する—同じプロセスで「あなたの書き込みを読む」影響は受けない；通常の終了（sdk.uninit / プロセス終了）時に自動的に書き込み。ハードクラッシュ / 強制終了の際、約1秒の記録が失われる可能性がある：このベースは最近のコンテキストキャッシュとして位置づけられており、監査用の永続化には適していません
  • 設定：ErisPulse.transcript = {enabled = true, max_per_session = 50, ttl_hours = 168}
  • マネージャーアプリ：sdk.transcript.append() / get() / clear()、aflush() / flush()で手動書き込み

メッセージトランザクション：message_tx

トランザクション内のすべての出力送信は自動的に記帳されます。例外が発生した場合、逆順に自動的に送信済みメッセージを撤回（アダプターがdelete_messageを実装していない場合はスキップし、トランザクションログは正常に記録される）。

async with event.message_tx():
    await event.reply("処理中です、少々お待ちください")
    result = await do_something()          # ここで例外が発生 →
    await event.reply(f"完了: {result}")   # 以前の「処理中」が自動的に撤回される

トランザクション外で送信されたものは記帳されません（ゼロオーバーヘッド）；get_send_receipts()で現在のトランザクションで送信されたレシートを確認できます。

トレースID：trace-id

各入力イベントには自動的にトレースID（event["id"]を再利用、存在しない場合は生成）が割り当てられ、以下を貫きます：

  • handlerコンテキスト（get_current_trace_id()で読み取り）
  • 出力送信（[Send]ログ行に[trace:...]を追加、message.sending/sentフックのtrace_idフィールド）
  • ライフサイクルフックデータ（dictに自動的に_trace_idを追加）
  • 定向イベント（lifecycle.emit(..., to=...)）とメッセージトランザクションのレシート

1つのメッセージが複数のモジュールによって処理された場合、全経路で同一のIDで連携できます（ログ / スロークエリ / 監査）。
