В этот трекер включены только проблемы, которые реально влияют на работу — те, что слишком незначительны, чтобы даже назвать их «легкими», здесь не представлены. Исправленные ошибки

[BUG-001] Повторная регистрация обработчиков событий приводит к многократной обработке событий

Проблема: При регистрации обработчиков с помощью нескольких декораторов, таких как @message / @notice, одно и то же событие срабатывает многократно, что приводит к многократному выполнению команд и дублированию вывода журналов.

Причина: BaseEventHandler при регистрации обработчиков в шине событий адаптера не имел логики дедупликации; каждый декоратор монтируется в шину один раз, и при диспетчеризации событий вызывается многократно.

Затронутые версии: 2.2.0-dev.0 - 2.2.1-dev.0

Версия исправления: 2.2.1-dev.0

Содержание исправления: Оптимизирован BaseEventHandler, чтобы гарантировать регистрацию обработчика для каждого типа события в адаптере только один раз, предотвращая повторные срабатывания.

Дата исправления: 2025/08/18

Критичность: 🔴 Критическая

Тип: Система событий

[BUG-002] Ошибка типа пути конфигурации адаптера в команде Init

Причина: В версии 2.3.7 при изменении путей файлов конфигурации типы параметров методов оказались несогласованными. _configure_adapters_interactive_sync принимает параметр типа str, но внутри использует оператор / объекта Path для конкатенации путей.

Затронутые версии: 2.8.0 - 2.11.0 (автоматическая запись во входящие введена с 2.8.0) Версия исправления: 2.11.1-dev.0 Содержание исправления: перед записью эхо распознаётся по self.user_id == user_id и обрабатывается по новой настройке ErisPulse.transcript.self_echo в трёх режимах: "bot" (по умолчанию) — записывается role="bot" + sender=self_id + meta.self_echo=true; "skip" — не записывается; "user" — сохраняется старое поведение. Для платформ без эха (self отсутствует или не совпадает) поведение по каждому полю остаётся неизменным. Связано: #470 (опирается на столбец meta из #467 для хранения маркера self_echo) Регрессионный тест: tests/unit/test_unit_transcript_attribution.py::TestSelfEcho

[BUG-050] Выполнение epsdk restart внутри контейнера приводит к немедленному завершению контейнера

Проблема: когда фреймворк работает как главный процесс контейнера (PID 1) (официальный образ CMD ["epsdk", "run"] или скрипт прямого запуска), после установки компонента через ep i <пакет> и выполнения по подсказке epsdk restart контейнер сразу завершается и больше не поднимается — установленный новый компонент не вступил в силу, сервис прерван. Причина: реализация epsdk restart — «завершить работающий экземпляр + перезапустить с исходными параметрами» — перезапуск выполняется под управлением процесса epsdk CLI. В сценарии контейнера целевой экземпляр — это PID 1 (главный процесс контейнера), SIGINT/SIGTERM приводит к его завершению, что означает уничтожение всего PID namespace, CLI сам и дочерний процесс, ожидающий перезапуска, убиваются вместе, и перезапуск так и не может произойти. Затронутые версии: 2.11.0 - 2.11.2 (управление экземплярами через runtime.json введено с 2.11.0; в более ранних версиях команды restart не было) Версия исправления: 2.12.0-dev.0 Содержание исправления: когда epsdk restart обнаруживает в файле состояния pid == 1 (признак главного процесса контейнера), он больше не завершает процесс с перезапуском, а отправляет процессу фреймворка SIGUSR1, и фреймворк выполняет мягкий перезапуск на уровне компонентов внутри процесса (sdk.restart(): конвейер горячей перезагрузки модулей и адаптеров, entry-point недавно установленного адаптера вступает в силу немедленно во время работы); sdk.run() регистрирует обработчик SIGUSR1, обслуживающий этот канал. Сценарий перезапуска всего процесса передаётся перезапуску контейнера (docker restart / политика restart). Регрессионный тест: tests/unit/test_unit_cli_runtime.py::TestRestartContainerHot
