Система интерактивных сессий

Tip

Когда нужно читать эту статью: если вам нужны wait_reply, многоконтактные диалоги, периодические напоминания, взаимное исключение сессий или трассировка цепочки событий. Если не нужны — можете пропустить, это не повлияет на использование других функций.

Note

Содержание этой главы доступно только в ErisPulse 2.8.0+.

ErisPulse реализовал "непрерывное взаимодействие с пользователем" на уровне фреймворка: от одной команды wait_reply до периодических напоминаний, ожидания нескольких событий, взаимного исключения сессий и восстановления после перезапуска — всё это управляется единым менеджером интерактивных сессий (Core/Event/interaction.py, sdk.interaction).

{!--< tips >!--} Каждая из описанных в этой статье возможностей имеет владельца (owner): интерактивные ожидания, аренды, таймеры — все они регистрируются с указанием имени модуля, и при отключении модуля или адаптера фреймворк автоматически очищает их, уведомляя сторону ожидания сразу, а не заставляя ждать истечения таймаута. Это расширение системы владения на интерактивные сессии (см. Система владения). {!--< /tips >!--}

Ожидание ответа: wait_reply

wait_reply является основой интерактивных сессий — приостанавливает текущий корутин, ожидая ответа от целевого пользователя в следующем сообщении.

from ErisPulse.Core.Event import command

@command("ask")
async def ask_command(event):
    reply = await event.wait_reply(prompt="Пожалуйста, введите ваше имя:", timeout=30)
    if reply is None:
        await event.reply("Таймаут")
        return
    await event.reply(f"Привет, {reply.get_text()}!")

Полный список параметров

Параметр Описание Значение по умолчанию
prompt Сообщение-подсказка, отправляемое перед приостановкой None
timeout Время ожидания (секунды) 60
pattern Фильтр по шаблону (glob: * / ? / [seq]), если не совпадает, продолжает ожидание None
regex Фильтр по регулярному выражению (должен совпадать, если задан и pattern), если не совпадает, продолжает ожидание None
validator Функция-валидатор (принимает Event, возвращает bool), если не проходит, продолжает ожидание None
callback Колбэк, вызываемый при получении ответа (альтернативный способ вместо возврата значения) None
method Метод отправки подсказки "Text"
session Сессионное ожидание: любой ответ в рамках сессии (группа / канал) будет считаться ответом False 
# Принимает только цифровую сумму, иначе продолжает ожидание
reply = await event.wait_reply("Введите сумму:", regex=r"\d+\s*元", timeout=30)

# Сессионное ожидание: сценарий совместной работы в группе, любой участник может ответить
reply = await event.wait_reply(session=True, prompt="Кто-нибудь может помочь ответить?")

Границы ожидания и команд

Во время ожидания, если поступает сообщение с зарегистрированной командой (например, /cancel), по умолчанию оно передается обработчику команд и не считается ответом (настройка ErisPulse.event.wait_reply.cmdpass, при True — сообщение всегда считается ответом). Проверка текста происходит по тому же принципу, что и при распределении команд: alt_message имеет приоритет, если отсутствует, используется объединение сообщений (с 2.10.1 поддерживается для адаптеров, использующих только message).

Когда ожидание может быть отменено

Ожидание больше не ограничено только таймаутом — следующие ситуации немедленно приводят к отмене (возврат None из wait_reply), а не к ожиданию таймаута:

Событие Причина отмены (InteractionCancelled.reason) Описание
Модуль, зарегистрировавший ожидание, был отключен / отключен owner_unload Очистка принадлежности: ожидание отменяется, когда исчезает модуль
Адаптер был остановлен / перезапущен platform_stop Все ожидания, связанные с платформой, отменяются
В той же сессии было зарегистрировано новое ожидание / аренда conflict См. раздел "Арбитраж сессий"
Ответивший пользователь был заблокирован / модуль был откреплен revoked Проверка прав доступа: по идентификатору пользователя и по модулю
Ответ был получен — Нормальный путь, возвращается событие ответа

Внутреннее исключение — InteractionCancelled (входит в систему исключений InteractionError), wait_reply уже преобразует его в возврат None; при необходимости причины можно использовать низкоуровневый API sdk.interaction.register().

Полная цепочка проверки ответа

Когда поступает сообщение с ответом, менеджер интерактивных сессий проверяет его по следующей последовательности (выполняется до командного распределения, приоритет сохранения диалога — даже если сообщение уже было распознано другим обработчиком, приостановленный диалог может быть завершен):

Соответствие сессионного ключа (точный идентификатор пользователя → сессионный ответ)
  → Фильтрация по шаблону / регулярному выражению (если не совпадает, продолжает ожидание)
  → Валидация (если не проходит, продолжает ожидание)
  → Проверка прав доступа (по идентификатору пользователя и по модулю, если не проходит, отменяет ожидание)
  → Пробуждение ожидающей стороны + подтверждение события (mark_processed)

Сессионные таймеры: remind / escalate

Превращает "таймаут" из возвращаемого значения в управляемый примитив. Таймеры привязаны к интерактивной сессии и автоматически отменяются при отключении модуля или остановке адаптера, в одной сессии одновременно может быть активно до 5 таймеров.

remind: Напоминание при отсутствии ответа

@command("ticket")
async def ticket_command(event):
    await event.reply("Заявка создана, результат будет здесь уведомлен")
    # Если нет ответа в течение 5 минут, мягко напомнить один раз; любой ответ от пользователя автоматически отменяет таймер
    event.remind(300, "Вы еще здесь? Результат будет сообщён как только появится")
    reply = await event.wait_reply(timeout=3600)
    ...
  • event.remind(delay, text=None, *, callback=None): При истечении времени отправляет сообщение text (или выполняет callback(event), поддерживает синхронные и асинхронные функции) в текущую сессию. Обязательная проверка: text и callback должны быть выбраны (если не указано, выбрасывается ValueError)
  • Возвращает объект Reminder: reminder.cancel() для ручного отменения, reminder.expired для проверки состояния
  • Автоматически отменяется при любом ответе пользователя — это и есть смысл "напоминания": напоминание появляется только при молчании пользователя
  • В Conversation также можно использовать: conv.remind(120, "Ещё думаете?")

escalate: Обязательное уведомление по истечении времени

event.escalate(1800, lambda e: notify_master(f"Заявка не обработана 30 минут: {event.get_command_args()}"))

Единственное отличие от remind: не отменяется ответом пользователя — действие "повышения" (уведомление владельца, передача в ручной режим) — это обязательное уведомление по истечении времени, отменяется только ручным cancel() / отключением модуля / остановкой адаптера.

remind escalate
Действие по истечении времени Отправка текста / выполнение callback Выполнение callback
Ответ пользователя Автоматически отменяет Не влияет
Очистка при отключении / остановке платформы Отменяет Отменяет
Ограничение на одну сессию 5 Не ограничено (очистка по принадлежности)

Многопоточное ожидание: expect + select

Ожидание нескольких путей одновременно, первый поступивший ответ — и всё. Типичный сценарий: ожидание одобрения администратора и одновременно ожидание отзыва пользователя, совместное голосование.

which, reply = await event.select(
    event.expect(pattern="同意*", user="10001"),
    event.expect(pattern="拒绝*", user="10002"),
    event.expect(validator=lambda e: e.get_text() == "搁置", session=True),
    timeout=60,
)
if which is None:
    await event.reply("В течение 60 секунд не получено ни одного результата одобрения")
elif which == 0:
    await event.reply("Одобрено")
elif which == 1:
    await event.reply("Отклонено")
  • event.expect(...) создает описание ожидания (не регистрирует ожидание): поддерживает pattern / regex / validator / user (ограничение ответившего) / session (любой может ответить)
  • event.select(*expectations, timeout=60): регистрирует все ожидания → при первом совпадении возвращает (индекс, событие ответа) → несовпавшие ожидания автоматически отменяются; по истечении времени возвращается (None, None). Обязательная проверка: хотя бы одно ожидание должно быть указано, иначе выбрасывается ValueError
  • Соответствующее событие уже признано фреймворком (mark_processed), не будет повторно обработано другими обработчиками

{!--< tips >!--} select и ручная обработка с asyncio.wait в многопоточном режиме: автоматическая очистка несовпавших ожиданий, автоматическое подтверждение соответствующего события, автоматическая проверка прав доступа и очистка по принадлежности — не нужно вручную управлять Future. {!--< /tips >!--}

Note


Начиная с версии 2.10.1, select стал агрегирующим ожиданием: все ожидания объединяются в один элемент + пользовательская логика определения совпадения, одновременное ожидание нескольких путей (например, один пользователь ожидает два разных шаблона) больше не отменяют друг друга, первый поступивший ответ возвращает результат. Проверка текста ответа происходит по тому же принципу, что и при распределении команд (alt_message имеет приоритет + возврат сообщения, если alt_message отсутствует).

Уточнение границ: event.wait_for(...) регистрируется напрямую на событийной линии адаптера, не проходит через промежуточные обработчики и фильтры по detail_type (входные права доступа проверяются на уровне входа в распределение); для полной цепочки ожидания используйте wait_reply / select.

Взаимоисключение сессий: acquire / hold / get_owner_of

Принадлежность расширяется с "ресурсов" на "сессии" — "кто сейчас взаимодействует с этим пользователем" становится важным запросом.

# Запрос: кто сейчас взаимодействует с этой сессией? (если свободна, возвращает None)
owner = sdk.interaction.get_owner_of(event)
if owner and owner != "MyModule":
    return  # Другой модуль уже взаимодействует, избегаем конфликта

# Взаимоисключающая аренда: эксклюзивное владение сессией (стратегия deny, если занята возвращает None)
lease = sdk.interaction.acquire(event)          # По умолчанию TTL 1 час, можно передать ttl=
if lease is None:
    return  # Уже занята
try:
    ...  # Эксклюзивное взаимодействие
finally:
    lease.release()

Форма контекстного менеджера (при неудаче выбрасывает SessionOccupiedError):

with sdk.interaction.hold(event) as lease:
    ...  # Автоматически освобождается при выходе

Аренда поддерживает renew(ttl) для продления; TTL лениво истекает — просроченная аренда автоматически очищается при следующем обращении.

При восстановлении диалога (Conversation.resume()) фреймворк автоматически приобретает аренду (см. Многошаговые диалоги "Восстановление = Захват") — восстановленный диалог автоматически владеет сессией, другие модули не могут вмешаться.

Почтовый ящик сессии: event.history

Стратегия хранения (7 дней / ограничение по количеству) и API для изменения во время выполнения, риски и аудит см. в специальной статье Почтовый ящик сессии.

Единая запись недавних сообщений для каждой сессии (сообщения от пользователя и бота), служит общей базой фактов для модулей, использующих контекст, предотвращения повторений, анализа поведения — каждый модуль больше не хранит историю по отдельности.

messages = await event.history(20)   # Последние 20 сообщений текущей сессии, по возрастанию времени
for m in messages:
    print(m["role"], ":", m["text"])  # role: "user" / "bot"
  • Автоматическая запись: входящие сообщения (role=user) + исходящие сообщения бота (role=bot)
  • Хранение: отдельная таблица SQLite, стратегия хранения = ограничение по количеству сообщений (по умолчанию 50) + глобальный TTL (по умолчанию 7 дней)
  • Запись: буфер в памяти + фоновая выгрузка на диск (задержка до 1 секунды), интерфейс запроса автоматически объединяет несохранённые записи из буфера — чтение из буфера в том же процессе не влияет. При нормальном завершении (sdk.uninit / выход из процесса) происходит выгрузка. При жестком сбое / принудительном завершении могут быть потеряны последние около 1 секунды записей: эта база данных предназначена для кэширования недавнего контекста, не подходит для аудита или долгосрочного хранения
  • Конфигурация: ErisPulse.transcript = {enabled = true, max_per_session = 50, ttl_hours = 168}
  • Интерфейс менеджера: sdk.transcript.append() / get() / clear(), aflush() / flush() для ручной выгрузки

Транзакции сообщений: message_tx

Все исходящие сообщения в транзакции автоматически записываются; при исключительном выходе транзакции автоматически отменяются отправленные ранее сообщения (если адаптер не реализует delete_message, отмена пропускается, но запись в журнале сохраняется).

async with event.message_tx():
    await event.reply("Обработка, пожалуйста, подождите")
    result = await do_something()          # Здесь выбрасывается исключение →
    await event.reply(f"Завершено: {result}")   # Сообщение "Обработка" автоматически отменяется

Сообщения, отправленные вне транзакции, не записываются (нулевые накладные расходы); get_send_receipts() позволяет просмотреть уже отправленные в текущей транзакции сообщения.

Трассировка цепочки: trace-id

Каждое входящее событие автоматически получает идентификатор трассировки (использует event["id"], если отсутствует, генерируется), который проходит через:

  • контекст обработчика (get_current_trace_id() для чтения)
  • исходящие отправки (строки лога [Send] с [trace:...], поле trace_id в хуках message.sending/sent)
  • данные жизненного цикла (словарь автоматически дополняется _trace_id)
  • направленные события (lifecycle.emit(..., to=...)) и транзакционные подтверждения сообщений

При обработке сообщения несколькими модулями, вся цепочка может быть прослежена по одному и тому же ID (для логов, медленных запросов, аудита).

Связь с другими системами

  • Принадлежность: ожидание / аренда / таймеры все регистрируются с указанием owner, при отключении модуля — очистка (см. Система принадлежности)
  • Область видимости: проверка прав доступа при совпадении ответа + по модулю; аудит при межмодульных вызовах — по направлению исходящих сообщений (см. Область видимости)
  • Conversation: многошаговые диалоги — это конечный автомат на основе интерактивных сессий (см. Conversation), ожидания также имеют все семантики отмены / проверки / принадлежности, описанные на этой странице

Связанные документы

  • Многошаговые диалоги (Conversation) — конечный автомат, автоматические контрольные точки и восстановление после перезапуска
  • Система принадлежности (owner) — полная картина и границы очистки принадлежности
  • Область видимости (scope) — настройка проверки прав доступа и аудита исходящих сообщений
  • Межмодульная коммуникация — межмодульные вызовы и направленные события
