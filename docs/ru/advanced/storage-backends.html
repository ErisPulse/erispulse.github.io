Хранилище

Tip

Когда нужно читать эту статью: при смене sqlite / mysql / postgres или при использовании пользовательского хранилища. Если не нужно, пропустите, это не повлияет на использование других функций.

ErisPulse включает три асинхронных хранилища, которые можно переключать с помощью конфигурации — API полностью совместимы, переключение происходит без изменения кода:

Хранилище Драйвер Установка Особенности
SQLite (по умолчанию) aiosqlite Готово к использованию Нулевая конфигурация, одиночный файл, WAL-параллелизм
MySQL / MariaDB aiomysql pip install ErisPulse[mysql] Подходит для уже существующей инфраструктуры MySQL, совместное использование нескольких экземпляров
PostgreSQL asyncpg pip install ErisPulse[postgres] Сильная поддержка транзакций, экосистема JSONB, высокая параллельность

{!--< tips >!--}

  1. Асинхронные методы являются основными (aget/aset/atransaction/aExecute), синхронные API — это слой совместимости
  2. Все внутренние функции фреймворка, такие как сохранение конфигурации, почтовый ящик сессий, контрольные точки диалога, используют одно и то же хранилище — смена хранилища означает полную миграцию
  3. Дополнительный пакет [mysql] включает cryptography — необходим для аутентификации caching_sha2_password, используемой по умолчанию в MySQL 8; при отсутствии этого пакета инициализация пула соединений завершится ошибкой {!--< /tips >!--}

Выбор хранилища

В файле config/config.toml настройте:

[ErisPulse.storage]
backend = "sqlite"        # "sqlite" (по умолчанию) / "mysql" / "postgres"
use_global_db = false     # Только для SQLite: использование глобальной базы данных data/config.db внутри пакета

Также поддерживаются переменные окружения (для Docker / 12-factor) для переопределения:

ERISPULSE_STORAGE_BACKEND=postgres
ERISPULSE_STORAGE_POSTGRES_HOST=db.example.com
ERISPULSE_STORAGE_POSTGRES_PASSWORD=secret

Правила именования переменных окружения: путь конфигурации в верхнем регистре, точки заменяются на подчеркивания
(например, ErisPulse.storage.postgres.host → ERISPULSE_STORAGE_POSTGRES_HOST).

Параметры подключения

MySQL (ErisPulse.storage.mysql)

[ErisPulse.storage.mysql]
host = "127.0.0.1"
port = 3306
user = "erispulse"
password = ""
database = "erispulse"
charset = "utf8mb4"
pool_min = 1
pool_max = 10

PostgreSQL (ErisPulse.storage.postgres)

[ErisPulse.storage.postgres]
host = "127.0.0.1"
port = 5432
user = "erispulse"
password = ""
database = "erispulse"
pool_min = 1
pool_max = 10

Note

После изменения параметров подключения необходимо перезапустить фреймворк для их применения (при горячем обновлении конфигурации будет выведено предупреждение о необходимости перезапуска). Пул соединений создается лениво по циклу событий; при временной ошибке создания (например, из-за сетевых сбоев или окна перезапуска базы данных) автоматически применяется экспоненциальная задержка повторных попыток.

Поведение при сбоях подключения

Запуск и работа фреймворка не зависят от доступности базы данных — сбой подключения к MySQL / PostgreSQL не приведет к краху или невозможности запуска:

  1. При мгновенном сбое создания пула соединений автоматически применяется экспоненциальная задержка повторных попыток (по умолчанию 3 попытки)
  2. При исчерпании попыток — записывается предупреждение (с указанием причины и времени охлаждения), фреймворк запускается и продолжает работать, только операции с хранилищем временно недоступны
  3. В течение периода охлаждения (по умолчанию 30 секунд) последующие операции с хранилищем быстро завершаются с ошибкой (не блокируют, не замедляют другие функции)
  4. По истечении периода охлаждения автоматически выполняется попытка повторного подключения — при восстановлении базы данных хранилище также восстанавливается, без необходимости перезапуска

Пример лога: mysql 连接池创建最终失败（已重试 3 次），30 秒后自动重连；期间存储操作将快速失败，框架其余功能不受影响

Завершение процесса

Процессы, завершающиеся без вызова sdk.uninit() (например, в отдельных скриптах или при прерывании), в фазе завершения интерпретатора автоматически закрывают хранилище: сначала завершаются операции сохранения, связанные с выходом (например, буфер почтового ящика), затем закрываются все соединения с базой данных, и, наконец, останавливается фоновый цикл. Поток соединения SQLite не завершается автоматически при завершении процесса, поэтому фреймворк завершает эти три шага до того, как интерпретатор завершит поток; обратный вызов atexit происходит позже, чем завершение потока, поэтому не следует обращаться к хранилищу в нем.

Семантика ошибок (начиная с 2.12)

Сценарий Поведение
Ошибка выполнения операции (таймаут на блокировку записи / SQL-ошибка / нарушение ограничений) Бросается StorageOperationError (для операций записи: aset / adelete / aclear / set_multi и синхронный мост на тех же путях) — больше не возвращается False молча, важные ошибки записи должны быть видны
Недоступность на уровне подключения (быстрая ошибка в периоде охлаждения) Возвращается False / None (быстрая ошибка на уровне подключения, сопровождается событиями storage.unreachable / storage.recovered)
Таймаут на начало транзакции (более 30 секунд) Бросается StorageOperationError (с STORAGE_TXN_BEGIN_TIMEOUT_SECS)

Важные операции записи следует оборачивать в try/except и делать компенсацию; в блоке транзакции помещайте только чистые операции с базой данных.

Асинхронный API

# Операции с ключ-значением
await sdk.storage.aset("app.name", "MyApp")
value = await sdk.storage.aget("app.name")
keys = await sdk.storage.aget_all_keys()

# Операции с таблицами
await sdk.storage.aCreateTable("users", {
    "id": "INTEGER PRIMARY KEY AUTOINCREMENT",
    "name": "TEXT NOT NULL",
})
rows = await sdk.storage.Table("users").Select("name").ToDict().aExecute()

# Асинхронная транзакция
async with sdk.storage.atransaction():
    await sdk.storage.aset("key1", "value1")
    await sdk.storage.Table("users").Insert({"name": "Alice"}).aExecute()

Синхронные методы (осторожно!)

У каждого асинхронного метода с префиксом a есть соответствующий синхронный метод (aget → get, aset → set, atransaction → transaction, aExecute → Execute), который выполняется через фоновый цикл событий — они блокируют вызывающий поток:

  • Вызов из асинхронного обработчика блокирует весь цикл событий до завершения операции с хранилищем: при частом вызове это приводит к таймауту обработчика, остановке обработки событий, зависанию веб-интерфейса и может привести к database is locked (таймаут ожидания записи). Фреймворк выводит предупреждение о частоте вызова (с указанием файл:строка (имя функции)), получив такое предупреждение, следует перенести соответствующий вызов на асинхронный метод с префиксом a
  • В режиме разработки можно включить ErisPulse.framework.strict.sync_in_async = true: синхронные вызовы больше не разрешаются, сразу бросается StrictModeError (с указанием точки вызова и инструкций по миграции), что позволяет обнаружить проблему сразу, а не на продакшене, когда она проявляется в виде зависаний
  • В режиме эксплуатации: по умолчанию верхний предел времени ожидания моста синхронных вызовов в асинхронном контексте составляет 10 секунд (ErisPulse.framework.sync_in_async_bridge_wait), по истечении которого вызов возвращает None по fail-soft схеме; ожидающие операции записи не теряются (они все еще выполняются в фоне, а неудача обозначается предупреждением), завершение транзакции и возврат соединения также завершатся, транзакция с таймаутом бросит StorageOperationError — но это крайний случай, а не разрешение

Убедитесь, что вы знаете, что делаете, иначе не используйте синхронный вариант. В чисто синхронных потоках (без цикла событий) вызовы не ограничены, это допустимый сценарий (например, синхронные входные скрипты, ожидание завершения транзакции через мост).

Использование asyncio.to_thread / пула потоков для выполнения синхронного драйвера аналогично, и в определенных сценариях может быть эффективным: при поддержке настоящей параллельности на стороне хранилища (PostgreSQL / MySQL — каждый поток имеет независимое соединение, серверная MVCC-параллельность), перемещение синхронного драйвера за пределы цикла событий является разумным подходом. Однако в случае SQLite не делайте этого — потоковые соединения будут конкурировать за одну и ту же блокировку записи с соединениями aiosqlite фреймворка, увеличивая область гонки и потенциально приводя к сбоям записи или потере данных.

Для хранилищ MySQL / PostgreSQL не нужно вручную использовать to_thread: фреймворк автоматически маршрутизирует синхронные вызовы в асинхронном контексте в ограниченный пул потоков (каждый воркер имеет независимый цикл событий, не блокируя друг друга), время блокировки основного цикла равно времени выполнения самой операции; верхний предел ожидания и fail-soft схема такие же, как выше. Хранилище SQLite сохраняет однопоточный мост последовательно (требование модели блокировки записи). Пользовательские хранилища по умолчанию не поддерживают эту возможность (установите _SUPPORTS_THREAD_BRIDGE в False).

Полный список методов см. в SQL-построителе запросов.

Отличия в диалектах

Все различия в диалектах скрыты внутри фреймворка, вызывающий код не должен их учитывать:

Различие SQLite MySQL PostgreSQL
Заполнитель ? %s (автоматически переводится) $1..$n (автоматически переводится)
UPSERT для KV INSERT OR REPLACE ON DUPLICATE KEY UPDATE ON CONFLICT DO UPDATE
Тип столбца значений KV TEXT LONGTEXT TEXT
Автоматически генерируемый первичный ключ Встроенная поддержка AUTO_INCREMENT (автоматически переводится) SERIAL (автоматически переводится)

Определение типов столбцов таблицы должно быть выполнено в стиле SQLite (например, "INTEGER PRIMARY KEY AUTOINCREMENT", "TEXT NOT NULL", "DOUBLE DEFAULT 0.0"), и диалект автоматически переводит их в эквивалентные записи для целевой СУБД.

Отладка "database is locked" в SQLite

Фреймворк SQLite уже включает: режим WAL-журнала (чтение и запись не блокируют друг друга) + busy_timeout (автоматическое ожидание при конкуренции за блокировку записи, по умолчанию 5000 мс, параметр см. ниже) + автотранзакционные соединения + несколько циклов событий с общими соединениями + транзакция BEGIN IMMEDIATE (начиная с 2.12 — транзакция сразу получает блокировку записи, устраняя проблему SQLITE_BUSY_SNAPSHOT при повышении "сначала читай, потом пиши" в deferred-транзакциях, этот busy не повторяется, и busy_timeout не может его устранить, это внутренняя причина периодических locked-ошибок при смешанной частой операции чтения и записи).

При использовании только фреймворка 2.12+ (хранение / ORM / смешанные двойные пути) locked-ошибки больше не должны возникать; если они все еще появляются, проверьте следующие сценарии:

Сценарий Причина Решение
Медленные операции в транзакции В блоке atransaction есть медленные операции (внешний HTTP, большие вычисления), удерживающие блокировку дольше, чем busy_timeout — фреймворк выводит предупреждение для транзакций, удерживающих блокировку более 1 секунды (STORAGE_TXN_SLOW_WARN_SECS), и указывает позицию начала Переместите медленные операции за пределы транзакции
Синхронный API блокирует цикл событий Множество таймаутов обработчиков событий + предупреждения о "использовании синхронного API хранилища в асинхронном контексте" Мигрируйте указанные вызовы на асинхронные методы с префиксом a (set → aset и т.д.)
Использование второго ORM В одном процессе одновременно используются sqlmodel / SQLAlchemy / обычный sqlite3 для записи в один файл базы данных Используйте только один ORM (встроенный уже является асинхронным), не смешивайте
Множественные процессы с одним файлом Множественные экземпляры / Dashboard / инструменты базы данных открывают один и тот же файл sqlite Используйте отдельные каталоги config/ для каждого экземпляра; инструменты управления открывайте в режиме только для чтения; при частой записи переключитесь на mysql / postgres (переключение происходит без изменения кода)
Старая версия фреймворка Проблема с повышением deferred-транзакции в версиях <2.12 Обновите фреймворк

Матрица блокировок (режим WAL): чтение с чтением, чтение с записью не блокируют друг друга; блокировка происходит только между записью с записью — транзакционное соединение (держит блокировку до завершения) и общие соединения циклов событий конкурируют за одну и ту же блокировку записи, длительные транзакции — главный подозреваемый в таймауте ожидания записи.

busy_timeout настраивается через ErisPulse.storage.sqlite.busy_timeout (миллисекунды, по умолчанию 5000); увеличение этого значения может продлить время ожидания при блокировке, изменения требуют перезапуска (PRAGMA применяется при установлении соединения).

Регистрация хранилища (подключаемое)

Хранилища обнаруживаются через таблицу регистрации, не ограничиваются тремя встроенными:

from ErisPulse.Core.storage import get_registered_backends

print(get_registered_backends())   # ['mysql', 'postgres', 'sqlite', ...внешние хранилища]
Пункт / Item Описание / Description
Регистрация / Register Внешние пакеты регистрируют хранилище в момент импорта модуля, вызывая register_storage_backend(name, cls); ErisPulse.storage.backend должен быть заполнен именем регистрации
Обнаружение / Discovery Внешние пакеты объявляют entry-points группу erispulse.storage.backends в pyproject.toml, фреймворк сканирует и загружает их перед созданием экземпляра хранилища
Объявление драйвера / Driver Диалект объявляет имя импорта драйвера через driver_module (пусто = встроенный драйвер без зависимостей). Зависимости драйвера объявляются в pyproject.toml пакета и устанавливаются вместе с пакетом — фреймворк не устанавливает зависимости во время выполнения, при отсутствии драйвера будет выведена ошибка с инструкцией по установке
Объявление возможностей / Capability Хранилище объявляет возможности через атрибуты класса, фреймворк использует их для маршрутизации: _SUPPORTS_THREAD_BRIDGE (настоящая параллельность, sync-in-async проходит через ограниченный пул потоков), _SUPPORTS_CONN_ROUTING (маршрутизация соединения для синхронных транзакций)
Незарегистрированное хранилище Выдается ошибка и список доступных хранилищ

Встроенные хранилища также проходят через эту таблицу регистрации (sqlite / mysql / postgres регистрируются при импорте), внешние и встроенные хранилища имеют равный статус.

Пользовательское SQL-хранилище

Пользовательские SQL-хранилища могут наследовать общий базовый класс, предоставляя только управление подключениями и диалект для выполнения запросов:

from ErisPulse.Core.Bases.sql_base import SQLDialect, SQLStorageBase

class MyDialect(SQLDialect):
    name = "mydb"
    # Переопределение: перевод заполнителей / ссылок на идентификаторы / UPSERT / сопоставление типов ...

class MyStorage(SQLStorageBase):
    dialect = MyDialect()

    async def _create_loop_resource(self): ...   # Пул соединений
    async def _destroy_loop_resource(self, r): ...
    async def _acquire_resource_conn(self, r): ...
    async def _release_resource_conn(self, r, c): ...
    async def _open_txn_conn(self): ...
    async def _close_txn_conn(self, c): ...
    async def _exec_query_on(self, kind, sql, params, conn): ...  # Выполнение запросов

Не-SQL хранилища (например, Redis) наследуют BaseStorage, реализуют асинхронный интерфейс KV, и могут использовать KVQueryBuilder для получения цепочечных операций таблиц (фильтрация в памяти, подходит для небольших объемов данных).
