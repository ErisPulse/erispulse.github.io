Документация ErisPulse

ErisPulse — это фреймворк асинхронного модульного робота, основанный на событиях — бизнес-код пишется один раз, а через адаптеры разворачивается на QQ, Telegram, Kook, Yunhu и других платформах. Система плагинов, горячая перезагрузка и полноценный инструментарий разработчика предоставляются из коробки.

Впервые используете? Просто посмотрите 5-минутное руководство — от установки до запуска первого робота, шаг за шагом.

Выберите свой путь

В зависимости от ваших целей выберите соответствующий путь обучения. Внутри каждого пути материалы расположены от простого к сложному.

Important

Нет необходимости читать всю документацию. Подавляющему большинству разработчиков достаточно последовательно прочитать пять основных документов уровня L1 (примерно 1–2 часа), чтобы самостоятельно разрабатывать 90% функциональности; вся остальная документация — справочные материалы для конкретных сценариев, к которым следует обращаться по мере необходимости — когда возникнет соответствующая задача. В начале каждого документа есть пометка «когда нужно читать этот документ».

Пять основных документов L1: Введение в разработку модулей → Базовые концепции → Класс-обёртка Event → Описание файла конфигурации → Перехват исключений

Авторам адаптеров дополнительно потребуются: Введение в разработку адаптеров → Конвертеры событий → Подробное руководство по SendDSL

Группировка по сценариям (справочно, по мере необходимости)

Группа Документы Подводные камни, если не разобраться с первым документом
Запуск и старт Процесс запуска и ручное управление · Ленивая загрузка Не понимая цепочку запуска (Finder / Loader / Manager / Router), при сбое загрузки модуля вы сможете лишь бессильно смотреть в логи
Связь и соединения Взаимодействие между модулями · Пул соединений и широковещательные рассылки · Система маршрутизации Не зная белый список сервисных контрактов (meta.services), межмодульный вызов module.call будет отклонён с ServiceNotProvidedError, и вы не будете знать причину
Хранение данных Бэкенды хранилища · Построение SQL · Сетевые клиенты Не понимая семантику периода охлаждения после сбоя соединения, при нестабильности базы данных можно ошибочно решить, что «фреймворк упал» (на самом деле операции хранилища быстро завершаются ошибкой и автоматически переподключаются после периода охлаждения)
Сообщения и диалоги Многоэтапные диалоги Conversation · Входящие сессий · MessageBuilder · Интернационализация Не понимая взаимоисключающие аренды сессий, вы столкнётесь с тем, что два модуля, одновременно ожидающие ответ одного и того же пользователя, будут вытеснять друг друга
Наблюдение за производительностью Бенчмарки и оптимизация производительности Если перед развёртыванием не смотреть цифры бенчмарков, планирование мощностей будет строиться на догадках; если после обновления не проводить регрессионное сравнение, деградация производительности останется незамеченной
Теневой и канареечный запуск Теневые модули и поэтапный перевод в основной режим Если перевести теневой модуль в основной режим раньше времени, не разобравшись с пятью барьерами изоляции, его исходящие сообщения «прослочатся» к реальным пользователям

Если не можете разобраться, какая подсистема за что отвечает, сверьтесь с этой таблицей:

Подсистема На какой вопрос отвечает Правило одной фразой
Связь (module-communication) Как модули вызывают друг друга и как адресно отправлять события? Межмодульные вызовы — через module.call; если целевой модуль объявил meta.services, можно вызывать только методы из белого списка
Права доступа (scope) Кто может использовать этот модуль, кто может вызывать события и какие действия выполнять? Три барьера — привязка модуля, допуск идентификаторов, исходящие ограничения — всё определяет конфигурация пользователя
Владение (ownership) Куда исчезают открытые модулем соединения, таймеры и подписки после его выгрузки? Кто зарегистрировал — тот и владеет; при выгрузке всё освобождается, «висячих» ресурсов не остаётся
Ленивая загрузка и спящий режим (lazy-loading) Когда модуль действительно загружается и куда он уходит при простое? activate_on — просыпается по факту использования, dormant_after — засыпает после простоя
Взаимодействие (interaction) Как дождаться следующего ответа пользователя и как организовать многоэтапный сбор? wait_reply — ожидает одного ответа, цепочка .got() — собирает несколько, аренды гарантируют отсутствие конфликтов
Теневой и канареечный режимы (shadow) Как обкатать новую версию модуля, не затрагивая рабочую систему? Тень получает копии событий, исходящие только фиксируются, promote — перевод в основной режим только после подтверждения человеком
Хранилище (storage-backends) Где хранятся данные и как поменять бэкенд? Один и тот же API хранилища, переключение sqlite / mysql / postgres через конфигурацию

Способы разработки

ErisPulse поддерживает два способа разработки:

  • Разработка модулей (рекомендуется): создание отдельного пакета модуля, установка через менеджер пакетов, удобно для распространения и управления.
  • Встраиваемая разработка: непосредственное написание обработчиков в проекте, подходит для быстрой разработки прототипа. Подробнее см. 5-минутное руководство.
