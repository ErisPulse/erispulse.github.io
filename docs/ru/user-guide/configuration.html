Описание конфигурационного файла

Note

Обязательно для L1 — одна из пяти ключевых документов в разделе "Путь чтения" на главной странице, необходима для разработки модулей.

В этом документе будет описан конфигурационный файл фреймворка. Если есть модули стороннего производителя, требующие настройки, обратитесь к документации модуля.

ErisPulse использует конфигурационный файл в формате TOML config/config.toml для управления конфигурацией проекта.

Позиция конфигурационного файла

Конфигурационный файл находится в папке config/ в корневом каталоге проекта:

project/
├── config/
│   └── config.toml
├── main.py

Подсказки по нескольким экземплярам и файлу блокировки

При запуске фреймворк создает файл блокировки .erispulse_config.lock в каталоге config/ и удерживает его до завершения процесса (используется для обнаружения общего каталога конфигурации для нескольких экземпляров). Если в журнале появляется предупреждение «Обнаружено, что конфигурационный файл, возможно, одновременно используется другим экземпляром ErisPulse», это означает, что два или более процессов ErisPulse записывают в один и тот же файл конфигурации (типичный сценарий: несколько контейнеров монтируют один и тот же каталог config/ хоста) — одновременная запись будет перезаписывать друг друга, поэтому для каждого экземпляра используйте отдельный каталог конфигурации.

Обработка ошибок при загрузке конфигурации

Фреймворк различает три состояния ошибок при загрузке config.toml и предоставляет действенные диагностические сообщения, а не просто переключается на конфигурацию по умолчанию:

Состояние ошибки Условия срабатывания Поведение фреймворка
Файл отсутствует config.toml отсутствует Нормальный запуск, используется пустая конфигурация (без предупреждений)
Ошибка синтаксиса TOML Файл существует, но формат неверный (например, отсутствуют кавычки, не закрыты скобки) Выводится номер строки/столбца и причина ошибки, и предыдущая действительная конфигурация сохраняется для продолжения работы (изменения в текущем файле не применяются)
Ошибка прав / другие ошибки Нет прав на чтение, ошибки ввода-вывода и т. д. Выводится ясная причина, и предыдущая действительная конфигурация сохраняется для продолжения работы

Важно: "Предыдущая действительная конфигурация" ≠ "Конфигурация по умолчанию": при повреждении файла фреймворк использует последнюю успешно проанализированную конфигурацию, загруженную перед запуском (при изменении поврежденного файла во время работы используется старое значение), а не сбрасывает все параметры на заводские значения. При устранении сбоев не предполагайте, что "конфигурация была сброшена".

Например, если вы случайно написали port = 8000 (без кавычек для строки), журнал выведет примерно следующее:

[ERROR] [Config] Синтаксическая ошибка в конфигурационном файле config/config.toml (строка 3, столбец 1): ...
[WARNING] [Config] Не удалось прочитать конфигурационный файл. Продолжаем работу с последней действительной конфигурацией, текущие изменения в файле не применились — пожалуйста, исправьте и перезагрузите или перезапустите

Таким образом, вы можете сразу определить проблему на уровне INFO, а не задаваться вопросом «почему мои изменения в конфигурации не вступили в силу».

Изменили конфигурационный файл во время работы? Если вы вручную отредактировали config.toml во время работы бота, внося синтаксическую ошибку, фреймворк при следующей попытке записи (слияния конфигурации) выведет сообщение «Конфигурационный файл поврежден (ошибка синтаксиса, строка X), невозможно записать — пожалуйста, сначала исправьте конфигурационный файл и перезапустите», а не запутанное «Ошибка записи». Конфигурационные параметры, которые должны быть записаны, сохраняются, не теряются.

Сохранение комментариев и минимизация записи на диск

Комментарии и порядок ключей в config.toml сохраняются полностью после записи фреймворком: независимо от того, используется ли setConfig(), сохранение через CLI-конфигурационный мастер или шаблон конфигурации адаптера/модуля, фреймворк изменяет только соответствующие ключи, ваши комментарии и отсортированный порядок не будут удалены или перестроены (на основе безупречного TOML-движка tomlclass, не затрагивающего неизмененные данные байт-в-байт, стиль разделителей строк CRLF/LF также не изменяется).

Фреймворк сдержан в записи данных на диск:

  • Конфигурация по умолчанию фреймворка не записывается автоматически: gc, scope, transcript и другие встроенные значения по умолчанию хранятся только в памяти, config.toml содержит только ключи, установленные явно, сохраняя минималистичность. Полный список настраиваемых параметров см. в config/config.full.example проекта, скопируйте нужные в config.toml и отредактируйте (не настроенные параметры по-прежнему используют встроенные значения по умолчанию, поведение не меняется).
  • Автоматическое поддержание config.full.example: независимо от того, выполняли ли вы epsdk init, каждый раз при запуске фреймворка (epsdk run / main.py) будет автоматически генерироваться config/config.full.example, если файл отсутствует; первая строка файла — это метка, поддерживаемая фреймворком, генератор обновляется (например, при добавлении новых конфигурационных параметров, установке новых компонентов) при запуске; удаление или изменение первой строки означает ручное управление, фреймворк больше не будет перезаписывать.
  • Шаблоны конфигурации адаптера/модуля: при первом инициализации шаблон с комментариями сохраняется на диск (описание полей — это комментарии); поля, помеченные как example, не записываются, только сохраняются в config.full.example для справки.
  • Чтение комментариев по объявлению: комментарии в конфигурационном файле сами по себе являются документацией — ep doctor и сообщения о неудачной проверке конфигурации будут ссылаться на оригинальный комментарий в файле (даже если вы вручную изменили комментарий, сообщение будет соответствовать текущему состоянию файла), при возникновении ошибки не нужно снова обращаться к документации для поиска значения поля.

Переменные окружения для перекрытия конфигурации

Фреймворк поддерживает перекрытие конфигурационных параметров ErisPulse.* с помощью переменных окружения (подходит для Docker / контейнеризации / CI-развертывания, без необходимости изменять config.toml).

Правила именования: замените точечный путь ErisPulse.<section>.<key> на все заглавные буквы, замените . на _ и добавьте префикс ERISPULSE_:

Конфигурация Переменная окружения Пример значения
ErisPulse.server.port ERISPULSE_SERVER_PORT 9000
ErisPulse.server.host ERISPULSE_SERVER_HOST 0.0.0.0
ErisPulse.logger.level ERISPULSE_LOGGER_LEVEL DEBUG
ErisPulse.framework.strict_mode ERISPULSE_FRAMEWORK_STRICT_MODE 2

Описание поведения:

  • Наивысший приоритет: переменные окружения перекрывают «конфигурационный файл» и «значения по умолчанию», автоматически преобразуются по типу (bool / int / float / список, разделенный запятыми / строка)
  • Не сохраняются: перекрытие действует только во время выполнения, не записывается обратно в config.toml
  • Поддержка горячей перезагрузки: после изменения переменных окружения во время выполнения, в сочетании с перезагрузкой конфигурации, изменения вступают в силу
# Пример развертывания в Docker: без изменения config.toml, просто перекройте порт
ERISPULSE_SERVER_PORT=9000 docker compose up -d

Примечание: ErisPulse.server.port и другие фреймворковые конфигурации через get_server_config() и другие API, будут подвержены влиянию переменных окружения.

Связывание переменных окружения с конфигурацией модуля (2.9.0+)

Сама конфигурация модуля (ConfigClass) поддерживает привязку переменных окружения на уровне полей — в field(metadata=...) объявите env:

@dataclass
class MyConfig(BaseConfig):
    api_key: str = field(default="", metadata={
        "description": "API ключ",
        "env": "MYMODULE_API_KEY",   # привязка переменной окружения
    })
    retries: int = field(default=3, metadata={"env": "MYMODULE_RETRIES"})

Описание поведения:

  • Приоритет: переменная окружения > config.toml > значение по умолчанию (конфигурация горячего обновления также сохраняет этот приоритет)
  • Преобразование типа: значение переменной окружения автоматически преобразуется по аннотации поля — str как есть, int / float / bool (true / 1 / yes / on) автоматически преобразуются, list / dict через JSON-парсинг; при неудачном преобразовании перекрытие игнорируется (возвращается конфигурация / значение по умолчанию) и выводится предупреждение
  • Одно объявление, везде действует: конфигурация, горячее обновление, проверка используют одну и ту же цепочку; схема конфигурационной панели будет помечать env имя, комментарии в шаблоне config.toml также будут указывать доступные переменные окружения (шаблон не записывает фактические значения переменных окружения, чтобы избежать утечки)
  • Полная совместимость: поведение полей, не объявленных env, не меняется; непосредственное создание экземпляра ConfigClass (без использования конфигурационной цепочки фреймворка) не подвержено влиянию переменных окружения
# Пример развертывания в Docker: без изменения config.toml, просто вставьте модульный ключ
MYMODULE_API_KEY=sk-xxx docker compose up -d

Конфигурационный класс vs ORM-поле, что выбрать? Конфигурационный класс управляет «как работает модуль» (параметры поведения, горячее обновление), ORM Field() управляет «какие данные создал пользователь» (таблица базы данных, запросы). Оба используют одну и ту же систему ограничений и движок валидатора; таблица сравнения см. в Слое данных модели · Когда использовать какое объявление.

Горячее обновление конфигурации

Начиная с 2.7.0, фреймворк систематически поддерживает горячее обновление конфигурации. После внешнего изменения config.toml (фоновый watcher каждые 5 секунд проверяет) или вызова кодом setConfig(), все компоненты автоматически реагируют:

Компонент Поддерживаемые конфигурации для горячего обновления Поведение
Logger logger.level / log_files / log_dir (включая параметры сегментации) / memory_limit / format / exclude_levels Автоматически переприменяются (с обнаружением изменений)
CommandHandler event.command.prefix / case_sensitive / allow_space_prefix / must_at_bot Действует с первой следующей сообщением
Адаптеры (конкурентность) framework.handler_max_concurrency Сигнал обнуления кэша, перестроение по новому значению
Активный GC framework.proactive_gc_* Конфигурация изменяется, задача GC перезапускается, поддерживает изменение/отключение/включение во время выполнения
Система мастеров master.users Каждый вызов is_master() проверяет в реальном времени, не требуется перезапуск
Конфигурации модулей/адаптеров Собственные конфигурационные параметры Вызывается on_config_update(old, new)回调

Конфигурации, требующие перезапуска (небезопасно безопасно переключить, при изменении выводится предупреждение «Требуется перезапуск процесса для вступления в силу»):

Конфигурация Причина
router.cors.* / router.security.* Промежуточные слои записываются в FastAPI при запуске службы, безопасное горячее переключение во время выполнения невозможно
storage.use_global_db SQLite файловый дескриптор уже открыт во время выполнения, безопасная смена пути невозможна

Ошибка при редактировании и сохранении? Если при редактировании config.toml возникает временная синтаксическая ошибка, фреймворк сохранит последнюю действительную конфигурацию и выведет диагностическое сообщение, не будет рассылать пустую конфигурацию компонентам (чтобы избежать on_config_update получения пустого значения и ошибочного возврата к значению по умолчанию).

Внутреннее разбиение цепочки горячего обновления

«Как модули узнают, что конфигурация изменилась?» — за этим стоит цепочка обнаружения → перезагрузки → рассылки:

flowchart TD
    A["Внешнее редактирование config.toml"] --> B{"Кто первым обнаружит?"}
    B -->|"Фоновый поток watcher<br/>Проверка mtime каждые 5 секунд"| C["_check_file_change определяет изменение"]
    B -->|"При чтении конфигурации<br/>Кэш истек более 60 секунд"| C
    C --> D["_load_config перезагружает TOML"]
    D --> E{"Успешно?"}
    E -->|"Нет (синтаксическая ошибка)"| F["Сохраняет последнюю действительную конфигурацию<br/>Не рассылает, выводит диагностическое сообщение"]
    E -->|"Да"| G["lifecycle.emit config.updated<br/>Передает old_config / new_config"]
    G --> H["Компоненты-слушатели реагируют<br/>(logger / scope / command / GC ...）"]

Две линии обнаружения (достаточно одной, обе могут быть использованы):

Линия Механизм Время срабатывания
Фоновый watcher daemon поток config-watcher каждые 5 секунд wait опрашивает файл mtime После редактирования файла максимум через 5 секунд
Ленивая проверка При любом getConfig() чтении, если кэш более 60 секунд старый, сначала проверяет файл При следующем чтении конфигурации

Фреймворк не повредит сам себя: setConfig() при записи отмечает «mtime, записанный самим», watcher при сравнении исключает его, обнаруживает только внешние изменения как изменения.

Два типа событий изменения конфигурации:

Событие Инициатор Данные Типичный сценарий
config.set Код / Dashboard вызывает setConfig() {key, old_value, new_value} Одиночное изменение (шаблон генерации, состояние записи, изменение конфигурации во время выполнения)
config.updated После редактирования внешнего файла watcher/Ленивая проверка ловит {old_config, new_config, config_file} Ручное редактирование config.toml

setConfig() по умолчанию задерживает запись на диск на 5 секунд (объединяет несколько записей), immediate=True записывает немедленно. watcher обнаруживает внешнее изменение, только обновляет кэш в памяти, не записывает обратно в файл.

Список компонентов-автоматических ответчиков (оба типа событий обычно подписываются, реакция одинакова):

Компонент Подписка Реакция
Logger config.set + config.updated Уровень/файл/каталог сегментации/память лимит/формат/уровни исключения переприменяются (с обнаружением изменений, без изменений не двигаются)
Scope config.updated Перестроение кэша привязки области
Система команд config.updated Перезагрузка параметров префикса/регистра/пробела перед префиксом/must_at_bot, действует с первой следующей сообщением
Адаптеры (конкурентность) config.set + config.updated handler_max_concurrency сигнал обнуления перестроения
Активный GC config.set + config.updated proactive_gc_* перезапуск задачи GC
Адаптеры Перенаправление в on_config_update Callback on_config_update(old, new) для каждого адаптера
Модули Перенаправление в on_config_update Callback on_config_update(old, new) для каждого модуля
Хранилище config.updated Изменение use_global_db только предупреждение (требуется перезапуск)
Роутер config.updated Изменение cors.* / security.* только предупреждение (требуется перезапуск)

API чтения и удаления конфигурации

getAllConfig: полный снимок конфигурации

Вместо прямого чтения приватного _cache (внешнее чтение приватных свойств не защищено обратной совместимостью):

config = sdk.config.getAllConfig()     # Глубокая копия снимка, изменение на месте не влияет на состояние фреймворка
config["ErisPulse"]["server"]["port"]

Вид с точки зрения getConfig одинаков: не записанные setConfig / delete уже отражены, строго согласованы с содержимым файла после задержки записи.

delConfig: удаление ключа конфигурации

setConfig(key, None) просто устанавливает пустое значение, ключ остается в файле; delConfig удаляет ключ из файла:

sdk.config.delConfig("ErisPulse.modules.status.OldModule")            # Задержка записи
sdk.config.delConfig("OneBot.deprecated_key", immediate=True)         # Запись немедленно
  • Поддерживает точечные пути; если ключ не существует, возвращает False
  • Запись идет по пути сохранения комментариев, остальное содержимое файла и порядок не изменяются
  • Использует событие config.set (события new_value=None): адаптеры / модули on_config_update и другие существующие слушатели без изменений могут воспринимать удаление

При диагностике «бот работает, но WebUI не открывается» сначала убедитесь, что порт свободен.

Конфигурация системы мастеров

Система мастеров используется для определения «владельца фреймворка» (например, администратора бота). master.users поддерживает два способа записи:

[ErisPulse.master]
# Способ 1: глобальный мастер (действует на всех платформах)
users = ["123456", "789012"]

# Способ 2: мастер по платформе (dict)
# users = { yunhu = ["123456"], telegram = ["789012"] }
Конфигурация Тип Значение по умолчанию Описание
users array / object пусто Список аккаунтов мастеров. list форма — глобальный мастер (действует на всех платформах); dict форма — мастер по платформе (ключ — имя платформы, значение — список аккаунтов мастеров для этой платформы)

В коде проверка осуществляется через master.is_master(event) или master.is_master(platform, user_id), каждый вызов читает конфигурацию в реальном времени (поддерживает горячее обновление, перезапуск не требуется):

from ErisPulse.Core import master

if master.is_master(event):
    await event.reply("Привет, хозяин")

Цепочка проверки и удаление в режиме реального времени

Цепочка проверки мастеров: конфигурационный мастер → запись в режиме реального времени → провайдер цепочки:

from ErisPulse.Core import master

master.is_master(event)                      # проверка по событию
master.is_master("yunhu", "123")             # явная проверка
master.add("yunhu", "123")                   # добавление в режиме реального времени (по умолчанию сохраняется; persist=False только в памяти)
master.remove("yunhu", "123")                # удаление (по умолчанию сохраняется)
master.list()                                # объединение: {"global": [...], "<platform>": [...]}

Пользовательские источники идентификации (провайдеры)

Помимо конфигурации, можно зарегистрировать пользовательские источники идентификации: fn(platform, user_id) -> bool, встроенные источники идентификации (конфигурация + запись в режиме реального времени) не срабатывают, последовательно проверяются, если любой провайдер разрешает, то считается мастером. Подходит для подключения адаптеров, баз данных ролей и других внешних систем идентификации.

Точка регистрации master.provider поддерживает декораторы / функциональный стиль, удаление происходит через fn.unregister():

from ErisPulse.Core import master

# Стиль 1: декоратор (рекомендуется, постоянный источник идентификации)
@master.provider
def admin_provider(platform, user_id):
    return user_id in {"999"}     # пользовательская логика проверки

master.is_master("yunhu", "999")   # True
admin_provider.unregister()        # отмена регистрации, когда больше не нужно

# Стиль 2: функциональный (регистрация при загрузке модуля / отмена при выгрузке)
fn = master.provider(admin_provider)
fn.unregister()

Исключения провайдера перехватываются и пропускаются, не блокируют цепочку проверки идентификации. Привязка метода экземпляра не может быть зарегистрирована с unregister, для сценариев с парной регистрацией/отменой используйте функцию уровня модуля.

Приоритет пользователя: зона действия мастера определяется пользователем

Параметр master=True команды — это по умолчанию разработчика: пользователь может переопределить или ослабить (см. [Единая конфигурация перезаписи событий (event.overrides)], пользовательская явная конфигурация вступает в силу).

Конфигурация активного GC

После инициализации SDK запускается фоновая задача активного GC, периодически выполняющая сборку мусора Python и внутреннюю очистку ресурсов (очистка неактивных ботов и т.д.). Все параметры поддерживают горячее обновление, изменения немедленно перезапускают задачу.

Конфигурация Тип Значение по умолчанию Описание
proactive_gc_interval number 300 Интервал сборки мусора (секунд), поддерживает десятичные дроби. 0 означает отключить активный GC
proactive_gc_generation integer 0 Обычный цикл сборки мусора поколений (0/1/2, ограничено 0..2). Обратите внимание, что gc.collect(2) эквивалентно полной сборке мусора, по умолчанию 0 сохраняет легкость; глубокая сборка мусора запускается периодически по proactive_gc_full_every
proactive_gc_full_every integer 20 Каждые N циклов делать полную сборку мусора, 0 означает отключить периодическую полную сборку. Полная сборка мусора ограничена порогом proactive_gc_memory_growth_mb
proactive_gc_memory_growth_mb integer 32 Порог роста памяти для полной сборки мусора (МБ): по сравнению с базой памяти после последней полной сборки (в первую очередь tracemalloc, затем RSS), только если рост достигает этого значения, выполняется полная сборка мусора. 0 означает не устанавливать порог
proactive_gc_idle_only boolean false При включении, в периоды пиковых нагрузок (существуют незавершенные pending handler) этот цикл пропускается, чтобы избежать пауз и конкуренции с обработкой сообщений; внутренняя очистка ресурсов не затрагивается
proactive_gc_gen0_min integer 500 Порог запуска обычного цикла сборки мусора для gen0: gc.get_count()[0] ниже этого значения, цикл пропускается (пустой цикл почти нулевые накладные расходы). 0 означает всегда выполнять сборку

Изменение 2.7.1: значение по умолчанию proactive_gc_generation изменилось с 2 на 0, значение по умолчанию proactive_gc_full_every изменилось с 0 на 20. Ранее generation=2 означало, что каждый цикл делает самую тяжелую полную сборку мусора; новое значение по умолчанию при сохранении охвата сборки мусора значительно снижает накладные расходы пустых циклов. Явно заданные старые значения по-прежнему действуют по буквальному смыслу.

Строгий режим

Строгий режим управляет стратегией обработки компонентов, которые не соответствуют требованиям или завершаются с ошибкой на этапе загрузки. Современные модули/адаптеры должны наследовать соответствующие базовые классы (BaseModule/BaseAdapter), компоненты, не унаследовавшие базовый класс, влияют на систему контекста фреймворка и на бэкап-очистку, что может привести к утечке ресурсов.

Изменение 2.5.2: значение по умолчанию изменилось с 1 (пропуск) на 0 (мягкий), чтобы уменьшить количество проблем при первом использовании новыми пользователями. Компоненты, не унаследовавшие базовый класс, будут предупреждены и попытаться загрузиться, а не отклонены. Чтобы восстановить предыдущее поведение, явно установите strict_mode = 1.

Уровень Название Поведение
0 Мягкий (по умолчанию) Нарушения только предупреждения, компоненты, не унаследовавшие базовый класс, все равно будут пытаться загрузиться (совместимость со старыми компонентами)
1 Строгий-пропуск Отклонить компоненты, не унаследовавшие базовый класс, и пропустить, остальное нормально запускается
2 Строгий-фатальный Собрать все нарушения и сообщить о них, затем завершить весь запуск

На всех уровнях, «ошибки на этапе загрузки/регистрации/инициализации» — это сбой компонента, всегда будут пропущены; различие заключается в том, что:

  • 0 → 1: единственное изменение поведения — «не унаследовавшие базовый класс» из «все еще загрузить» в «пропустить».
  • 1 → 2: все нарушения (не унаследовавшие базовый класс, загрузка не удалась, регистрация не удалась, инициализация не удалась и т.д.) повышаются до фатального, будут собраны на контрольном пункте запуска и выведены список нарушений, затем завершится.

Список исключений

Если некоторые компоненты действительно временно не могут быть обновлены (например, зависящий от старого модуля), их можно добавить в список исключений, и даже если они не соответствуют требованиям, они будут обрабатываться в соответствии с мягким режимом и продолжать загрузку:

[ErisPulse.framework.strict_mode_exceptions]
modules = ["SeTu", "SomeLegacyModule"]
adapters = ["OldAdapter"]

Когда компонент отклоняется строгим режимом, журнал будет четко указывать, как восстановить загрузку (добавить в список исключений или понизить уровень).

Связь с CLI

Автоматическая проверка до запуска epsdk run (анализируемость конфигурационного файла, целостность обязательных конфигураций компонентов) по умолчанию следует этой конфигурации: если не 0, проверка не удалась, запуск отклоняется, если 0, только предупреждения продолжаются. Также можно временно изменить без изменения конфигурации: epsdk run --strict включает проверку и строгий уровень одновременно (уровень только повышается, передается через ERISPULSE_FRAMEWORK_STRICT_MODE в процесс), --no-strict временно понижает до мягкого и только предупреждает.

Конфигурация модулей

Каждый модуль может определить свою конфигурацию в файле конфигурации:

[MyModule]
api_url = "https://api.example.com"
timeout = 30
enabled = true

В модуле читать и записывать конфигурацию:

from ErisPulse import sdk

# Чтение конфигурации
config = sdk.config.getConfig("MyModule", {})
api_url = config.get("api_url", "https://default.api.com")

# Запись конфигурации во время выполнения (отложено сохранение)
sdk.config.setConfig("MyModule.timeout", 60)

# Немедленное сохранение в файл
sdk.config.setConfig("MyModule.timeout", 60, immediate=True)

setConfig по умолчанию использует отложенное сохранение (примерно каждые 5 секунд сохраняется в файл), установка immediate=True немедленно сохраняет. Изменения конфигурации вызывают событие config.set жизненного цикла.

Конфигурация области действия (scope)

Note

Эта функция требует ErisPulse 2.8.0+.

Область действия определяет в каком контексте действует — какие модули доступны в определенной платформе / боте / сессии (1. уровень модуля), какие события принимаются для определенного пользователя / группы / бота / адаптера (2. уровень идентичности), какие исходящие вызовы может выполнить модуль (3. уровень исходящих вызовов):

[ErisPulse.scope]
default_allow = true        # Глобальный фолбэк (false = явный отказ строгого режима; не влияет на исходящий уровень)
cache_size = 1024           # Размер LRU кэша

# ① Модульный уровень (приоритет: сессия > бот > платформа; элементы поддерживают точное / glob / re: регулярные выражения)
[ErisPulse.scope.platforms.onebot11]
modules = ["Chat", "Tool*"]
blocked = ["re:^Danger"]

# Подуровень привязки с merge = true объединяет элементы с низшим приоритетом (по умолчанию общее перезаписывание)
[ErisPulse.scope.bots.onebot11."123456"]
modules = ["Music"]
merge = true

# ② Уровень идентичности (приоритет: пользователь > сессия > бот > адаптер; на каждом уровне только allow или deny)
[ErisPulse.scope.identity.adapters.onebot11]
deny = true                 # Все события этой платформы отбрасываются на входе
[ErisPulse.scope.identity.users.onebot11]
allow = ["u_admin"]         # Ключи пользователей поддерживают glob / re: регулярные выражения
deny = ["u_bad", "spam_*"]

# ③ Исходящий уровень (по умолчанию разрешено все; правила в виде встроенной таблицы, элементы поддерживают точное / glob / re: регулярные выражения)
[ErisPulse.scope.actions.MyModule]
send = { deny = true }                    # Полностью запрещено отправлять
api = { allow = ["get_*"] }               # Только разрешены стандартные API для запросов
request = { deny = true }                 # Запрещено обрабатывать запросы
Конфигурация Тип Описание
scope.default_allow boolean Глобальный фолбэк: разрешение/отказ для модулей/идентичности, не попавших под правило (true)
scope.cache_size integer Размер LRU кэша (по умолчанию 1024)
scope.platforms / bots / sessions table ① Модульные три уровня привязки: {modules=[...], blocked=[...], merge=bool?}
scope.identity.adapters / bots / sessions / users table ② Четыре уровня идентичности: {allow=true} / {deny=true}
scope.actions.<module>.<action> table ③ Правила исходящих действий: `{allow=[...], deny=true

Подробности и API времени выполнения (модульные sdk.scope.set_module() / set_identity() / set_action(), проверка is_allowed() / is_identity_allowed() / is_action_allowed(), а также словарный фолбэк get() / set() / delete()) см. в Область действия (scope).

Единая конфигурация перезаписи событий (event.overrides)

Система единой перезаписи: по типу события перезаписать поведение любого обработчика модуля, не изменяя код модуля. Стандартные типы OneBot12 (meta / message / notice / request) и расширенные типы (command) имеют свои собственные настраиваемые параметры:

[ErisPulse.event.overrides]

# message: текстовое условие (AND с условиями в коде)
[ErisPulse.event.overrides.message.ChatModule]
pattern = "闲聊*"

# notice / request / meta: detail_type белый список (элементы поддерживают точное / glob / re: регулярные выражения)
[ErisPulse.event.overrides.notice.MyModule]
detail_types = ["group_increase"]

# command (расширенный тип): реализация параметров перезаписи (приоритет пользователя; отключение через acl deny)
[ErisPulse.event.overrides.command.MyModule.restart]
master = true               # Перезапись как только владелец фреймворка (false — разрешить разработчикам владение)
hidden = true               # Скрыть в списке помощи
aliases = ["rs"]            # Активные псевдонимы

# acl (command专属): черный и белый списки пользователей (имя команды поддерживает glob / re: регулярные выражения, точные ключи имеют приоритет)
[ErisPulse.event.overrides.acl."roll*"]
allow = ["onebot11:u_vip"]  # Идентификатор пользователя "platform:user_id"
deny = ["onebot11:u_bad"]

# ACL фолбэк: разрешение (true) / строгий отказ (false) для команд без настроенной ACL
acl_default_allow = true
Конфигурация Тип Описание
event.overrides.message.<module> table Текстовое условие: {pattern="...", regex="..."}
event.overrides.notice / request.<module> table {detail_types=[...], pattern, regex}
event.overrides.meta.<module> table {detail_types=[...]}
event.overrides.command.<module> table Параметры перезаписи модуля (scalar hidden = true и т.д.)
event.overrides.command.<module>.<command> table Перезапись параметров команды (приоритет команды)
event.overrides.acl.<command> table Черный и белый списки пользователей: {allow=[...], deny=[...]}
event.overrides.acl_default_allow boolean ACL фолбэк: разрешение (true) / строгий отказ (false) для команд без настроенной ACL

API времени выполнения (после from ErisPulse.Core.Event import overrides вызовите overrides.message.set() / overrides.command.set() / overrides.acl.set() по подпространствам типа, или через sdk.Event.overrides доступ к overrides.message.set() / overrides.command.set() / overrides.acl.set() и т.д.)
