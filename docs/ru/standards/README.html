Технические стандарты

Tip

Когда читать этот документ: когда вы разрабатываете или модифицируете адаптер и вам нужно проверить, соответствуют ли преобразование событий, ответы API, методы отправки и т. д. кроссплатформенному стандарту ErisPulse, обращайтесь к соответствующим спецификациям в этом каталоге для сверки. Если не знаете, с чего начать, сначала прочитайте общий обзор ниже.

Общий обзор: Руководство по стандартизации адаптеров — принципы стандартизации, карта стандартов, правила именования, шаблоны обработки различий и чек-лист разработчика. Для новых адаптеров/новых возможностей начните с него.

Этот документ содержит технические стандарты ErisPulse, обеспечивающие согласованность и совместимость между всеми компонентами.

Список стандартных документов

  1. Стандарт типов сессий - Определения и сопоставление типов сессий ErisPulse
  2. Стандарт преобразования событий - Стандарты преобразования событий платформы, расширение правил именования, стандартные сегменты сообщений
  3. Стандарт ответа API - Стандарт формата ответа API адаптера и требования к расширению
  4. Спецификация методов отправки - Назначение имен методов класса Send, параметры и требования к обратному преобразованию
  5. Спецификация действий запроса - Требования к полям событий запроса, DSL HandleRequest и требования к реализации адаптера
  6. Стандарт действия API - Единый интерфейс стандартных действий API OneBot12 (управление пользователями/группами/каналами/сообщениями/файлами с фрагментами/мета-действия)
  7. Руководство по стандартизации адаптеров (общий план) - Принципы стандартизации/рабочий процесс/правила именования + стандарты интерактивных компонентов (кнопки/клавиатура/события обратного вызова) и сопоставление с платформами

Обзор стандарта

ErisPulse использует OneBot12 в качестве основного стандарта событий и расширяет его с помощью дополнительных расширений и уточнений.

Основные принципы

  1. Совместимость: Все стандарты должны быть совместимы со стандартом OneBot12.
  2. Расширяемость: Платформенные функции расширяются с помощью префиксов, чтобы избежать конфликтов.
  3. Согласованность: Ключевые поля, такие как временные метки и форматы идентификаторов, должны обрабатываться единообразно.
  4. Отслеживаемость: Сохраняются исходные данные для отладки и устранения проблем.

Почему нужен стандарт?

1. Обеспечение совместимости между платформами

Форматы событий на разных платформах различаются. Стандартизированный перевод обеспечивает:

  • Код модуля нужно писать только один раз, чтобы он работал на всех платформах
  • Логика обработки событий остается одинаковой
  • Снижение затрат на разработку и обслуживание

2. Стандартизация интерфейсов API

Единый формат ответа API обеспечивает:

  • Модуль может последовательно обрабатывать ошибки API
  • Информация об ошибках единообразна и легко понимаема
  • Структура возвращаемых данных одинакова

3. Повышение качества кода

Стандартные правила помогают:

  • Поддерживать единообразный стиль кода
  • Сокращать конфликты имен
  • Повышать читаемость кода

Преимущества соблюдения стандартов

Для разработчиков адаптеров

  • Четкие правила преобразования
  • Единый формат ответа
  • Легкость отладки и тестирования

Для разработчиков модулей

  • Единый интерфейс событий
  • Предсказуемое поведение API
  • Упрощение разработки для разных платформ

Для конечных пользователей

  • Стабильное поведение системы
  • Единый формат сообщений
  • Хорошая совместимость

Чек-лист соответствия стандарту

Преобразование событий

  • Все стандартные поля корректно сопоставлены
  • К специфичным для платформы полям добавлен префикс
  • Метки времени преобразованы в 10-значный секундный формат
  • Исходные данные сохранены в {platform}_raw
  • Исходный тип события сохранён в {platform}_raw_type
  • Для сегментов сообщений сгенерировано поле alt_message
  • События запросов содержат поле request_id

Ответы API

  • Содержит поле status
  • Содержит поле retcode
  • Содержит поле data
  • Содержит поле message_id
  • Содержит поле message
  • Коды возврата соответствуют спецификации OneBot12

Именование методов отправки

  • Используется «большая верблюжья» нотация (PascalCase)
  • Возвращается объект Task
  • Методы-модификаторы возвращают self
  • Именование параметров соответствует спецификации

Отправка медиа (Image / Voice / Video / File)

  • Для параметра file обязательна полная поддержка всех форм: HTTP(S) URL / локальный путь / bytes
  • Для параметра file следует по возможности поддерживать формы: URI file:// / Base64 / Data URI (при невозможности поддержки возвращается retcode=10002 согласно лестнице деградации)
  • Порядок определения формы соответствует спецификации (bytes → URL → file:// → путь)
  • Имя файла для File генерируется в порядке вывода (явное filename > basename URL > basename пути > значение платформы по умолчанию)
  • Ограничения платформы для медиа задокументированы в документации адаптера
  • Неподдерживаемые типы медиа обрабатываются согласно лестнице деградации (деградация до близкородственного типа или retcode=10002, без выбрасывания исключений и без тихого отбрасывания)

Подробное описание протокола см. в Спецификации методов отправки §2.1

Операции с запросами

  • В классе HandleRequest реализованы методы _do_accept / _do_reject
  • Операции возвращают ответ в стандартном формате API
  • Неподдерживаемые операции возвращают retcode=10002
