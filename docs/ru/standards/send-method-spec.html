Спецификация методов отправки ErisPulse

Документ определяет стандарты именования методов, параметров и требования к обратному преобразованию в адаптере Send класса ErisPulse.

0. Определение ключевых терминов

В данном документе термины должно (MUST), следует (SHOULD), может (MAY) трактуются следующим образом (согласно RFC 2119):

Термин Смысл Последствия нарушения
должно Обязательное требование, зависимость от поведения фреймворка/кроссплатформенной совместимости Адаптер считается несоответствующим стандарту, код модуля может не работать
следует Сильно рекомендуется; если нет веских причин, следует следовать При отклонении необходимо в документации адаптера объяснить причину и альтернативное поведение
может Опциональный выбор, определяется возможностями платформы Нет

1. Стандартное именование методов

Все методы отправки используют PascalCase (с заглавной буквы).

1.1 Стандартные методы отправки

Название метода Описание Тип параметра Требования реализации
Text Отправка текстового сообщения str Обязательно
Image Отправка изображения str | bytes Обязательно (уже реализовано в базовом классе, см. §6.4)
Voice Отправка аудио str | bytes Обязательно (уже реализовано в базовом классе; если платформа не поддерживает аудио, смотри §2.1.5)
Video Отправка видео str | bytes Обязательно (уже реализовано в базовом классе; если платформа не поддерживает видео, смотри §2.1.5)
File Отправка файла str | bytes, filename: str | None = None Обязательно (уже реализовано в базовом классе)
At @пользователя/группы str (user_id) Модифицирующий метод, по необходимости
Face Отправка эмодзи str (emoji) Может
Reply Ответ на сообщение str (message_id) Модифицирующий метод, по необходимости
Forward Пересылка сообщения str (message_id) Может
Markdown Отправка Markdown-сообщения str Может
HTML Отправка HTML-сообщения str Может
Card Отправка карты dict Может

Стандартные методы (Text/Image/Voice/Video/File) встроены в базовый класс SendDSL и по умолчанию делегируют Raw_ob12, адаптеру не нужно повторно реализовывать для получения сигнатуры типов; только когда платформа требует специальной логики, метод может быть переопределен (см. §6.4).

1.2 Методы цепочки-модификаторы

Название метода Описание Тип параметра
At @пользователя (многократное использование) str (user_id)
AtAll @всех участников Без параметров
Reply Ответ на сообщение str (message_id)

1.3 Методы протокола

Название метода Описание Обязательно
Raw_ob12 Отправка OneBot12-сообщений Обязательно

Raw_ob12 является обязательным методом. Это одна из основных обязанностей адаптера: получение OneBot12-сообщений и их преобразование в вызовы API платформы. Raw_ob12 является единым входом для обратного преобразования (OneBot12 → платформа), обеспечивая возможность модулям не зависеть от специфических методов платформы и отправлять сообщения непосредственно в формате OneBot12.

Поведение при отсутствии переопределения Raw_ob12: Базовый класс по умолчанию записывает ошибку и возвращает стандартный формат ответа с ошибкой (status: "failed", retcode: 10002), указывая, что разработчику адаптера необходимо реализовать этот метод.

1.4 Рекомендуемое расширение именования

Если адаптеру нужно поддерживать отправку не OneBot12-форматированных данных (например, JSON, XML), рекомендуется использовать следующие имена:

Рекомендуемое имя Описание
Raw_json Отправка произвольных JSON-данных
Raw_xml Отправка произвольных XML-данных

Важно: Эти методы не предоставляются базовым классом и не требуют обязательной реализации. Они служат только рекомендациями по именованию, адаптер может определять их по необходимости. Если адаптер не поддерживает эти форматы, то определять их не нужно.

Конструктор сообщений (MessageBuilder): ErisPulse предоставляет класс MessageBuilder для удобного построения OneBot12-сообщений, совместно с Raw_ob12. Подробнее см. раздел Конструктор сообщений (MessageBuilder).

2. Детальное описание стандартов параметров

2.1 Протокол отправки медиафайлов (Image / Voice / Video / File)

Этот раздел определяет единый стандарт протокола для отправки медиафайлов: модули вызывают один и тот же код для четырех методов, а адаптер отвечает за преобразование различных форматов file в вызовы API платформы.

2.1.1 Допустимые формы параметра file

Форма Пример Требования адаптера
HTTP(S) URL https://example.com/image.jpg Должен принимать
Локальный путь /path/to/file.jpg、C:\path\to\file.jpg Должен принимать
Бинарные данные b"\x89PNG..." Должен принимать
URI file:// file:///path/to/file.jpg Следует принимать (можно перенаправить как локальный путь)
Base64 строка / Data URI iVBORw0KGgo=...、data:image/png;base64,... Следует принимать (совместимость с OneBot12)

Адаптер должен обеспечивать одинаковое поведение при трех обязательных формах — модуль может передать URL, путь или bytes, и получит одно и то же сообщение. Если платформа не может напрямую использовать определенную форму (например, API не поддерживает внешние URL), адаптер должен загрузить/прочитать и загрузить файл, не требуя от модуля пересылки в другой форме.

2.1.2 Порядок определения формы

Адаптер должен при реализации обработки параметра file следовать следующему порядку определения формы:

  1. Тип bytes → непосредственная загрузка
  2. Строка начинается с http:// / https:// → обработка как URL (прямая ссылка или загрузка и последующая загрузка, в зависимости от возможностей платформы)
  3. Строка начинается с file:// → удаляется префикс и обрабатывается как локальный путь
  4. Остальные строки → обрабатываются как локальный путь (если существует, читается и загружается; если нет, возвращается стандартный формат ответа с ошибкой)
def _resolve_media(self, file: "str | bytes") -> bytes:
    """Определение и нормализация формы (пример)"""
    if isinstance(file, (bytes, bytearray)):
        return bytes(file)
    if file.startswith(("http://", "https://")):
        return self._download(file)          # Загрузка, если платформа не поддерживает URL
    if file.startswith("file://"):
        file = file[len("file://"):]
    with open(file, "rb") as f:              # Локальный путь
        return f.read()

2.1.3 Семантика имени файла в File

Метод File имеет сигнатуру: File(file, filename=None) (filename — необязательный параметр, уже реализован в базовом классе).

Порядок вывода имени файла (если явно не указан filename):

  1. Явный параметр filename (наивысший приоритет)
  2. basename из URL (например, https://host/a/b/report.pdf → report.pdf, нужно удалить query string)
  3. basename из локального пути (например, /tmp/data/backup.zip → backup.zip)
  4. Имя, сгенерированное платформой (например, file_{timestamp}; следует сохранять расширение — расширение влияет на тип и предпросмотр на стороне платформы)

Image / Voice / Video также могут принимать filename (передается через сообщение data.filename), но только File гарантирует кроссплатформенную семантику имени файла.

2.1.4 Обязанность декларации ограничений платформы

Разные платформы имеют ограничения на размер, формат (MIME), длительность (аудио/видео) и т.д. Адаптер следует:

  • Декларировать в документации поддерживаемые типы медиа и ограничения
  • Возвращать стандартный формат ответа с ошибкой (status: "failed"; retcode использует 10002 или семантический код ошибки платформы, message объясняет причину), если данные превышают ограничения или не поддерживаются, не выбрасывая исключений, которые прерывают логику модуля

2.1.5 Ступенчатое снижение возможностей

Если платформа не поддерживает определенный тип медиа, следует следующая ступенчатая схема снижения (в соответствии с принципом "снижение возможностей не вызывает ошибок"):

Сценарий Поведение снижения
Voice не поддерживает аудиосообщения Следует отправлять как File (или близкую к платформе форму); если невозможно, возвращается retcode=10002
Video не поддерживает видеосообщения То же
Медиа-тип полностью не поддерживается (нет возможности отправки файлов) Возвращается retcode=10002, message указывает, что тип данных не поддерживается
Форма не поддерживается (например, не может обрабатывать base64) Возвращается retcode=10002, можно в message указать, что модуль должен использовать URL/bytes

Запрещенные действия: Тихое игнорирование (без возврата), выброс исключений, требование от модуля написания платформо-специфичной логики.

2.2 Стандарт параметров @пользователя

Метод: At (модифицирующий метод)

Параметр: user_id (str)

Требования:

  • user_id должен быть строковым идентификатором пользователя
  • Формат user_id может отличаться на разных платформах (числа, UUID, строки и т.д.)
  • Адаптер отвечает за преобразование user_id в платформо-специфический формат
  • Обращение к основному методу отправки должно быть последним

Пример:

# Один @пользователь
Send.To("group", "g123").At("123456").Text("Привет")

# Несколько @пользователей (цепочка вызовов)
send.To("group", "g123").At("123456").At("789012").Text("Всем привет")

2.3 Стандарт параметров ответа на сообщение

Метод: Reply (модифицирующий метод)

Параметр: message_id (str)

Требования:

  • message_id должен быть строковым идентификатором сообщения
  • Должен быть идентификатором ранее полученного сообщения
  • На некоторых платформах может не поддерживаться функция ответа, адаптер должен грациозно снижать возможности

Пример:

send.To("group", "g123").Reply("msg_123456").Text("Получено")

2.4 Возможности объединённой пересылки (MergeForward, необязательно)

MergeForward(nodes) — необязательный метод, объединяющий несколько элементов в "объединённую пересылку / раскладной формат", который адаптер должен реализовать по возможности платформы. В отличие от Forward(from_chat_id, message_id) (пересылка уже существующего сообщения), оба метода могут существовать.

Контекст: Основной стандарт OneBot12 не содержит сообщений-узлов и API для объединённой пересылки — "сообщения-узлы" — это концепция OneBot v11 (расширение go-cqhttp), реализованная на уровне сообщений, v12 передаёт эти платформо-специфические возможности в расширения. Реализация ErisPulse — расширение-эквивалент: не добавляются новые стандартные сообщения, а реализуются необязательные методы + list_sends для проверки возможностей на выполнении — адаптеры, реализующие MergeForward, автоматически получают возможность, не реализующие — вызывающая сторона автоматически возвращается к обычному тексту, без изменений модуля.

Сигнатура метода:

def MergeForward(self, nodes: List[Dict]) -> asyncio.Task:
    """
    Отправка объединённой пересылки / раскладного сообщения

    :param nodes: Массив узлов пересылки (формат узла go-cqhttp OneBot v11):
        [
            {
                "type": "node",
                "data": {
                    "user_id": "10000",     # ID отправителя для отображения
                    "nickname": "QvQChat",  # Отображаемое имя отправителя
                    "content": [            # Массив сообщений, текущий текст
                        {"type": "text", "data": {"text": "【1/3】Заголовок\nТекст…"}}
                    ],
                },
            },
        ]
    :return: asyncio.Task, await возвращает стандартный формат ответа
    """

Требования реализации:

  1. Если платформа имеет встроенную пересылку (OneBot11-системы): Должен вызывать специальный протокольный конечный пункт (send_group_forward_msg / send_private_forward_msg) — реализации, такие как NapCat, отвергают send_msg с сегментами node (retcode 1400); при сбое специального конечного пункта можно вернуться к send_msg и отправить сегменты node напрямую
  2. Если платформа не имеет встроенной пересылки, но есть раскладные сообщения (Yunhu / Telegram / Kook / Discord / Matrix и т.д.): Следует отображать узлы в раскладной форму платформы (HTML-карточка / Card / Embed / список blockquote), примеры стилей и задачи по адаптерам см. в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md
  3. Если оба отсутствуют: Не следует реализовывать этот метод (и не возвращать успех, отправляя словарь node как обычный текст) — если не реализован, list_sends не содержит MergeForward, вызывающая сторона автоматически возвращается к обычному тексту
  4. Семантика сбоя: Возвращается стандартный формат ответа с ошибкой (status: "failed") или выбрасывается исключение, вызывающая сторона вернется к отправке обычного текста, содержимое не будет потеряно
  5. Не следует внутри MergeForward вызывать Raw_ob12 для отправки тех же nodes (OneBot11-Raw_ob12 уже встроен с автоматической маршрутизацией сегментов node, это приведёт к циклу)

Пример проверки вызывающей стороной:

sends = adapter.list_sends(platform)
if "MergeForward" in sends:
    await adapter.Send.To("group", "123").MergedForward(nodes)
else:
    await adapter.Send.To("group", "123").Text(plain_text)

Пример реализации: ErisPulse-OneBot11Adapter (специальный конечный пункт → send_msg возврат); шаблоны рендеринга и задачи по адаптерам см. в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md.

3. Именование платформо-специфических методов

Не рекомендуется добавлять методы с платформо-префиксами в класс Send. Рекомендуется использовать общие имена методов или методы Raw_{протокол}.

Не рекомендуется:

def YunhuForm(self, form_id: str):  # ❌ Не рекомендуется
    pass

def TelegramSticker(self, sticker_id: str):  # ❌ Не рекомендуется
    pass

Рекомендуется:

def Form(self, form_id: str):  # ✅ Общее имя метода
    pass

def Sticker(self, sticker_id: str):  # ✅ Общее имя метода
    pass

def Raw_ob12(self, message):  # ✅ Отправка OneBot12-формата
    pass

Требования к расширению методов:

  • Имена методов должны использовать PascalCase, без платформо-префиксов
  • Метод должен возвращать объект asyncio.Task
  • Метод должен иметь полную аннотацию типов и строку документации
  • Дизайн параметров должен максимально соответствовать стилю стандартных методов

4. Стандарт именования параметров

Имя параметра Описание Тип
text Текстовое содержимое str
file Медиа-содержимое (URL / путь / бинарные данные, см. §2.1.1) str / bytes
filename Имя файла (File необязательный, см. §2.1.3) str / None
user_id ID пользователя str / int
group_id ID группы str / int
message_id ID сообщения str
data Объект данных (например, данные карточки) dict

5. Стандарт возвращаемых значений

  • Методы отправки (например, Text, Image) должны возвращать объект asyncio.Task
  • Модифицирующие методы (например, At, Reply, AtAll) должны возвращать self для поддержки цепочки вызовов

6. Стандарт обратного преобразования (OneBot12 → платформа)

Адаптер должен не только преобразовывать события платформы в формат OneBot12 (прямое преобразование), но и обязан обеспечить возможность обратного преобразования OneBot12-сегментов сообщений в вызовы API платформы (обратное преобразование). Единым входом для обратного преобразования является метод Raw_ob12.

6.1 Модель преобразования

Прямое преобразование (входящие события)               Обратное преобразование (отправляющие события)
─────────────────                ─────────────────
События платформы                   Сегменты OneBot12-сообщений
    │                                  │
    ▼                                  ▼
Converter.convert()               Send.Raw_ob12()
    │                                  │
    ▼                                  ▼
OneBot12-стандартные события         Вызовы API платформы
(содержит {platform}_raw)           (возвращает стандартный формат ответа)

Основная симметрия: Прямое преобразование сохраняет исходные данные в {platform}_raw, обратное преобразование принимает стандартный формат OneBot12 и восстанавливает вызовы платформы.

6.2 Стандарт реализации Raw_ob12

Метод Raw_ob12 принимает стандартный список сегментов OneBot12 и должен преобразовать их в вызовы API платформы.

Сигнатура метода:

def Raw_ob12(self, message_segments: List[Dict]) -> asyncio.Task:
    """
    Отправка OneBot12-стандартных сегментов сообщений

    :param message_segments: Список OneBot12-сегментов сообщений
        [
            {"type": "text", "data": {"text": "Привет"}},
            {"type": "image", "data": {"file": "https://..."}},
            {"type": "mention", "data": {"user_id": "123"}},
        ]
    :return: asyncio.Task, await возвращает стандартный формат ответа
    """

Требования реализации:

  1. Должны обрабатываться все стандартные типы сегментов: По крайней мере, поддержка text, image, audio, video, file, mention, reply
  2. Должны обрабатываться платформо-расширения: Для сегментов с префиксом {platform}_xxx преобразовывать в соответствующие вызовы платформы
  3. Должен возвращаться стандартный формат ответа: Следовать стандарту API-ответа
  4. Неподдерживаемые сегменты должны пропускаться и записываться в журнал предупреждений, не должны вызывать исключения, приводящие к сбою отправки всей сообщения

6.3 Правила преобразования сегментов

6.3.1 Преобразование стандартных сегментов

Адаптер должен реализовать преобразование следующих стандартных сегментов:

OneBot12-сегмент Требования преобразования
text Использовать data.text напрямую
image data.file обрабатывается по протоколу медиа (три обязательные формы + порядок определения)
audio Аналогично обработке image
video Аналогично обработке image
file Аналогично обработке image; имя файла обрабатывается по правилу вывода data.filename
mention Преобразовать в механизм @пользователя платформы (например, entities в Telegram, at_uid в Yunhu)
reply Преобразовать в механизм отсылки сообщения платформы
face Преобразовать в механизм отправки эмодзи платформы, если не поддерживается, пропустить
location Преобразовать в механизм отправки локации платформы, если не поддерживается, пропустить

6.3.2 Преобразование платформо-расширений

Для сегментов с платформо-префиксом адаптер должен распознавать и преобразовывать:

def _convert_ob12_segments(self, segments: List[Dict]) -> Any:
    """Преобразование OneBot12-сегментов в платформо-специфический формат"""
    platform_prefix = f"{self._platform_name}_"
    
    for segment in segments:
        seg_type = segment["type"]
        seg_data = segment["data"]
        
        if seg_type.startswith(platform_prefix):
            # Платформо-расширение → платформо-специфический вызов
            self._handle_platform_segment(seg_type, seg_data)
        elif seg_type in self._standard_segment_handlers:
            # Стандартный сегмент → эквивалентная операция платформы
            self._standard_segment_handlers[seg_type](seg_data)
        else:
            # Неизвестный сегмент → запись предупреждения и пропуск
            logger.warning(f"Не поддерживаемый тип сегмента: {seg_type}")

6.3.3 Обработка составных сегментов

Сообщение может содержать несколько сегментов, адаптер должен корректно обрабатывать составные сообщения:

# Модуль отправляет сообщение с текстом+изображением+@пользователем
await send.Raw_ob12([
    {"type": "mention", "data": {"user_id": "123"}},
    {"type": "text", "data": {"text": "Привет"}},
    {"type": "image", "data": {"file": "https://example.com/img.jpg"}}
])

Стратегия обработки:

  • Предпочтительное объединение: Если платформа поддерживает объединение текста, изображения и @ в одном сообщении, следует объединить и отправить
  • Альтернативное разделение: Если платформа не поддерживает объединение, отправить по отдельности
  • Сохранение порядка: Порядок отправки сегментов должен соответствовать порядку в списке

6.4 Raw_ob12 и стандартные методы

Стандартные методы отправки (Text、Image и т.д.) уже реализованы в базовом классе SendDSL и по умолчанию делегируют Raw_ob12, адаптеру подклассу не нужно повторно реализовывать:

class Send(SendDSL):
    def Raw_ob12(self, message_segments: List[Dict]) -> asyncio.Task:
        """Основная реализация: OneBot12-сегменты → вызов API платформы (обязательно реализовать)"""
        return asyncio.create_task(self._send_ob12(message_segments))

    # Text/Image/Voice/Video/File уже унаследованы из базового класса, автоматически делегируют Raw_ob12
    # Если нужна платформо-специфическая логика, можно переопределить отдельный метод:
    # def Text(self, text: str) -> asyncio.Task:
    #     return self.Raw_ob12([{"type": "text", "data": {"text": text}}])

Преимущества:

  • Логика преобразования сосредоточена в Raw_ob12, минимизируя дублирование кода
  • Стандартные методы и Raw_ob12 ведут себя одинаково
  • Модуль получает одинаковый результат, независимо от использования Text() или Raw_ob12()
  • Базовый класс предоставляет сигнатуры типов, IDE дополняет стандартные методы

6.5 Пример реализации

class YunhuSend(SendDSL):
    """Реализация Send для платформы Yunhu"""
    
    def Raw_ob12(self, message_segments: list) -> asyncio.Task:
        """OneBot12-сегменты → вызов API Yunhu"""
        return asyncio.create_task(self._do_send(message_segments))
    
    async def _do_send(self, segments: list) -> dict:
        """Реальная логика отправки"""
        # 1. Анализ состояния модификаторов
        at_users = self._at_users or []
        reply_to = self._reply_to
        at_all = self._at_all
        
        # 2. Преобразование сегментов
        yunhu_elements = []
        for seg in segments:
            seg_type = seg["type"]
            seg_data = seg["data"]
            
            if seg_type == "text":
                yunhu_elements.append({"type": "text", "content": seg_data["text"]})
            elif seg_type == "image":
                yunhu_elements.append({"type": "image", "url": seg_data["file"]})
            elif seg_type == "mention":
                at_users.append(seg_data["user_id"])
            elif seg_type == "reply":
                reply_to = seg_data["message_id"]
            elif seg_type == "yunhu_form":
                # Платформо-расширение
                yunhu_elements.append({"type": "form", "form_id": seg_data["form_id"]})
            else:
                logger.warning(f"Yunhu не поддерживает сегмент: {seg_type}")
        
        # 3. Вызов API Yunhu
        response = await self._call_yunhu_api(yunhu_elements, at_users, reply_to, at_all)
        
        # 4. Возврат стандартного формата ответа
        return {
            "status": "ok" if response["code"] == 0 else "failed",
            "retcode": response["code"],
            "data": {"message_id": response.get("msg_id", ""), "time": int(time.time())},
            "message_id": response.get("msg_id", ""),
            "message": "",
            "yunhu_raw": response
        }

10. Проверочный список реализации адаптера

Методы отправки

  • Стандартные методы (Text, Image и т.д.) реализованы
  • Возвращаемые значения — asyncio.Task
  • Модифицирующие методы (At, Reply, AtAll) возвращают self
  • Платформо-расширения используют PascalCase, без платформо-префиксов
  • Все методы имеют полную аннотацию типов и строку документации

Протокол отправки медиа

  • file параметр обязательно поддерживает все формы: HTTP(S) URL / локальный путь / bytes (см. §2.1.1)
  • Порядок определения формы соответствует §2.1.2 (bytes → URL → file:// → путь)
  • Порядок вывода имени файла для File соответствует §2.1.3 (явный filename > basename URL > basename пути > платформо-генерируемое)
  • Ограничения платформы (размер / MIME / длительность) декларированы в документации адаптера (§2.1.4)
  • Неподдерживаемые типы медиа обрабатываются по схеме снижения возможностей §2.1.5: близкие типы снижаются или возвращается retcode=10002, не выбрасываются исключения, не игнорируются тихо

Объединённая пересылка (необязательно, см. §2.4)

  • Если платформа имеет встроенную пересылку, MergeForward использует специальный протокольный конечный пункт, при сбое возвращается send_msg (OneBot11-системы)
  • Если платформа не имеет пересылки, но есть раскладные сообщения, MergeForward отображается в раскладной форму платформы (HTML-карточка / Card / Embed / список blockquote), см. SDK/Adapter/ADAPTER_FORWARD_GUIDE.md
  • Если оба отсутствуют, MergeForward не реализован, не возвращается успех, если отправляется словарь node как текст
  • Внутри MergeForward не вызывается Raw_ob12 для отправки тех же nodes

Обратное преобразование

  • Raw_ob12 реализован (обязательно, нельзя пропускать)
  • Raw_ob12 обрабатывает все стандартные сегменты (text, image, audio, video, file, mention, reply)
  • Raw_ob12 обрабатывает платформо-расширения ({platform}_xxx типы)
  • Стандартные методы (Text, Image и т.д.) делегируют Raw_ob12, а не реализуют логику преобразования самостоятельно
  • Неподдерживаемые сегменты пропускаются и записываются в журнал предупреждений, не выбрасываются исключения
  • Составные сегменты обрабатываются корректно (объединение или последовательная отправка)

11. Конструктор сообщений (MessageBuilder)

MessageBuilder — инструмент для построения OneBot12-сегментов, предоставляемый ErisPulse, используется совместно с Raw_ob12, упрощая построение OneBot12-сообщений.

11.1 Импорт

from ErisPulse.Core import MessageBuilder
# или
from ErisPulse.Core.Event import MessageBuilder

11.2 Цепочечное построение

# Построение сообщения с текстом, изображением, @пользователем
segments = (
    MessageBuilder()
    .mention("123456")
    .text("Привет, посмотри на эту картинку")
    .image("https://example.com/img.jpg")
    .reply("msg_789")
    .build()
)

# Отправка
await adapter.Send.To("group", "456").Raw_ob12(segments)

11.3 Быстрое построение одного сегмента

# Быстрое построение одного сегмента (возвращает list[dict], можно передать в Raw_ob12)
await adapter.Send.To("user", "123").Raw_ob12(MessageBuilder.text("Привет"))

from ErisPulse.Core import MessageBuilder
