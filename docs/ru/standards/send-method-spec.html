Спецификация методов отправки ErisPulse

Tip

Когда стоит читать этот документ: когда вы реализуете класс Send в адаптере — именование методов, поддержку форматов медиапараметров (URL/путь/bytes), обратное преобразование Raw_ob12, возможности объединённой пересылки — сверяйтесь с этим документом. Если это не нужно — пропустите.

Данный документ определяет соглашения об именовании, спецификации параметров и требования к обратному преобразованию для методов отправки класса Send в адаптерах ErisPulse.

0. Соглашения о ключевых словах

Ключевые слова Обязательно (MUST), Рекомендуется (SHOULD), Можно (MAY) в этом документе интерпретируются в следующей семантике (со ссылкой на RFC 2119):

Ключевое слово Семантика Последствия нарушения
Обязательно (MUST) Императивное требование; от него зависят поведение фреймворка и кроссплатформенная согласованность Адаптер считается несоответствующим стандарту, код модулей может не работать
Рекомендуется (SHOULD) Настоятельная рекомендация; следовать, если нет веских причин поступить иначе При отклонении необходимо указать в документации адаптера причину и альтернативное поведение
Можно (MAY) Необязательный пункт; решается самостоятельно в зависимости от возможностей платформы Отсутствуют

1. Стандартное именование методов

Все методы отправки используют PascalCase (стиль ВерхнегоВерблюжьегоРегистра), первая буква заглавная.

1.1 Стандартные методы отправки

Имя метода Описание Тип параметра Требование к реализации
Text Отправка текстового сообщения str Обязательно
Image Отправка изображения str | bytes Обязательно (встроено в базовый класс, см. §6.4)
Voice Отправка голосового сообщения str | bytes Обязательно (встроено в базовый класс; при отсутствии поддержки голоса платформой — деградация согласно §2.1.5)
Video Отправка видео str | bytes Обязательно (встроено в базовый класс; при отсутствии поддержки видео платформой — деградация согласно §2.1.5)
File Отправка файла str | bytes, filename: str | None = None Обязательно (встроено в базовый класс)
At Упоминание пользователя/группы str (user_id) Модифицирующий метод, по необходимости
Face Отправка эмодзи str (emoji) Необязательно
Reply Ответ на сообщение str (message_id) Модифицирующий метод, по необходимости
Forward Пересылка сообщения str (message_id) Необязательно
Markdown Отправка сообщения Markdown str Необязательно
HTML Отправка сообщения HTML str Необязательно
Card Отправка карточного сообщения dict Необязательно

Стандартные методы (Text/Image/Voice/Video/File) встроены в базовый класс SendDSL и по умолчанию делегируют Raw_ob12; адаптер получает сигнатуры типов без повторной реализации. Переопределять отдельные методы следует только тогда, когда платформе требуется особая логика (см. §6.4).

1.2 Модифицирующие методы для цепочек

Имя метода Описание Тип параметра
At Упоминание пользователя (можно вызывать несколько раз) str (user_id)
AtAll Упоминание всех участников Нет
Reply Ответ на сообщение str (message_id)

1.3 Методы протокола

Имя метода Описание Обязателен ли
Raw_ob12 Отправка сегментов сообщений в формате OneBot12 Обязательно

Raw_ob12 — метод, реализация которого обязательна. Это одна из ключевых обязанностей адаптера: принимать стандартные сегменты сообщений OneBot12 и преобразовывать их в вызовы нативного API платформы. Raw_ob12 — единая точка входа обратного преобразования (OneBot12 → платформа), гарантирующая, что модули могут отправлять сообщения стандартными сегментами, не завися от платформенно-специфичных методов.

Поведение при отсутствии переопределения Raw_ob12: реализация по умолчанию в базовом классе записывает лог уровня error и возвращает стандартный формат ответа об ошибке (status: "failed", retcode: 10002), напоминая разработчику адаптера о необходимости реализовать этот метод.

1.4 Рекомендуемые соглашения об именовании расширений

Если адаптеру требуется поддержка отправки сырых данных в формате, отличном от OneBot12 (например, специфичный для платформы JSON, XML и т.д.), рекомендуется использовать следующие соглашения об именовании:

Рекомендуемое имя метода Описание
Raw_json Отправка произвольных данных JSON
Raw_xml Отправка произвольных данных XML

Примечание: эти методы не являются предоставляемыми базовым классом методами по умолчанию, и их реализация не обязательна. Они служат лишь соглашением об именовании; адаптер может определять их самостоятельно по необходимости. Если адаптер не поддерживает эти форматы, определять их не нужно.

MessageBuilder (конструктор сообщений): ErisPulse предоставляет утилитарный класс MessageBuilder для удобного построения списков сегментов сообщений OneBot12, используемых совместно с Raw_ob12. Подробнее см. Подробно о MessageBuilder.

2. Подробная спецификация параметров

2.1 Протокол отправки медиасообщений (Image / Voice / Video / File)

Этот раздел — единый стандарт протокола отправки медиа: модуль вызывает четыре медиаметода одним и тем же кодом, а адаптер отвечает за преобразование различных форм параметра file в нативное для платформы поведение загрузки/отправки.

2.1.1 Допустимые формы параметра file

Форма Пример Требования к адаптеру
HTTP(S) URL https://example.com/image.jpg Обязательно принимать
Локальный путь к файлу /path/to/file.jpg, C:\path\to\file.jpg Обязательно принимать
Бинарные данные b"\x89PNG..." Обязательно принимать
URI file:// file:///path/to/file.jpg Рекомендуется принимать (можно преобразовать в локальный путь для обработки)
Строка Base64 / Data URI iVBORw0KGgo=..., data:image/png;base64,... Рекомендуется принимать (совместимо с практиками экосистемы OneBot12)

Адаптер обязан вести себя единообразно на трёх обязательных формах — независимо от того, передаёт модуль URL, путь или bytes, полученное сообщение будет одним и тем же. Если платформа не может напрямую использовать какую-то форму (например, API платформы не поддерживает ссылки на внешние URL), адаптер самостоятельно скачивает/читает и загружает данные; недопустимо требовать от модуля повторить попытку с другой формой.

2.1.2 Порядок определения формы

При реализации обработки медиапараметров адаптер должен определять форму в следующем порядке:

  1. Тип bytes → прямая загрузка
  2. Строка начинается с http:// / https:// → обрабатывать как URL (прямая ссылка или скачивание с последующей загрузкой — по возможностям платформы)
  3. Строка начинается с file:// → отрезать префикс и обрабатывать как локальный путь
  4. Остальные строки → обрабатывать как локальный путь (если существует — прочитать и загрузить; если нет — вернуть стандартный ответ об ошибке)
def _resolve_media(self, file: "str | bytes") -> bytes:
    """Определение формы и нормализация (пример)"""
    if isinstance(file, (bytes, bytearray)):
        return bytes(file)
    if file.startswith(("http://", "https://")):
        return self._download(file)          # скачивать, когда платформа не может ссылаться на URL
    if file.startswith("file://"):
        file = file[len("file://"):]
    with open(file, "rb") as f:              # локальный путь
        return f.read()

2.1.3 Семантика имени файла для File

Сигнатура метода File: File(file, filename=None) (filename — необязательный параметр, встроен в базовый класс).

Порядок определения имени файла (адаптер генерирует его по этой схеме, когда filename не предоставлен явно):

  1. Явный параметр filename (наивысший приоритет)
  2. basename из URL (например, https://host/a/b/report.pdf → report.pdf; необходимо отрезать query string)
  3. basename из локального пути (например, /tmp/data/backup.zip → backup.zip)
  4. Генерация по умолчанию платформы (например, file_{timestamp}; следует сохранять реальное расширение — расширение влияет на распознавание типа и поведение предпросмотра на стороне платформы)

Image / Voice / Video также могут принимать filename (передаётся через data.filename сегмента сообщения), но кроссплатформенная семантика имени файла гарантируется только для File.

2.1.4 Обязанность декларирования ограничений платформы

Ограничения платформ на максимальный размер медиа, форматы (MIME), длительность (аудио/видео) и т.д. различаются. Адаптер должен:

  • декларировать в документации адаптера поддерживаемые типы медиа и диапазоны ограничений;
  • при превышении лимитов или неподдерживаемом вводе возвращать стандартный ответ об ошибке (status: "failed"; retcode — 10002 или семантический код ошибки платформы, message поясняет причину); недопустимо выбрасывать исключения, прерывая логику модуля.

2.1.5 Лестница деградации возможностей

Когда платформа не поддерживает какой-либо тип медиа, деградация выполняется по следующей лестнице (согласно общему принципу «деградация возможностей без ошибок»):

Сценарий Поведение при деградации
Voice не поддерживает голосовые сообщения Следует отправлять как File (или ближайшую платформенную форму); при невозможности выразить — вернуть retcode=10002
Video не поддерживает видеосообщения То же
Тип медиа полностью не поддерживается (нет файловых возможностей) Вернуть retcode=10002, в message указать неподдерживаемый тип данных
Форма не поддерживается (например, невозможно обработать base64) Вернуть retcode=10002, можно указать в message подсказку модулю использовать URL/bytes

Запрещённое поведение: молчаливое отбрасывание (без ответа), выбрасывание исключений, требование к модулю писать платформенные ветки обработки.

2.2 Спецификация параметра упоминания пользователя

Метод: At (модифицирующий метод)

Параметр: user_id (str)

Требования:

  • user_id должен быть строковым идентификатором пользователя
  • Формат user_id может отличаться на разных платформах (число, UUID, строка и т.д.)
  • Адаптер отвечает за преобразование user_id в платформенно-специфичный формат
  • Обратите внимание: вызов фактического метода отправки должен находиться на последней позиции

Пример:

# Одиночное упоминание пользователя
Send.To("group", "g123").At("123456").Text("Привет")

# Несколько упоминаний (цепной вызов)
send.To("group", "g123").At("123456").At("789012").Text("Всем привет")

2.3 Спецификация параметра ответа на сообщение

Метод: Reply (модифицирующий метод)

Параметр: message_id (str)

Требования:

  • message_id должен быть строковым идентификатором сообщения
  • Должен быть ID ранее полученного сообщения
  • Некоторые платформы могут не поддерживать функцию ответа; адаптер должен корректно деградировать

Пример:

send.To("group", "g123").Reply("msg_123456").Text("Принято")

2.4 Возможность объединённой пересылки (MergeForward, необязательно)

MergeForward(nodes) — необязательный метод возможности: упаковывает несколько фрагментов содержимого для отправки в форме «объединённой пересылки / свёрнутого форматированного текста»; адаптер определяет оптимальное представление в зависимости от возможностей платформы. Семантика отличается от Forward(from_chat_id, message_id) из §1.1 (пересылка существующего сообщения); оба сосуществуют.

Контекст стандарта: ядро стандарта OneBot12 не содержит сегмента node и API объединённой пересылки — «узлы сообщений» являются концепцией уровня реализации экосистемы OneBot v11 (расширение go-cqhttp); v12 передаёт подобные платформенно-специфические возможности механизму расширений. Реализация в ErisPulse — эквивалент механизма расширений: без добавления новых стандартных сегментов сообщений — через необязательные методы возможностей + обнаружение в рантайме через list_sends — адаптеры с реализованным MergeForward автоматически получают возможность; вызывающая сторона при отсутствии реализации автоматически откатывается к обычному тексту, модули не требуют никаких изменений.

Сигнатура метода:

def MergeForward(self, nodes: List[Dict]) -> asyncio.Task:
    """
    Отправка объединённой пересылки / свёрнутого форматированного текста

    :param nodes: массив узлов объединённой пересылки (формат узлов OneBot v11 из расширения go-cqhttp):
        [
            {
                "type": "node",
                "data": {
                    "user_id": "10000",     # id отправителя для отображения
                    "nickname": "MyBot",     # ник отправителя для отображения
                    "content": [            # массив сегментов сообщения, сейчас сегменты text
                        {"type": "text", "data": {"text": "[1/3] Заголовок\nОсновной текст…"}}
                    ],
                },
            },
        ]
    :return: asyncio.Task, после await возвращает стандартный формат ответа
    """

Требования к реализации:

  1. Платформа имеет нативную объединённую пересылку (семейство OneBot11): обязательно вызывать специализированный эндпоинт протокола (send_group_forward_msg / send_private_forward_msg) — реализации вроде NapCat отклоняют сегменты node, передаваемые через send_msg (retcode 1400); при отказе специализированного эндпоинта можно откатиться к прямой отправке сегментов node через send_msg
  2. Платформа не имеет нативной пересылки, но имеет форматированный текст (Yunhu / Telegram / Kook / Discord / Matrix и др.): следует рендерить узлы в свёрнутую форму форматированного текста платформы (сворачиваемая HTML-карточка / Card / Embed / список blockquote); справочные стили и список задач по каждому адаптеру см. в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md
  3. Нет ни того, ни другого: недопустимо реализовывать этот метод (тем более возвращать успех, отправляя словари node как чистый текст) — без реализации list_sends не содержит MergeForward, и вызывающая сторона автоматически откатывается к обычному тексту
  4. Семантика сбоя: допустимо вернуть стандартный ответ об ошибке (status: "failed") или выбросить исключение; вызывающая сторона откатится к отправке чистого текста, содержимое не теряется
  5. Недопустимо внутри MergeForward снова вызывать Raw_ob12 для отправки тех же nodes (в Raw_ob12 OneBot11 уже встроена автоматическая маршрутизация чистых сегментов node — образуется цикл)
  6. Парсинг исходящих сегментов node (соглашение для всех адаптеров): диспетчеризация сегментов Raw_ob12 каждого адаптера должна регистрировать сегмент node — чистый список node автоматически маршрутизируется в представление объединённой пересылки этого адаптера (на платформах с MergeForward это эквивалентно прямому вызову; на платформах без этого метода извлекается текст каждого узла и выводится построчно как есть в формате «ник: текст»); текст сегментов node в смешанном списке включается в основной текст. Любой адаптер, получивший сегмент node, не должен молча его отбрасывать.

Формы реализации на платформах (подробнее в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md):

  • Нативные эндпоинты: OneBot11, SnowLuma (трёхуровневый откат: специализированный эндпоинт send_group/private_forward_msg → upload_forward_msg с получением resid и отправкой сегмента forward → прямая отправка сегментов node; API SnowLuma полностью выровнено с NapCat, адаптер может подключаться напрямую к бэкенду NapCat)
  • Сворачиваемая HTML-карточка <details>: Yunhu (протоколы bot/пользователя), Email, Sandbox, Allons(Ideaura)
  • HTML по белому списку / цитатные блоки: Telegram (<b>+<blockquote>), Matrix (вариант blockquote, удаление details/инлайн-стилей по белому списку)
  • Платформенные карточки: Kook (Card header+section), Discord (Embed fields)
  • Официальный Markdown-список цитат: QQBot (в официальном md нет синтаксиса сворачивания, серверная валидация отклоняет недопустимые теги с ошибкой 40034011)
  • Не реализуется (деградация к выводу сегментов node как есть): OneBot12 (в стандарте нет сегмента node), WeCom, Terminal, Webhook, WechatMp

Пример обнаружения на стороне вызывающего:

sends = adapter.list_sends(platform)
if "MergeForward" in sends:
    await adapter.Send.To("group", "123").MergeForward(nodes)
else:
    await adapter.Send.To("group", "123").Text(plain_text)

Референсная реализация: ErisPulse-OneBot11Adapter (специализированный эндпоинт → откат к send_msg); шаблоны рендеринга и список задач по каждому адаптеру см. в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md.

3. Именование платформенно-специфичных методов

Не рекомендуется напрямую добавлять методы с платформенным префиксом в класс Send. Рекомендуется использовать универсальные имена методов или методы Raw_{протокол}.

Не рекомендуется:

def YunhuForm(self, form_id: str):  # ❌ Не рекомендуется
    pass

def TelegramSticker(self, sticker_id: str):  # ❌ Не рекомендуется

Рекомендуется:

def Form(self, form_id: str):  # ✅ Универсальное имя метода
    pass

def Sticker(self, sticker_id: str):  # ✅ Универсальное имя метода
    pass

def Raw_ob12(self, message):  # ✅ Отправка в формате OneBot12
    pass

Требования к методам расширений:

  • имя метода в PascalCase, без платформенного префикса;
  • должен возвращать объект asyncio.Task;
  • должны предоставляться полные аннотации типов и строки документации;
  • дизайн параметров должен по возможности соответствовать стилю стандартных методов.

4. Соглашения об именовании параметров

Имя параметра Описание Тип

file Медиа-содержимое (URL / путь / бинарные данные, см. §2.1.1) str / bytes

  • Методы отправки (например, Text, Image): должны возвращать объект asyncio.Task
  • Модифицирующие методы (например, At, Reply, AtAll): должны возвращать self для поддержки цепных вызовов

6. Спецификация обратного преобразования (OneBot12 → платформа)

Адаптер не только должен преобразовывать нативные события платформы в формат OneBot12 (прямое преобразование), но и обязан предоставлять возможность преобразования сегментов сообщений OneBot12 обратно в вызовы нативного API платформы (обратное преобразование). Единая точка входа обратного преобразования — метод Raw_ob12.

6.1 Модель преобразования

Прямое преобразование (направление приёма)       Обратное преобразование (направление отправки)
─────────────────                ─────────────────
Нативное событие платформы                       Список сегментов сообщений OneBot12
    │                                  │
    ▼                                  ▼
Converter.convert()               Send.Raw_ob12()
    │                                  │
    ▼                                  ▼
Стандартное событие OneBot12                     Вызов нативного API платформы
(содержит {platform}_raw)                        (возвращает стандартный формат ответа)

Ключевая симметрия: прямое преобразование сохраняет исходные данные в {platform}_raw, обратное преобразование принимает стандартный формат OneBot12 и восстанавливает его в вызовы платформы.

6.2 Спецификация реализации Raw_ob12

Raw_ob12 принимает список стандартных сегментов сообщений OneBot12 и обязан преобразовывать их в вызовы нативного API платформы.

Сигнатура метода:

def Raw_ob12(self, message_segments: List[Dict]) -> asyncio.Task:
    """
    Отправка стандартных сегментов сообщений OneBot12

    :param message_segments: список сегментов сообщений OneBot12
        [
            {"type": "text", "data": {"text": "Hello"}},
            {"type": "image", "data": {"file": "https://..."}},
            {"type": "mention", "data": {"user_id": "123"}},
        ]
    :return: asyncio.Task, после await возвращает стандартный формат ответа
    """

Требования к реализации:

  1. Должны обрабатываться все стандартные типы сегментов сообщений: как минимум поддержка text, image, audio, video, file, mention, reply
  2. Должны обрабатываться платформенные сегменты расширений: сегменты типа {platform}_xxx преобразовывать в соответствующие нативные вызовы платформы
  3. Должен возвращаться стандартный формат ответа: согласно Стандарту API-ответов
  4. Неподдерживаемые сегменты должны пропускаться с записью предупреждения; не следует выбрасывать исключение, приводящее к сбою отправки всего сообщения

6.3 Правила преобразования сегментов сообщений

6.3.1 Преобразование стандартных сегментов сообщений

Адаптер обязан реализовать преобразование следующих стандартных сегментов сообщений:

Сегмент OneBot12 Требования к преобразованию
text Напрямую использовать data.text
image data.file обрабатывается согласно медиапротоколу §2.1 (три обязательные формы + порядок определения)
audio Та же логика обработки, что и у image
video Та же логика обработки, что и у image
file Та же логика обработки, что и у image; имя файла обрабатывается по порядку определения из §2.1.3 через data.filename
mention Преобразуется в механизм упоминаний платформы (например, entities в Telegram, at_uid в Yunhu)
reply Преобразуется в механизм цитирования/ответа платформы
face Преобразуется в механизм отправки эмодзи платформы; при отсутствии поддержки — пропустить
location Преобразуется в механизм отправки геопозиции платформы; при отсутствии поддержки — пропустить

6.3.2 Преобразование платформенных сегментов расширений

Для сегментов с платформенным префиксом адаптер должен распознавать и преобразовывать их:

def _convert_ob12_segments(self, segments: List[Dict]) -> Any:
    """Преобразование сегментов сообщений OneBot12 в нативный формат платформы"""
    platform_prefix = f"{self._platform_name}_"
    
    for segment in segments:
        seg_type = segment["type"]
        seg_data = segment["data"]
        
        if seg_type.startswith(platform_prefix):
            # Сегмент расширения платформы → нативный вызов платформы
            self._handle_platform_segment(seg_type, seg_data)
        elif seg_type in self._standard_segment_handlers:
            # Стандартный сегмент → эквивалентная операция платформы
            self._standard_segment_handlers[seg_type](seg_data)
        else:
            # Неизвестный сегмент → записать предупреждение и пропустить
            logger.warning(f"Неподдерживаемый тип сегмента сообщения: {seg_type}")

6.3.3 Обработка составных сегментов сообщений

Одно сообщение может содержать несколько сегментов; адаптер должен корректно обрабатывать составные сообщения:

# Модуль отправляет сообщение с текстом + изображением + упоминанием пользователя
await send.Raw_ob12([
    {"type": "mention", "data": {"user_id": "123"}},
    {"type": "text", "data": {"text": "Привет"}},
    {"type": "image", "data": {"file": "https://example.com/img.jpg"}}
])

Стратегия обработки:

  • Приоритет слиянию: если платформа поддерживает текст, изображения, @ и т.д. в одном сообщении, следует отправлять слитно
  • Откат к разделению: если платформа не поддерживает слияние, разделить на несколько сообщений и отправить по порядку
  • Сохранение порядка: порядок отправки сегментов должен соответствовать порядку в списке

6.4 Отношение Raw_ob12 к стандартным методам

Стандартные методы отправки адаптера (Text, Image и т.д.) уже встроены в базовый класс SendDSL и по умолчанию делегируются Raw_ob12; подклассу адаптера не нужно реализовывать их повторно:

class Send(SendDSL):
    def Raw_ob12(self, message_segments: List[Dict]) -> asyncio.Task:
        """Ключевая реализация: сегменты сообщений OneBot12 → API платформы (обязательна)"""
        return asyncio.create_task(self._send_ob12(message_segments))

    # Text/Image/Voice/Video/File унаследованы от базового класса, автоматически делегируют Raw_ob12
    # Если нужна платформенно-специфичная логика, можно переопределить отдельный метод:
    # def Text(self, text: str) -> asyncio.Task:
    #     return self.Raw_ob12([{"type": "text", "data": {"text": text}}])

Преимущества:

  • логика преобразования сосредоточена в одном месте — Raw_ob12, меньше дублирования кода
  • поведение стандартных методов и Raw_ob12 полностью совпадает
  • модуль получает одинаковый результат независимо от того, используется Text() или Raw_ob12()
  • базовый класс предоставляет сигнатуры типов, IDE может дополнять стандартные методы

6.5 Пример реализации

class YunhuSend(SendDSL):
    """Реализация Send для платформы Yunhu"""
    
    def Raw_ob12(self, message_segments: list) -> asyncio.Task:
        """Сегменты сообщений OneBot12 → вызов API Yunhu"""
        return asyncio.create_task(self._do_send(message_segments))
    
    async def _do_send(self, segments: list) -> dict:
        """Фактическая логика отправки"""
        # 1. Разбор состояния модификаторов
        at_users = self._at_users or []
        reply_to = self._reply_to
        at_all = self._at_all
        
        # 2. Преобразование сегментов сообщений
        yunhu_elements = []
        for seg in segments:
            seg_type = seg["type"]
            seg_data = seg["data"]
            
            if seg_type == "text":
                yunhu_elements.append({"type": "text", "content": seg_data["text"]})
            elif seg_type == "image":
                yunhu_elements.append({"type": "image", "url": seg_data["file"]})
            elif seg_type == "mention":
                at_users.append(seg_data["user_id"])
            elif seg_type == "reply":
                reply_to = seg_data["message_id"]
            elif seg_type == "yunhu_form":
                # Сегмент расширения платформы
                yunhu_elements.append({"type": "form", "form_id": seg_data["form_id"]})
            else:
                logger.warning(f"Сегмент сообщения, не поддерживаемый Yunhu: {seg_type}")
        
        # 3. Вызов API Yunhu
        response = await self._call_yunhu_api(yunhu_elements, at_users, reply_to, at_all)
        
        # 4. Возврат стандартного формата ответа
        return {
            "status": "ok" if response["code"] == 0 else "failed",
            "retcode": response["code"],
            "data": {"message_id": response.get("msg_id", ""), "time": int(time.time())},
            "message_id": response.get("msg_id", ""),
            "message": "",
            "yunhu_raw": response
        }

10. Чек-лист реализации адаптера

Методы отправки

  • Стандартные методы (Text, Image и т.д.) реализованы
  • Все возвращаемые значения — asyncio.Task
  • Модифицирующие методы (At, Reply, AtAll) возвращают self
  • Методы расширений платформы используют PascalCase, без платформенного префикса
  • Все методы имеют полные аннотации типов и строки документации

Протокол отправки медиа

  • Все обязательные формы параметра file поддерживаются: HTTP(S) URL / локальный путь / bytes (см. §2.1.1)
  • Порядок определения формы соответствует §2.1.2 (bytes → URL → file:// → путь)
  • Порядок определения имени файла File соответствует §2.1.3 (явный filename > basename URL > basename пути > значение по умолчанию платформы)
  • Ограничения платформы на медиа (размер / MIME / длительность) задекларированы в документации адаптера (§2.1.4)
  • Неподдерживаемые типы медиа обрабатываются по лестнице деградации §2.1.5: деградация к близкому типу или возврат retcode=10002, без исключений и без молчаливого отбрасывания

Объединённая пересылка (необязательно, см. §2.4)

  • При наличии у платформы нативной объединённой пересылки MergeForward использует специализированный эндпоинт протокола, при сбое — откат к send_msg (семейство OneBot11)
  • При отсутствии нативной пересылки, но наличии форматированного текста, MergeForward рендерится в свёрнутую форму платформы (HTML-карточка / Card / Embed / blockquote)
  • При отсутствии обоих MergeForward не реализуется; не возвращается успех с отправкой словарей node как чистого текста
  • Внутри MergeForward больше не вызывается Raw_ob12 для пересылки тех же nodes

Обратное преобразование

  • Raw_ob12 реализован (обязательно, пропускать нельзя)
  • Raw_ob12 обрабатывает все стандартные сегменты сообщений (text, image, audio, video, file, mention, reply)
  • Raw_ob12 обрабатывает платформенные сегменты расширений (типы {platform}_xxx)
  • Стандартные методы отправки (Text, Image и т.д.) внутренне делегируют Raw_ob12, а не реализуют логику преобразования независимо
  • Неподдерживаемые сегменты пропускаются с записью предупреждения, без выбрасывания исключений
  • Составные сегменты сообщений обрабатываются корректно (слияние или разделение по порядку)

11. MessageBuilder (конструктор сообщений) — что нужно знать стороне адаптера

MessageBuilder — предоставляемый ErisPulse инструмент построения сегментов сообщений OneBot12 для построения сообщений на стороне модулей: цепные вызовы (или статическое быстрое построение) в итоге выдают стандартный список сегментов сообщений [{"type": ..., "data": ...}], который вызывающая сторона передаёт напрямую в Raw_ob12.

Стороне адаптера нужно знать только одно: то, что получает Raw_ob12, — это и есть результат работы этого инструмента — полностью изоморфный рукописному списку сегментов сообщений; обрабатывайте его согласно логике диспетчеризации сегментов из §6.2, без необходимости определять, откуда он — из MessageBuilder или из литерала.

Полное использование (механизм двух режимов, все методы сегментов сообщений, утилитарные методы copy() / clear() и примеры) см. в Подробно о MessageBuilder; в этом документе повторяться не будем.
