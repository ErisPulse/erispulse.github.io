Руководство по стандартизации адаптеров (генеральное руководство)

Tip

Когда читать этот документ: когда вы разрабатываете новый адаптер, добавляете новую возможность для какой-либо платформы, вам нужно решить «включать в стандарт или оформлять как расширение {platform}_», как придумывать имена, как обрабатывать различия между платформами — сначала прочитайте этот документ. Если нужно лишь уточнить конкретную спецификацию по какой-то области, можно сразу перейти к соответствующему документу из карты стандартов в §2.

Настоящий документ является генеральным руководством по стандартизации адаптеров ErisPulse: он устанавливает принципы кроссплатформенной стандартизации, карту стандартов, паттерны обработки различий, процесс включения новых возможностей в стандарт, а также даёт полные определения стандарта интерактивных компонентов (кнопки/клавиатуры, выпадающие списки и т.д.) и интерактивных событий обратного вызова. Любой разработчик адаптеров при реализации новой функциональности должен в первую очередь использовать стандартные определения, чтобы разработчики модулей получали одинаковый опыт на любой платформе с одним и тем же кодом — одинаковые имена, одинаковые параметры, одинаковые возвращаемые значения.

1. Принципы стандартизации

  1. Единообразие имён: одно и то же понятие на всех платформах использует одно и то же имя (например, отзыв сообщения единообразно delete_message, сегмент кнопок единообразно keyboard), независимо от платформы
  2. Единообразие параметров: структура параметров стандартных действий/сегментов/методов одинакова на всех платформах; платформенно-специфичные параметры предоставляются как необязательные расширяемые параметры или поля расширения, не загрязняя стандартную сигнатуру
  3. Единообразие возвращаемых значений: все вызовы API/отправки возвращают стандартную структуру ответа (status/retcode/data/message_id/message), стандартные поля внутри data (такие как user_id/user_name) имеют одинаковую семантику; исходные данные платформы помещаются в {platform}_raw
  4. Обоснованные расширения: платформенно-специфичные возможности именуются с префиксом {platform}_ (сегменты: yunhu_form; действия: yunhu.board; поля событий: qqbot_button_id), явно обозначая их некроссплатформенность
  5. Различия поглощаются на уровне адаптера: код модулей программируется ориентированно на стандарт, различия платформ преобразуются адаптером (маппинг параметров, нормализация полей, деградация возможностей), от модулей не требуется писать платформенные ветвления
  6. Деградация возможностей без ошибок: когда платформа не поддерживает некоторую стандартную возможность, выполняется грациозная деградация (возврат retcode=10002, текстовизация компонента в alt_message), без выбрасывания исключений, прерывающих логику модуля

3. Рабочий процесс стандартизации (как новые возможности попадают в стандарт)

Платформенно-специфичная возможность (префикс {platform}_)
        │  одна и та же возможность появилась на ≥2 платформах
        ▼
Выявление общего (извлечение универсальных понятий и подмножества параметров)
        │
        ▼
Черновик стандарта (именование + параметры + возвращаемые значения + таблицы маппинга для каждой платформы)
        │  ревью
        ▼
Внесение в настоящее генеральное руководство / документы стандартов по областям + реализация слоя совместимости в базовом классе фреймворка/адаптерах
        │
        ▼
Стандартный сегмент/действие (без префикса) — доступно модулям кроссплатформенно

Пример: кнопки изначально были реализованы независимо на каждой платформе (telegram_inline_keyboard / кнопки Yunhu / QQBot keyboard) → появились на ≥3 платформах → извлечена общая структура (label/type/data + rows) → опубликован стандартный сегмент keyboard → каждый адаптер реализует слой совместимости (декораторы принимают общую структуру + преобразование стандартного сегмента + прозрачная передача нативных сегментов).

3.1 Правила именования

Объект Правило Пример
Стандартные сегменты сообщений нижний регистр, общие понятия без префикса keyboard, select, mention

3.2 Правила параметров и возвращаемых значений

  • Стандартные параметры на всех платформах имеют одинаковые имена и одинаковую семантику; единицы/формат явно указываются в документе стандарта (например, метки времени в секундах, строковые ID)
  • Обязательные параметры берутся как общее подмножество возможностей всех платформ; платформенные расширенные возможности — необязательные параметры
  • Жёсткие ограничения платформ (например, rich media QQBot нельзя отправлять вместе с event_id) автоматически обрабатываются/деградируют на уровне адаптера и не раскрываются модулям
  • Стандартные поля возвращаемого data одинаковы на всех платформах; дополнительная платформенная информация помещается в поля с платформенными именами внутри data или в {platform}_raw

5.2 keyboard — кнопки/инлайн-клавиатура

Структура сегмента сообщения (направление отправки)

Стандартный сегмент keyboard = двумерный массив rows, каждая кнопка имеет вид {"label": "отображаемый текст", "type": "callback" | "link", "data": "данные обратного вызова или адрес перехода"}, также допускаются платформенно-специфичные необязательные поля (адаптер маппит по возможностям или игнорирует).

Эталонное определение структуры: полный JSON сегмента сообщения, таблица полей и семантика полей приведены в Стандарте преобразования событий §4.1.1 — сегмент keyboard (кнопки/инлайн-клавиатура), в настоящем разделе не повторяются.

Таблица маппинга по платформам

Платформа Стандартный сегмент → нативная структура Справочник нативной структуры
Telegram reply_markup.inline_keyboard: [{text, callback_data | url}] callback→callback_data (≤64 байт), link→url
Yunhu content.buttons: [{label, action_type}] callback→action_type:2 + action + value, link→action_type:1 + url
QQBot keyboard.content.rows: [{label, type, data}] callback→type:2 + data, link→type:0 + data (сообщение должно быть типа markdown)
Kook модуль action-group карточки: [{type, text, value, click}] callback→click:return + value, link→click:link + url
Discord components[].components: [{label, style, custom_id | url}] callback→style:1 + custom_id, link→style:5 + url

Send-декораторы (реализуются классом Send каждого адаптера)

Универсальные декораторы реализуются каждым адаптером в собственном классе Send (без изменения базового класса фреймворка):

  • .Keyboard(rows): стандартное имя, принимает универсальную структуру rows из §5.2, внутри генерирует стандартный сегмент сообщения keyboard (или напрямую преобразует в нативную структуру платформы), обрабатывается единообразно через Raw_ob12
  • .Buttons(rows): необязательный семантический псевдоним, поведение идентично
  • Обратная совместимость: при обнаружении нативной структуры платформы она передаётся напрямую (без ошибок, без преобразования)
  • Платформенные нативные сегменты-расширения (например, telegram_inline_keyboard) продолжают передаваться прозрачно, без изменений
# Один и тот же код — любая платформа (декораторы и преобразования предоставляются каждым адаптером)
rows = [[{"label": "Нравится", "type": "callback", "data": "like:1"},
         {"label": "Профиль", "type": "link", "data": "https://example.com"}]]
await adapter.Send.To("group", gid).Keyboard(rows).Text("Выберите")

Список совместимости адаптеров: QQBot / Telegram / Yunhu уже реализовано (декораторы + преобразование стандартного сегмента); новые адаптеры могут просто реализовать согласно настоящему документу (см. §7 Checklist).

Стандартное поле Тип Обязательно Описание

  • Полнофункциональные карточки платформ продолжать выражать сегментом-расширением {platform}_card (например, kook_card)

Стандарт типов сессий ErisPulse

Tip

Когда нужно читать эту статью: когда вы адаптируете платформу, сопоставляя нативные сессии с платформы с типами (private/group/channel/guild/thread), или в модуле, если не уверены, какой тип цели нужно передавать в Send.To(), или хотите понять, как происходит автоматическое преобразование event.reply(). Если не нужно, можете пропустить.

В этом документе определены стандартные типы сессий, поддерживаемые ErisPulse, включая типы событий получения и типы целей отправки.

1. Основные понятия

1.1 Типы получения и отправки

ErisPulse различает два типа сессий:

  • Тип получения (Receive Type): поле detail_type события, используемое для получения
  • Тип отправки (Send Type): тип цели, используемый в методе Send.To() при отправке сообщений

1.2 Отношения между типами

Тип получения (detail_type)     Тип отправки (Send.To)
─────────────────        ────────────────
private                 →        user
group                   →        group
channel                 →        channel
guild                   →        guild
thread                  →        thread
user                    →        user

Ключевые моменты:

  • private — это тип получения, при отправке стандартный тип — user
  • group, channel, guild, thread — одинаковые типы при получении и отправке
  • Рекомендуемый путь: использовать event.reply() — автоматически выполняет преобразование типов и вывод цели, без необходимости ручного управления (автоматическое преобразование private → user происходит здесь)
  • При ручной отправке: передавайте тип отправки (например, Send.To("user", ...)); передача типа получения, например, Send.To("private", ...) тоже может быть автоматически преобразована, но не рекомендуется (см. §6.1)

2. Стандартные типы сессий

2.1 Стандартные типы OneBot12

private

  • Тип получения: private
  • Тип отправки: user
  • Описание: сообщения в личной переписке
  • Поле ID: user_id
  • Применимые платформы: все платформы, поддерживающие личную переписку

group

  • Тип получения: group
  • Тип отправки: group
  • Описание: сообщения в группе, включая различные формы групп (например, supergroup в Telegram)
  • Поле ID: group_id
  • Применимые платформы: все платформы, поддерживающие групповые чаты

user

  • Тип получения: user
  • Тип отправки: user
  • Описание: тип пользователя, некоторые платформы (например, Telegram) представляют личные чаты как user, а не private
  • Поле ID: user_id
  • Применимые платформы: Telegram и другие платформы

2.2 Расширенные типы ErisPulse

channel

  • Тип получения: channel
  • Тип отправки: channel
  • Описание: сообщения в канале, поддерживают широковещательные сообщения нескольким пользователям
  • Поле ID: channel_id
  • Применимые платформы: Discord, Telegram, Line и др.

guild

  • Тип получения: guild
  • Тип отправки: guild
  • Описание: сообщения в сервере/сообществе, обычно используются для событий уровня сервера Discord
  • Поле ID: guild_id
  • Применимые платформы: Discord и др.

thread

  • Тип получения: thread
  • Тип отправки: thread

5. Автоматическое определение типа

Если у события отсутствует явное поле detail_type, система автоматически определяет тип по доступным полям ID:

Note

Изменение поведения в 2.7.0+: detail_type используется только если это известный тип сессии (стандартный или пользовательский). У событий notice/request (например, group_member_increase, friend_increase) detail_type является семантическим подтипом, а не типом сессии, и система будет определять правильный тип сессии по полям ID.

5.1 Приоритет определения

Приоритет (от высокого к низкому):
1. group_id     → group
2. channel_id   → channel
3. guild_id     → guild
4. thread_id    → thread
5. user_id      → private

5.2 Примеры использования

# У события только group_id
event = {"group_id": "123", "user_id": "456"}
receive_type = infer_receive_type(event)
# Возвращает: "group" (используется приоритетный group_id)

# У события только user_id
event = {"user_id": "123"}
receive_type = infer_receive_type(event)
# Возвращает: "private"

# У события notice detail_type — семантический подтип, в 2.7.0+ определяется по полю ID
event = {"type": "notice", "detail_type": "group_member_increase", "group_id": "123"}
receive_type = infer_receive_type(event)
# Возвращает: "group" (а не "group_member_increase")

9. Рекомендуемые практики

7.1 Разработчики адаптеров

  1. Используйте стандартные сопоставления: по возможности сопоставляйте с типами стандарта, а не создавайте новые типы
  2. Правильно преобразуйте: убедитесь, что сопоставление типов получения и отправки корректно
  3. Сохраняйте исходные данные: сохраняйте оригинальный тип события в {platform}_raw
  4. Документируйте: в документации адаптера укажите сопоставления типов

7.2 Разработчики модулей

  1. Используйте вспомогательные методы: используйте методы, такие как get_send_type_and_target_id()
  2. Избегайте жесткого кодирования: не пишите код вида if group_id else "private"
  3. Учитывайте все типы: код должен поддерживать все стандартные типы, а не только private/group
  4. Гибко проектируйте: используйте методы обертки событий, а не прямой доступ к полям

7.3 Определение типов

  • Предпочитайте detail_type: если есть явное поле, не используйте определение
  • Рационально используйте определение: только когда нет явного типа
  • Учитывайте приоритеты: знайте приоритеты определения, чтобы избежать неожиданных результатов

10. Часто задаваемые вопросы

В1: Почему при отправке private нужно преобразовывать в user?

О: Это требование стандарта OneBot12. private — это понятие получения, при отправке лучше использовать user, что соответствует семантике.

В2: Как поддержать новые типы сессий?

О: Зарегистрируйте пользовательский тип с помощью register_custom_type(), или используйте стандартные типы, такие как channel, guild.

В3: Что делать, если у события нет detail_type?

О: Система автоматически определит тип по доступным полям ID. Приоритет: group > channel > guild > thread > user.

В4: Как адаптер должен сопоставлять Telegram supergroup?

О: В логике преобразования адаптера сопоставьте supergroup со стандартным типом group.

В5: Как обрабатывать специальные платформы, такие как почта?

О: Для неуниверсальных или платформенных специфических типов используйте {platform}_raw и {platform}_raw_type для сохранения исходных данных, адаптер должен обрабатывать их самостоятельно.

Стандартизированные правила преобразования адаптеров

Tip

Когда нужно читать эту статью: когда вы конвертируете нативные события платформы в стандартные события OneBot12 в адаптере — проверьте обязательные поля, структуру сегментов сообщений, именование расширенных полей ({platform}_ префикс), вывод типа сессии, сопоставляя с этой статьей. Если не нужно, пропустите.

1. Основные принципы

  1. Строгое соответствие: все стандартные поля должны полностью соответствовать спецификации OneBot12
  2. Ясное расширение: функции, специфичные для платформы, должны иметь префикс {platform}_ (например, yunhu_form)
  3. Полная целостность данных: исходные данные события должны сохраняться в поле {platform}_raw, тип исходного события — в поле {platform}_raw_type
  4. Единое время: все временные метки должны быть преобразованы в 10-значные Unix-временные метки (в секундах)
  5. Единое имя платформы: поле platform должно соответствовать названию или псевдониму, зарегистрированному в ErisPulse

4.2 Платформенные расширенные сегменты сообщений

Сегменты сообщений, специфичные для платформы, должны иметь платформенный префикс:

// Yunhu - форма
{"type": "yunhu_form", "data": {"form_id": "123456", "form_name": "Форма регистрации"}}

// Telegram - стикер
{"type": "telegram_sticker", "data": {"file_id": "CAACAgIAAxkBAA...", "emoji": "😂"}}

Требования к расширенным сегментам сообщений:

  1. Поля внутри data не должны иметь префикса: {"type": "yunhu_form", "data": {"form_id": "..."}}, а не {"type": "yunhu_form", "data": {"yunhu_form_id": "..."}}
  2. Обеспечьте механизм понижения: модуль может не распознавать расширенные сегменты сообщений, адаптер должен предоставить текстовое замещение в alt_message
  3. Документация: каждый расширенный сегмент сообщения должен быть подробно описан в документации адаптера: type, структура data и сценарии использования

5. Обработка неизвестных событий

Для неопознанных типов событий следует генерировать событие предупреждения:

{
  "id": "1234567893",
  "time": 1752241223,
  "type": "unknown",

6. Стандарты именования расширений

6.1 Именование полей

Правило: {platform}_{field_name}

Платформенный префикс    Имя поля            Полное имя поля
────────    ───────          ──────────
yunhu       command           yunhu_command
telegram    sticker_file_id   telegram_sticker_file_id
onebot11    anonymous         onebot11_anonymous
email       subject           email_subject

Требования:

  • platform должен полностью соответствовать названию платформы, зарегистрированному в адаптере (регистрозависимо)
  • field_name должно использовать стиль snake_case
  • Запрещено использовать двойное подчёркивание __ в начале (зарезервировано Python)
  • Запрещено использовать имя, совпадающее со стандартным полем (например, type, time, message и т.д.)

6.2 Именование типов сегментов сообщений

Правило: {platform}_{segment_type}

Стандартные типы сегментов сообщений (text, image, audio, video, mention, reply и т.д.) не должны иметь платформенный префикс. Только платформенные специфичные типы сегментов сообщений должны иметь префикс.

6.3 Именование полей исходных данных

Следующие имена полей являются зарезервированными, все адаптеры должны соблюдать:

Зарезервированное поле Тип Описание
{platform}_raw any Полная копия исходных данных события платформы
{platform}_raw_type string Идентификатор типа исходного события платформы

Требования:

  • {platform}_raw должен быть глубокой копией исходных данных, а не ссылкой
  • {platform}_raw_type должен быть строкой, даже если платформа использует числовой тип, его нужно преобразовать в строку
  • Эти два поля должны присутствовать во всех событиях (если данные недоступны, то null и пустая строка "")

8.3 Рекомендуемые практики

  1. Приоритет стандартных полей: не предполагайте, что расширенные поля всегда существуют
  2. Определение платформы: используйте event.get_platform() для определения платформы, а не по наличию расширенных полей
  3. Плавное понижение: при невозможности обработки расширенных сегментов сообщений используйте alt_message как резервный вариант
  4. Не жёстко кодируйте префиксы: используйте переменную platform для динамического составления
# ✅ Рекомендуется
platform = event.get_platform()
raw_data = event.get(f"{platform}_raw")

# ❌ Не рекомендуется
raw_data = event.get("yunhu_raw")

8.4 Обработка запросов

Разработчики модулей могут использовать event.approve() и event.reject() для обработки запросов:

from ErisPulse.Core.Event import request

# Автоматическое согласование запроса на добавление в друзья
@request.on_friend_request()
async def handle_friend_request(event):
    user_name = event.get_user_nickname() or event.get_user_id()
    comment = event.get_comment()
    
    # Согласование запроса
    result = await event.approve()
    if result.get("status") == "ok":
        print(f"Согласован запрос на добавление в друзья от {user_name}")
    else:
        print(f"Ошибка согласования запроса: {result.get('message')}")

# Запрос на вступление в группу: решение по условиям
@request.on_group_request()
async def handle_group_request(event):
    comment = event.get_comment()
    
    # Отклонение запроса
    result = await event.reject(comment="Временно не принимаю новые группы")

Прямое управление через адаптер (для сценариев, не связанных с обработчиками событий):

from ErisPulse import adapter

# Прямое управление по request_id
await adapter.myplatform.Request("req_abc123").accept()
await adapter.myplatform.Request("req_abc123").reject()

# Указание аккаунта бота
await adapter.myplatform.Request("req_abc123").Using("bot1").accept()

# С комментарием

9. Вывод типа сессии для событий notice / request

9.1 Проблемный фон

Типы detail_type событий notice и request — это семантические подтипы (например, group_member_increase, friend_increase), а не типы сессии (например, group, private).

type        detail_type                  Смысл            Тип сессии
────        ───────────                  ────            ────────
message     group                        Сообщение в группе         group (detail_type — тип сессии)
message     private                      Личное сообщение          private (detail_type — тип сессии)
notice      group_member_increase        Увеличение участников группы    group (выводится по group_id)
notice      friend_increase              Увеличение друзей           private (выводится по user_id)
request     friend                       Запрос на добавление в друзья     private (выводится по user_id)
request     group                        Запрос на вступление в группу      group (detail_type — тип сессии)

9.2 Правила вывода

Порядок вывода infer_receive_type():

  1. Если detail_type — известный тип сессии (private/group/channel/guild/thread/user), используйте его
  2. Если detail_type — пользовательский тип сессии, используйте его
  3. В противном случае (семантические подтипы notice/request), выводите по ID-полю:
    • Если есть group_id → "group"
    • Если есть channel_id → "channel"
    • Если есть guild_id → "guild"
    • Если есть thread_id → "thread"
    • Если есть user_id → "private"

9.3 Вывод цели event.reply()

Цель отправки event.reply() в событиях notice/request определяется выводом типа сессии:

  • События уведомления о группе (с group_id) → отправка в группу
  • События уведомления о друзьях (только user_id) → отправка в личный чат
from ErisPulse.Core.Event import notice

@notice.on_group_increase()
async def handle_welcome(event):
    group_id = event.get("group_id")    # "group_789"
    user_id = event.get("user_id")      # "user_456"

    # event.reply() отправляется в группу (group/group_789)
    await event.reply("Добро пожаловать в группу!")

    # Если нужно уведомить администратора (личный чат), явно укажите цель:
    await adapter.Send.To("user", "admin_id").Text(f"Новый участник {user_id} присоединился к {group_id}")

9.4 Рекомендации для разработчиков адаптеров

Убедитесь, что события notice/request содержат правильные ID-поля:

detail_type Обязательные ID-поля Выводимый тип сессии
group_member_increase group_id + user_id group
group_member_decrease group_id + user_id group
friend_increase user_id private
friend_decrease user_id private
friend (запрос) user_id private
group (запрос) group_id group

Raw_ob12 — метод, реализация которого обязательна. Это одна из ключевых обязанностей адаптера: принимать стандартные сегменты сообщений OneBot12 и преобразовывать их в вызовы нативного API платформы. 2. Подробная спецификация параметров

2.1 Протокол отправки медиасообщений (Image / Voice / Video / File)

Этот раздел — единый стандарт протокола отправки медиа: модуль вызывает четыре медиаметода одним и тем же кодом, а адаптер отвечает за преобразование различных форм параметра file в нативное для платформы поведение загрузки/отправки.

2.1.1 Допустимые формы параметра file

Форма Пример Требования к адаптеру
HTTP(S) URL https://example.com/image.jpg Обязательно принимать
Локальный путь к файлу /path/to/file.jpg, C:\path\to\file.jpg Обязательно принимать
Бинарные данные b"\x89PNG..." Обязательно принимать
URI file:// file:///path/to/file.jpg Рекомендуется принимать (можно преобразовать в локальный путь для обработки)
Строка Base64 / Data URI iVBORw0KGgo=..., data:image/png;base64,... Рекомендуется принимать (совместимо с практиками экосистемы OneBot12)

Адаптер обязан вести себя единообразно на трёх обязательных формах — независимо от того, передаёт модуль URL, путь или bytes, полученное сообщение будет одним и тем же. Если платформа не может напрямую использовать какую-то форму (например, API платформы не поддерживает ссылки на внешние URL), адаптер самостоятельно скачивает/читает и загружает данные; недопустимо требовать от модуля повторить попытку с другой формой.

2.1.2 Порядок определения формы

При реализации обработки медиапараметров адаптер должен определять форму в следующем порядке:

  1. Тип bytes → прямая загрузка
  2. Строка начинается с http:// / https:// → обрабатывать как URL (прямая ссылка или скачивание с последующей загрузкой — по возможностям платформы)
  3. Строка начинается с file:// → отрезать префикс и обрабатывать как локальный путь
  4. Остальные строки → обрабатывать как локальный путь (если существует — прочитать и загрузить; если нет — вернуть стандартный ответ об ошибке)
def _resolve_media(self, file: "str | bytes") -> bytes:
    """Определение формы и нормализация (пример)"""
    if isinstance(file, (bytes, bytearray)):
        return bytes(file)
    if file.startswith(("http://", "https://")):
        return self._download(file)          # скачивать, когда платформа не может ссылаться на URL
    if file.startswith("file://"):
        file = file[len("file://"):]
    with open(file, "rb") as f:              # локальный путь
        return f.read()

2.1.3 Семантика имени файла для File

Сигнатура метода File: File(file, filename=None) (filename — необязательный параметр, встроен в базовый класс).

Порядок определения имени файла (адаптер генерирует его по этой схеме, когда filename не предоставлен явно):

  1. Явный параметр filename (наивысший приоритет)
  2. basename из URL (например, https://host/a/b/report.pdf → report.pdf; необходимо отрезать query string)
  3. basename из локального пути (например, /tmp/data/backup.zip → backup.zip)
  4. Генерация по умолчанию платформы (например, file_{timestamp}; следует сохранять реальное расширение — расширение влияет на распознавание типа и поведение предпросмотра на стороне платформы)

Image / Voice / Video также могут принимать filename (передаётся через data.filename сегмента сообщения), но кроссплатформенная семантика имени файла гарантируется только для File.

2.1.4 Обязанность декларирования ограничений платформы

Ограничения платформ на максимальный размер медиа, форматы (MIME), длительность (аудио/видео) и т.д. различаются. Адаптер должен:

  • декларировать в документации адаптера поддерживаемые типы медиа и диапазоны ограничений;
  • при превышении лимитов или неподдерживаемом вводе возвращать стандартный ответ об ошибке (status: "failed"; retcode — 10002 или семантический код ошибки платформы, message поясняет причину); недопустимо выбрасывать исключения, прерывая логику модуля.

2.1.5 Лестница деградации возможностей

Когда платформа не поддерживает какой-либо тип медиа, деградация выполняется по следующей лестнице (согласно общему принципу «деградация возможностей без ошибок»):

Сценарий Поведение при деградации
Voice не поддерживает голосовые сообщения Следует отправлять как File (или ближайшую платформенную форму); при невозможности выразить — вернуть retcode=10002
Video не поддерживает видеосообщения То же
Тип медиа полностью не поддерживается (нет файловых возможностей) Вернуть retcode=10002, в message указать неподдерживаемый тип данных
Форма не поддерживается (например, невозможно обработать base64) Вернуть retcode=10002, можно указать в message подсказку модулю использовать URL/bytes

Запрещённое поведение: молчаливое отбрасывание (без ответа), выбрасывание исключений, требование к модулю писать платформенные ветки обработки.

2.2 Спецификация параметра упоминания пользователя

Метод: At (модифицирующий метод)

Параметр: user_id (str)

Требования:

  • user_id должен быть строковым идентификатором пользователя
  • Формат user_id может отличаться на разных платформах (число, UUID, строка и т.д.)
  • Адаптер отвечает за преобразование user_id в платформенно-специфичный формат
  • Обратите внимание: вызов фактического метода отправки должен находиться на последней позиции

Пример:

# Одиночное упоминание пользователя

# Несколько упоминаний (цепной вызов)
send.To("group", "g123").At("123456").At("789012").Text("Всем привет")

2.3 Спецификация параметра ответа на сообщение

Метод: Reply (модифицирующий метод)

Параметр: message_id (str)

Требования:

  • message_id должен быть строковым идентификатором сообщения
  • Должен быть ID ранее полученного сообщения
  • Некоторые платформы могут не поддерживать функцию ответа; адаптер должен корректно деградировать

Пример:

send.To("group", "g123").Reply("msg_123456").Text("Принято")

2.4 Возможность объединённой пересылки (MergeForward, необязательно)

MergeForward(nodes) — необязательный метод возможности: упаковывает несколько фрагментов содержимого для отправки в форме «объединённой пересылки / свёрнутого форматированного текста»; адаптер определяет оптимальное представление в зависимости от возможностей платформы. Семантика отличается от Forward(from_chat_id, message_id) из §1.1 (пересылка существующего сообщения); оба сосуществуют.

Контекст стандарта: ядро стандарта OneBot12 не содержит сегмента node и API объединённой пересылки — «узлы сообщений» являются концепцией уровня реализации экосистемы OneBot v11 (расширение go-cqhttp); v12 передаёт подобные платформенно-специфические возможности механизму расширений. Реализация в ErisPulse — эквивалент механизма расширений: без добавления новых стандартных сегментов сообщений — через необязательные методы возможностей + обнаружение в рантайме через list_sends — адаптеры с реализованным MergeForward автоматически получают возможность; вызывающая сторона при отсутствии реализации автоматически откатывается к обычному тексту, модули не требуют никаких изменений.

Сигнатура метода:

def MergeForward(self, nodes: List[Dict]) -> asyncio.Task:
    """
    Отправка объединённой пересылки / свёрнутого форматированного текста

    :param nodes: массив узлов объединённой пересылки (формат узлов OneBot v11 из расширения go-cqhttp):
        [
            {
                "type": "node",
                "data": {
                    "user_id": "10000",     # id отправителя для отображения
                    "nickname": "MyBot",     # ник отправителя для отображения
                    "content": [            # массив сегментов сообщения, сейчас сегменты text
                        {"type": "text", "data": {"text": "[1/3] Заголовок\nОсновной текст…"}}
                    ],
                },
            },
        ]
    :return: asyncio.Task, после await возвращает стандартный формат ответа
    """

Требования к реализации:

  1. Платформа имеет нативную объединённую пересылку (семейство OneBot11): обязательно вызывать специализированный эндпоинт протокола (send_group_forward_msg / send_private_forward_msg) — реализации вроде NapCat отклоняют сегменты node, передаваемые через send_msg (retcode 1400); при отказе специализированного эндпоинта можно откатиться к прямой отправке сегментов node через send_msg
  2. Платформа не имеет нативной пересылки, но имеет форматированный текст (Yunhu / Telegram / Kook / Discord / Matrix и др.): следует рендерить узлы в свёрнутую форму форматированного текста платформы (сворачиваемая HTML-карточка / Card / Embed / список blockquote); справочные стили и список задач по каждому адаптеру см. в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md
  3. Нет ни того, ни другого: недопустимо реализовывать этот метод (тем более возвращать успех, отправляя словари node как чистый текст) — без реализации list_sends не содержит MergeForward, и вызывающая сторона автоматически откатывается к обычному тексту
  4. Семантика сбоя: допустимо вернуть стандартный ответ об ошибке (status: "failed") или выбросить исключение; вызывающая сторона откатится к отправке чистого текста, содержимое не теряется
  5. Недопустимо внутри MergeForward снова вызывать Raw_ob12 для отправки тех же nodes (в Raw_ob12 OneBot11 уже встроена автоматическая маршрутизация чистых сегментов node — образуется цикл)
  6. Парсинг исходящих сегментов node (соглашение для всех адаптеров): диспетчеризация сегментов Raw_ob12 каждого адаптера должна регистрировать сегмент node — чистый список node автоматически маршрутизируется в представление объединённой пересылки этого адаптера (на платформах с MergeForward это эквивалентно прямому вызову; на платформах без этого метода извлекается текст каждого узла и выводится построчно как есть в формате «ник: текст»); текст сегментов node в смешанном списке включается в основной текст. Любой адаптер, получивший сегмент node, не должен молча его отбрасывать.

Формы реализации на платформах (подробнее в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md):

  • Нативные эндпоинты: OneBot11, SnowLuma (трёхуровневый откат: специализированный эндпоинт send_group/private_forward_msg → upload_forward_msg с получением resid и отправкой сегмента forward → прямая отправка сегментов node; API SnowLuma полностью выровнено с NapCat, адаптер может подключаться напрямую к бэкенду NapCat)
  • Сворачиваемая HTML-карточка <details>: Yunhu (протоколы bot/пользователя), Email, Sandbox, Allons(Ideaura)
  • HTML по белому списку / цитатные блоки: Telegram (<b>+<blockquote>), Matrix (вариант blockquote, удаление details/инлайн-стилей по белому списку)
  • Платформенные карточки: Kook (Card header+section), Discord (Embed fields)
  • Официальный Markdown-список цитат: QQBot (в официальном md нет синтаксиса сворачивания, серверная валидация отклоняет недопустимые теги с ошибкой 40034011)
  • Не реализуется (деградация к выводу сегментов node как есть): OneBot12 (в стандарте нет сегмента node), WeCom, Terminal, Webhook, WechatMp

Пример обнаружения на стороне вызывающего:

sends = adapter.list_sends(platform)
if "MergeForward" in sends:
    await adapter.Send.To("group", "123").MergeForward(nodes)
else:
    await adapter.Send.To("group", "123").Text(plain_text)

Референсная реализация: ErisPulse-OneBot11Adapter (специализированный эндпоинт → откат к send_msg); шаблоны рендеринга и список задач по каждому адаптеру см. в SDK/Adapter/ADAPTER_FORWARD_GUIDE.md.

6. Спецификация обратного преобразования (OneBot12 → платформа)

Адаптер не только должен преобразовывать нативные события платформы в формат OneBot12 (прямое преобразование), но и обязан предоставлять возможность преобразования сегментов сообщений OneBot12 обратно в вызовы нативного API платформы (обратное преобразование). Единая точка входа обратного преобразования — метод Raw_ob12.

6.1 Модель преобразования

Прямое преобразование (направление приёма)       Обратное преобразование (направление отправки)
─────────────────                ─────────────────
Нативное событие платформы                       Список сегментов сообщений OneBot12
    │                                  │
    ▼                                  ▼
Converter.convert()               Send.Raw_ob12()
    │                                  │
    ▼                                  ▼
Стандартное событие OneBot12                     Вызов нативного API платформы
(содержит {platform}_raw)                        (возвращает стандартный формат ответа)

Ключевая симметрия: прямое преобразование сохраняет исходные данные в {platform}_raw, обратное преобразование принимает стандартный формат OneBot12 и восстанавливает его в вызовы платформы.

6.2 Спецификация реализации Raw_ob12

Raw_ob12 принимает список стандартных сегментов сообщений OneBot12 и обязан преобразовывать их в вызовы нативного API платформы.

Сигнатура метода:

def Raw_ob12(self, message_segments: List[Dict]) -> asyncio.Task:
    """
    Отправка стандартных сегментов сообщений OneBot12

    :param message_segments: список сегментов сообщений OneBot12
        [
            {"type": "text", "data": {"text": "Hello"}},
            {"type": "image", "data": {"file": "https://..."}},
            {"type": "mention", "data": {"user_id": "123"}},
        ]
    :return: asyncio.Task, после await возвращает стандартный формат ответа
    """

Требования к реализации:

  1. Должны обрабатываться все стандартные типы сегментов сообщений: как минимум поддержка text, image, audio, video, file, mention, reply
  2. Должны обрабатываться платформенные сегменты расширений: сегменты типа {platform}_xxx преобразовывать в соответствующие нативные вызовы платформы
  3. Должен возвращаться стандартный формат ответа: согласно Стандарту API-ответов
  4. Неподдерживаемые сегменты должны пропускаться с записью предупреждения; не следует выбрасывать исключение, приводящее к сбою отправки всего сообщения

6.3 Правила преобразования сегментов сообщений

6.3.1 Преобразование стандартных сегментов сообщений

Адаптер обязан реализовать преобразование следующих стандартных сегментов сообщений:

Сегмент OneBot12 Требования к преобразованию
text Напрямую использовать data.text
image data.file обрабатывается согласно медиапротоколу §2.1 (три обязательные формы + порядок определения)
audio Та же логика обработки, что и у image
video Та же логика обработки, что и у image
file Та же логика обработки, что и у image; имя файла обрабатывается по порядку определения из §2.1.3 через data.filename
mention Преобразуется в механизм упоминаний платформы (например, entities в Telegram, at_uid в Yunhu)
reply Преобразуется в механизм цитирования/ответа платформы
face Преобразуется в механизм отправки эмодзи платформы; при отсутствии поддержки — пропустить
location Преобразуется в механизм отправки геопозиции платформы; при отсутствии поддержки — пропустить

6.3.2 Преобразование платформенных сегментов расширений

Для сегментов с платформенным префиксом адаптер должен распознавать и преобразовывать их:

def _convert_ob12_segments(self, segments: List[Dict]) -> Any:
    """Преобразование сегментов сообщений OneBot12 в нативный формат платформы"""
    platform_prefix = f"{self._platform_name}_"
    
    for segment in segments:
        seg_type = segment["type"]
        seg_data = segment["data"]
        
        if seg_type.startswith(platform_prefix):
            # Сегмент расширения платформы → нативный вызов платформы
            self._handle_platform_segment(seg_type, seg_data)
        elif seg_type in self._standard_segment_handlers:
            # Стандартный сегмент → эквивалентная операция платформы
            self._standard_segment_handlers[seg_type](seg_data)
        else:
            # Неизвестный сегмент → записать предупреждение и пропустить
            logger.warning(f"Неподдерживаемый тип сегмента сообщения: {seg_type}")

6.3.3 Обработка составных сегментов сообщений

Одно сообщение может содержать несколько сегментов; адаптер должен корректно обрабатывать составные сообщения:

# Модуль отправляет сообщение с текстом + изображением + упоминанием пользователя
await send.Raw_ob12([
    {"type": "mention", "data": {"user_id": "123"}},
    {"type": "text", "data": {"text": "Привет"}},
    {"type": "image", "data": {"file": "https://example.com/img.jpg"}}
])

Стратегия обработки:

  • Приоритет слиянию: если платформа поддерживает текст, изображения, @ и т.д. в одном сообщении, следует отправлять слитно
  • Откат к разделению: если платформа не поддерживает слияние, разделить на несколько сообщений и отправить по порядку
  • Сохранение порядка: порядок отправки сегментов должен соответствовать порядку в списке

6.4 Отношение Raw_ob12 к стандартным методам

Стандартные методы отправки адаптера (Text, Image и т.д.) уже встроены в базовый класс SendDSL и по умолчанию делегируются Raw_ob12; подклассу адаптера не нужно реализовывать их повторно:

class Send(SendDSL):
    def Raw_ob12(self, message_segments: List[Dict]) -> asyncio.Task:
        """Ключевая реализация: сегменты сообщений OneBot12 → API платформы (обязательна)"""
        return asyncio.create_task(self._send_ob12(message_segments))

    # Text/Image/Voice/Video/File унаследованы от базового класса, автоматически делегируют Raw_ob12
    # Если нужна платформенно-специфичная логика, можно переопределить отдельный метод:
    # def Text(self, text: str) -> asyncio.Task:
    #     return self.Raw_ob12([{"type": "text", "data": {"text": text}}])

Преимущества:

  • логика преобразования сосредоточена в одном месте — Raw_ob12, меньше дублирования кода
  • поведение стандартных методов и Raw_ob12 полностью совпадает
  • модуль получает одинаковый результат независимо от того, используется Text() или Raw_ob12()
  • базовый класс предоставляет сигнатуры типов, IDE может дополнять стандартные методы

6.5 Пример реализации

class YunhuSend(SendDSL):
    """Реализация Send для платформы Yunhu"""
    
    def Raw_ob12(self, message_segments: list) -> asyncio.Task:
        """Сегменты сообщений OneBot12 → вызов API Yunhu"""
        return asyncio.create_task(self._do_send(message_segments))
    
    async def _do_send(self, segments: list) -> dict:
        """Фактическая логика отправки"""
        # 1. Разбор состояния модификаторов
        at_users = self._at_users or []
        reply_to = self._reply_to
        at_all = self._at_all
        
        # 2. Преобразование сегментов сообщений
        yunhu_elements = []
        for seg in segments:
            seg_type = seg["type"]
            seg_data = seg["data"]
            
            if seg_type == "text":
                yunhu_elements.append({"type": "text", "content": seg_data["text"]})
            elif seg_type == "image":
                yunhu_elements.append({"type": "image", "url": seg_data["file"]})
            elif seg_type == "mention":
                at_users.append(seg_data["user_id"])
            elif seg_type == "reply":
                reply_to = seg_data["message_id"]
            elif seg_type == "yunhu_form":
                # Сегмент расширения платформы
                yunhu_elements.append({"type": "form", "form_id": seg_data["form_id"]})
            else:
                logger.warning(f"Сегмент сообщения, не поддерживаемый Yunhu: {seg_type}")
        
        # 3. Вызов API Yunhu
        response = await self._call_yunhu_api(yunhu_elements, at_users, reply_to, at_all)
        
        # 4. Возврат стандартного формата ответа
        return {
            "status": "ok" if response["code"] == 0 else "failed",
            "retcode": response["code"],
            "data": {"message_id": response.get("msg_id", ""), "time": int(time.time())},
            "message_id": response.get("msg_id", ""),
            "message": "",
            "yunhu_raw": response
        }

10. Чек-лист реализации адаптера

Методы отправки

  • Стандартные методы (Text, Image и т.д.) реализованы
  • Все возвращаемые значения — asyncio.Task
  • Модифицирующие методы (At, Reply, AtAll) возвращают self
  • Методы расширений платформы используют PascalCase, без платформенного префикса
  • Все методы имеют полные аннотации типов и строки документации

Протокол отправки медиа

  • Все обязательные формы параметра file поддерживаются: HTTP(S) URL / локальный путь / bytes (см. §2.1.1)
  • Порядок определения формы соответствует §2.1.2 (bytes → URL → file:// → путь)
  • Порядок определения имени файла File соответствует §2.1.3 (явный filename > basename URL > basename пути > значение по умолчанию платформы)
  • Ограничения платформы на медиа (размер / MIME / длительность) задекларированы в документации адаптера (§2.1.4)
  • Неподдерживаемые типы медиа обрабатываются по лестнице деградации §2.1.5: деградация к близкому типу или возврат retcode=10002, без исключений и без молчаливого отбрасывания

Объединённая пересылка (необязательно, см. §2.4)

  • При наличии у платформы нативной объединённой пересылки MergeForward использует специализированный эндпоинт протокола, при сбое — откат к send_msg (семейство OneBot11)
  • При отсутствии нативной пересылки, но наличии форматированного текста, MergeForward рендерится в свёрнутую форму платформы (HTML-карточка / Card / Embed / blockquote)
  • При отсутствии обоих MergeForward не реализуется; не возвращается успех с отправкой словарей node как чистого текста
  • Внутри MergeForward больше не вызывается Raw_ob12 для пересылки тех же nodes

Обратное преобразование

  • Raw_ob12 реализован (обязательно, пропускать нельзя)
  • Raw_ob12 обрабатывает все стандартные сегменты сообщений (text, image, audio, video, file, mention, reply)
  • Raw_ob12 обрабатывает платформенные сегменты расширений (типы {platform}_xxx)
  • Стандартные методы отправки (Text, Image и т.д.) внутренне делегируют Raw_ob12, а не реализуют логику преобразования независимо
  • Неподдерживаемые сегменты пропускаются с записью предупреждения, без выбрасывания исключений
  • Составные сегменты сообщений обрабатываются корректно (слияние или разделение по порядку)

11. MessageBuilder (конструктор сообщений) — что нужно знать стороне адаптера

MessageBuilder — предоставляемый ErisPulse инструмент построения сегментов сообщений OneBot12 для построения сообщений на стороне модулей: цепные вызовы (или статическое быстрое построение) в итоге выдают стандартный список сегментов сообщений [{"type": ..., "data": ...}], который вызывающая сторона передаёт напрямую в Raw_ob12.

Стороне адаптера нужно знать только одно: то, что получает Raw_ob12, — это и есть результат работы этого инструмента — полностью изоморфный рукописному списку сегментов сообщений; обрабатывайте его согласно логике диспетчеризации сегментов из §6.2, без необходимости определять, откуда он — из MessageBuilder или из литерала.

Полное использование (механизм двух режимов, все методы сегментов сообщений, утилитарные методы copy() / clear() и примеры) см. в Подробно о MessageBuilder; в этом документе повторяться не будем.

1. Предпосылки проектирования

В ErisPulse форматы сообщений (отправка и получение сообщений) и событий полностью соответствуют стандарту OneBot12, но вызов действий API (например, получение информации о пользователе, получение списка групп, отмена сообщения и т.д.) ранее не был унифицирован — разработчикам модулей приходилось писать разные вызовы call_api для каждой платформы.

ApiDSL решает эту проблему, предоставляя строго типизированные стандартные методы действий:

Код модуля (унифицированный для всех платформ)             Реализация адаптера (платформа специфична)
─────────────────              ──────────────────
adapter.Api.get_user_info("123")  →  вызов адаптера call_api / переопределение
adapter.Api.get_group_list()      →  вызов адаптера call_api / переопределение
adapter.Api.delete_message("id")  →  вызов адаптера call_api / переопределение

3.5 Действия с файловыми ресурсами

Warning

Модель файловых ресурсов (двухчастный file_id) в ErisPulse считается "пониженного уровня": ErisPulse не использует модель "сначала загрузить, получить file_id, затем ссылаться" для отправки файлов — модули отправляют файлы с помощью SendDSL.File(file, filename) (URL / путь / байты отправляются напрямую во время отправки, см. спецификацию метода отправки). Действия upload_file / get_file / фрагментация зависят от специфичных для платформы возможностей файловых ресурсов file_id, имеют недостаточную универсальность; только когда у адаптера есть такая возможность, они могут быть переданы, встроенные адаптеры не реализуют и не рекомендуют реализовывать; при вызове обычно возвращается retcode=10002. Если модулю нужно отправлять файлы между платформами, используйте SendDSL.File, не полагайтесь на file_id.

Перспектива: стандартизация модели ресурсов file_id на уровне фреймворка — будущее направление, в текущей версии не предоставляется.

3.5.1 Фрагментированная передача (большие файлы, входит в вышеупомянутый пониженный уровень)

Действия OneBot12 по фрагментации по stage различаются этапами. ApiDSL разделяет этапы одного действия на отдельные методы (offset — смещение байт, data в JSON — Base64); таблица предназначена для справки, адаптер не должен и не должен реализовывать:

Три этапа фрагментированной загрузки: prepare → transfer (циклически по частям) → finish

Метод Этап Параметры Возвращаемое значение
upload_file_fragmented_prepare(name, total_size) prepare name: str, total_size: int file_id (используется во время передачи)
upload_file_fragmented_transfer(file_id, offset, data) transfer file_id, offset: int, data: bytes Нет
upload_file_fragmented_finish(file_id, sha256) finish file_id, sha256: str (проверка целостности файла) file_id 
total = os.path.getsize(path)
r = await adapter.Api.upload_file_fragmented_prepare(os.path.basename(path), total)
fid = r["data"]["file_id"]
offset = 0
with open(path, "rb") as f:
    while chunk := f.read(65536):
        await adapter.Api.upload_file_fragmented_transfer(fid, offset, chunk)

sha256 = hashlib.sha256(open(path, "rb").read()).hexdigest()

Стандартная реализация ApiDSL передает имя стандартного действия как endpoint напрямую в adapter.call_api():

# Стандартная реализация ApiDSL эквивалентна:
async def get_user_info(self, user_id: str) -> dict:
    return await self._adapter.call_api("get_user_info", user_id=user_id, account_id=self._account_id)

Сценарий применения: когда базовый API адаптера сам следует стандартному протоколу OneBot12, call_api нативно поддерживает имена стандартных действий (например, напрямую подключается к сервису, соответствующему этому протоколу).

5.2 Переопределение стандартных методов (сопоставление с оригинальными API платформы)

Адаптер может переопределить отдельные стандартные методы, сопоставляя их с оригинальными API платформы:

class MyAdapter(BaseAdapter):

    class Api(BaseAdapter.Api):
        """Реализация стандартных действий API для MyPlatform"""

        async def get_user_info(self, user_id: str) -> dict:
            # Сопоставление с оригинальным API платформы
            raw = await self._adapter._request("GET", f"/users/{user_id}")
            if raw.get("code") != 0:
                # Ошибка на стороне платформы: используйте сегмент 341xx～345xx для трех низших цифр (346xx зарезервирован фреймворком, не используйте)
                return self._adapter.make_error(retcode=34400, message="Пользователь не существует")

            user = raw["data"]
            return self._adapter.make_response(
                data={
                    "user_id": str(user["id"]),
                    "user_name": user.get("nick", ""),
                    "user_displayname": user.get("display_name", ""),
                    "user_remark": user.get("remark", ""),
                },
                raw=raw,
            )

        async def get_friend_list(self) -> dict:
            raw = await self._adapter._request("GET", "/friends")
            friends = [
                {
                    "user_id": str(u["id"]),
                    "user_name": u.get("nick", ""),
                    "user_displayname": u.get("display_name", ""),
                    "user_remark": u.get("remark", ""),
                }
                for u in raw.get("data", [])
            ]
            return self._adapter.make_response(data=friends, raw=raw)

5.3 Не поддерживаемые действия

Методы, которые адаптер не переопределил, используют стандартную реализацию (передаются в call_api). Если call_api также не поддерживает это действие, следует вернуть стандартный ответ об ошибке:

async def call_api(self, endpoint: str, **params):
    if endpoint not in self._supported_endpoints:
        return self.make_error(retcode=10002, message=f"Действие не поддерживается: {endpoint}")
    # ... вызов API платформы

Разработчики модулей могут определить поддержку по значению retcode в возвращаемом значении:

result = await adapter.myplatform.Api.get_friend_list()
if result["retcode"] == 10002:
    print("Эта платформа не поддерживает получение списка друзей")

Tip

Когда читать этот документ: когда вы реализуете возвращаемые значения call_api / Send / Request в адаптере и хотите убедиться, что структура ответа и коды возврата соответствуют стандарту ErisPulse, или вам нужно выяснить значение конкретного retcode — сверяйтесь с этим документом. Если в этом нет необходимости — пропустите.

1. Описание

Откуда взялась эта спецификация?

Для обеспечения единообразия возвращаемых значений интерфейсов отправки на различных платформах и совместимости с OneBot12 адаптеры ErisPulse для формата API-ответов используют стандарт структуры возвращаемых значений отправки сообщений, определённый в OneBot12.

Однако протокол ErisPulse имеет некоторые особые определения:

    1. Среди базовых полей message_id является обязательным, но в стандарте OneBot12 такого поля нет
    1. В возвращаемое содержимое необходимо добавить поле {platform_name}_raw для хранения исходных данных ответа

2. Базовая структура возвращаемого значения

Все ответы на действия должны содержать следующие базовые поля:

Имя поля Тип данных Обязательное Описание
status string Да Статус выполнения, должен быть "ok" или "failed"
retcode int64 Да Код возврата, следует правилам кодов возврата OneBot12
data any Да Данные ответа; при успехе содержит результат запроса, при неудаче — null
message_id string Да Идентификатор сообщения; если отсутствует — пустая строка
message string Да Сообщение об ошибке; при успехе — пустая строка
{platform_name}_raw any Нет Исходные данные ответа

Необязательные поля:

Имя поля Тип данных Обязательное Описание
echo string Нет Если запрос содержит поле echo, оно возвращается в неизменном виде

  1. Все ответы должны содержать поля status, retcode, data и message
  2. Если запрос содержит непустое поле echo, ответ должен содержать поле echo с тем же значением
  3. Коды возврата должны строго следовать спецификации OneBot12
  4. Сообщения об ошибках (message) должны быть понятны человеку

5. Расширения спецификации

ErisPulse сделал следующие расширения поверх стандартной структуры возвращаемых значений OneBot12:

5.1 Обязательное поле message_id

В стандарте OneBot12 message_id находится внутри объекта data и не является обязательным. ErisPulse поднял его до обязательного поля верхнего уровня:

  • Если message_id недоступен, следует установить пустую строку ""
  • message_id присутствует всегда, модулям не нужно выполнять проверку на null

5.2 Поле исходного ответа {platform}_raw

Возвращаемое значение должно содержать поле {platform}_raw, в котором хранится полная копия исходных данных ответа платформы:

{
    "status": "ok",
    "retcode": 0,
    "data": {"message_id": "1234", "time": 1632847927},
    "message_id": "1234",
    "message": "",
    "telegram_raw": {
        "ok": true,
        "result": {"message_id": 1234, "date": 1632847927, ...}
    }
}

Требования:

  • {platform}_raw должен быть глубокой копией исходного ответа, а не ссылкой
  • platform должен полностью совпадать с именем платформы, указанным при регистрации адаптера (с учётом регистра)
  • Информация об ошибках в исходном ответе также должна сохраняться для удобства отладки

5.3 Расширенные коды возврата фреймворка (пользовательские три младших разряда сегмента ошибок платформы 34xxx)

Спецификация OneBot12 позволяет реализациям определять собственные значения трёх младших разрядов 3xxxx. Семантика 34xxx — Platform Error (ошибка платформы бота, например сбой из-за ограничений платформы). Внутри 34xxx используется послойно по зонам ответственности:

Сегмент (младшие три разряда) Принадлежность Назначение
340xx Реализация адаптера Семейство операций запросов (Request Not Found / Already Handled / Not Supported / Permission Denied, см. request-action-spec §7)
341xx–345xx Реализация адаптера Ошибки на стороне платформы: права доступа / антифрод / ограничения аккаунта и т. п. (младшие три разряда определяются реализацией, исходная ошибка помещается в {platform}_raw)
346xx Фреймворк ErisPulse (зарезервировано) Перехваты самим фреймворком и общие сбои; адаптерам/модулям не занимать
347xx–349xx Реализация адаптера Прочие ошибки выполнения на стороне платформы

Коды 346xx, используемые в настоящее время фреймворком ErisPulse:

Код ошибки Название ошибки Описание
34600 SDK Failure Общий сбой фреймворка (код возврата по умолчанию для make_error())
34601 Action Denied Исходящее действие отключено скоупом (scope.actions); вызов не инициируется, сразу возвращается этот ответ

Разграничение ответственности: 34601 — это перехват фреймворком до вызова (модуль вообще не имеет права инициировать действие); коды платформы 34004 / 34xxx — это действие отправлено, но отклонено платформой (например, у бота нет прав, сработал антифрод). При диагностике проблем с правами модули должны проверять оба случая: сначала 34601 (свой модуль отключён скоупом), затем 34xxx (ограничения на стороне платформы).

Структура возврата — стандартный ответ с ошибкой из §2:

{
    "status": "failed",
    "retcode": 34601,
    "data": null,
    "message_id": "",
    "message": "action 'send' denied by scope.actions"
}

5.4 Контрольный список для реализации адаптера

  • Содержит поля status, retcode, data, message_id, message
  • Коды возврата следуют спецификации OneBot12 (подробнее см. §3.2)
  • message_id присутствует всегда (пустая строка, если недоступен)
  • {platform}_raw содержит исходные данные ответа платформы

6. Примечания

  • Для кодов ошибок 3xxxx три младших разряда могут определяться реализацией самостоятельно

  • 34600 / 34601 зарезервированы фреймворком ErisPulse (см. §5.3), адаптерам/модулям следует их не использовать

1. Обзор

Событие запроса (type: "request") — это специальный тип события, определенный в OneBot12, представляющий запрос, требующий принятия решения ботом (например, запрос на добавление в друзья, приглашение в группу и т.д.).

В отличие от событий сообщений, события запроса требуют двустороннего взаимодействия:

  1. Получение: адаптер преобразует оригинальные запросы платформы в стандартные события запроса
  2. Ответ: модуль выполняет операции с помощью DSL запроса или Event.approve()/Event.reject()
Оригинальное событие запроса платформы
    │
    ▼
Converter.convert()        ← Реализация адаптера (прямое преобразование)
    │
    ▼
Стандартное событие запроса (с request_id)
    │
    ├─→ Обработчик модуля @request.on_friend_request()
    │       │

2. Требования к полям события запроса

2.1 Стандартные поля

Событие запроса должно содержать обязательные поля стандарта OneBot12, а также следующие поля:

Поле Тип Обязательно Описание
request_id string Рекомендуется Идентификатор запроса, используется для одобрения/отклонения
user_id string Да ID пользователя, отправившего запрос
user_nickname string Нет Никнейм пользователя, отправившего запрос
comment string Нет Комментарий к запросу

2.2 Поле request_id

request_id — это ключевой идентификатор запроса:

  • Назначение: идентифицирует запрос, который можно обработать, используется в DSL запроса
  • Правила генерации:
    • Предпочтительно использовать оригинальный идентификатор запроса платформы (например, поле flag OneBot11, chat_invite_link Telegram и т.д.)
    • Если платформа не предоставляет оригинального идентификатора запроса, адаптер должен сгенерировать уникальный идентификатор (рекомендуемый формат: {platform}_{timestamp}_{user_id})
  • Уникальность: должен быть уникален в пределах одной платформы
  • Поведение при отсутствии: если request_id отсутствует, event.approve() / event.reject() выбросят ValueError

3. DSL запросов

3.1 Цепочечные вызовы

Request предоставляет интерфейс цепочечных вызовов, аналогичный Send:

# Основное использование
await adapter.Request("req_id").accept()
await adapter.Request("req_id").reject()

# Указание учетной записи бота
await adapter.Request("req_id").Using("bot1").accept()

# С комментарием (через kwargs)
await adapter.Request("req_id").accept(comment="Добро пожаловать")
await adapter.Request("req_id").reject(comment="Пока не добавляю в друзья")

# Комбинированное использование
await adapter.Request("req_id").Using("bot1").accept(comment="Добро пожаловать")

Операция возвращает стандартный формат ответа API:

Успешно:

    "retcode": 0,

    "message_id": "",
    "message": ""

Неудачно:

5. Требования к реализации адаптера

5.1 Требования к конвертеру

Конвертер адаптера при преобразовании событий запроса должен правильно устанавливать поле request_id:

def convert_request_event(self, raw_event: dict) -> dict:
    """Преобразование оригинального события запроса платформы"""
    return {
        "id": self._generate_event_id(raw_event),
        "time": int(time.time()),
        "type": "request",
        "detail_type": self._map_request_type(raw_event),  # "friend" или "group"
        "platform": self._platform_name,
        "self": {
            "platform": self._platform_name,
            "user_id": str(self._bot_id),
        },
        "user_id": str(raw_event.get("user_id", "")),
        "user_nickname": raw_event.get("nickname", ""),
        "comment": raw_event.get("message", ""),
        "request_id": self._extract_request_id(raw_event),  # ← Ключевое поле
        f"{self._platform_name}_raw": raw_event,
        f"{self._platform_name}_raw_type": raw_event.get("type", ""),
    }

def _extract_request_id(self, raw_event: dict) -> str:
    """
    Извлечение идентификатора запроса из оригинального события платформы
    
    Предпочтительно использовать оригинальный идентификатор платформы, если нет, генерируем уникальный ID
    """
    # Предпочтительно использовать оригинальный идентификатор платформы
    if flag := raw_event.get("flag"):
        return str(flag)
    if request_key := raw_event.get("request_key"):
        return str(request_key)
    
    # Резервное: генерируем уникальный ID
    import hashlib
    raw = f"{self._platform_name}_{raw_event.get('user_id')}_{raw_event.get('timestamp')}"
    return hashlib.md5(raw.encode()).hexdigest()

5.2 Реализация внутреннего класса Request

Адаптер переопределяет accept и reject в внутреннем классе Request:

from ErisPulse.Core import BaseAdapter, RequestDSL

class MyAdapter(BaseAdapter):
    
    class Request(RequestDSL):
        """Реализация операций запроса для MyPlatform"""
        
        def accept(self, **kwargs):
            """
            Одобрение запроса
            
            :param kwargs: Дополнительные параметры, например comment="Комментарий"
            :return: asyncio.Task
            """
            async def _do():
                try:
                    result = await self._adapter.call_api(
                        endpoint="/set_request",
                        request_id=self._request_id,
                        approve=True,
                        **kwargs,
                    )
                    return {
                        "status": "ok" if result.get("code") == 0 else "failed",
                        "retcode": result.get("code", 0),
                        "data": None,
                        "message_id": "",
                        "message": result.get("message", ""),
                    }
                except Exception as e:
                    return {
                        "status": "failed",
                        "retcode": 34001,
                        "data": None,
                        "message_id": "",
                        "message": f"Операция запроса не удалась: {e}",
                    }
            
            return self._create_task(_do())
        
        def reject(self, **kwargs):
            """Отклонение запроса"""
            async def _do():
                try:
                    result = await self._adapter.call_api(
                        endpoint="/set_request",
                        request_id=self._request_id,
                        approve=False,
                        **kwargs,
                    )
                    return {
                        "status": "ok" if result.get("code") == 0 else "failed",
                        "retcode": result.get("code", 0),
                        "data": None,
                        "message_id": "",
                        "message": result.get("message", ""),
                    }
                except Exception as e:
                    return {
                        "status": "failed",
                        "retcode": 34001,
                        "data": None,
                        "message_id": "",
                        "message": f"Операция запроса не удалась: {e}",
                    }
            
            return self._create_task(_do())

5.3 Платформа не поддерживает операции запроса

Если платформа не поддерживает запросы на добавление в друзья/приглашения в группы (например, некоторые платформы обрабатывают запросы автоматически), адаптер может:

  1. Не переопределять внутренний класс Request: использовать реализацию по умолчанию базового класса, вызов accept()/reject() вернёт retcode=10002
  2. Не генерировать request_id при преобразовании: не генерировать request_id, чтобы event.approve() выбросил ValueError
  3. Записывать логи: в accept/reject записывать предупреждения и возвращать соответствующий код ошибки

5.4 Итог: Send и Request параллельны

Адаптер имеет два параллельных внутренних класса DSL, каждый с собственной функцией:

BaseAdapter
├── Send(SendDSL)     ← Отправка сообщений
│   ├── Raw_ob12()    ← Обязательно реализовать
│   ├── Text()        ← Рекомендуется реализовать
│   └── Image()       ← Реализовать по необходимости
│
└── Request(RequestDSL) ← Операции запроса
    ├── accept()        ← Реализовать по необходимости
    └── reject()        ← Реализовать по необходимости

5.5 Примечания к __init__ адаптера

При переопределении __init__ внутреннего класса Request необходимо передавать параметры и вызывать super().__init__(), подробнее см. Введение в разработку адаптеров - Примечания к __init__ (Request аналогично, параметры: adapter, request_id, account_id).

6. Проверочный список реализации адаптера

Основные требования

  • Если переопределяется __init__, вызван super().__init__() (убедитесь, что инициализированы фабрики Send / Request)

Преобразование запроса

  • Событие запроса содержит поле request_id (рекомендуется)
  • detail_type корректно отображается в "friend" или "group"
  • Сохранены оригинальные данные платформы в поле {platform}_raw
  • Правила генерации request_id описаны в документации

Операции запроса

  • Внутренний класс Request реализован (если платформа поддерживает операции запроса)
  • Метод accept() реализован
  • Метод reject() реализован
  • Операции возвращают стандартный формат ответа API
  • Операции, которые платформа не поддерживает, возвращают retcode=10002
  • Ошибки сети возвращают retcode=33xxx (следуя стандарту ответов API)

7. Расширение кодов ошибок

Рекомендуемые коды ошибок адаптера/платформы, связанные с операциями запроса (следуя стандарту ответов API §3.2, в диапазоне 34xxx с самыми низкими тремя цифрами для пользовательских определений):

Код ошибки Название ошибки Описание
34001 Request Not Found Запрос не существует или просрочен
34002 Request Already Handled Запрос уже обработан
34003 Request Not Supported Платформа не поддерживает данную операцию запроса
34004 Permission Denied Бот не имеет прав обрабатывать этот запрос (возвращается платформой)

Граница с кодами фреймворка: вышеуказанные 340xx — это ошибки, возвращаемые платформой/адаптером при обработке запроса; фреймворк ErisPulse, отключая действие request для модуля в scope.actions, до вызова адаптера напрямую возвращает 34601 (Action Denied, см. стандарт ответов API §5.3), эти два типа ошибок не заменяют друг друга: сначала проходит фреймворк 34601, затем платформа 340xx.
