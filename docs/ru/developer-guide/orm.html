Слой моделей данных (ORM)

Tip

Когда стоит читать этот документ: если нужны модели данных, автоматическое создание таблиц или связи между моделями. Если нет — можно пропустить, это не влияет на использование остальных функций.

Note

ORM асинхронен по своей природе: все CRUD-методы (create / get / save / delete / create_table / терминальные операции QuerySet) являются async def и вызываются через await прямо в цикле событий — в качестве нижележащих драйверов используются aiosqlite / aiomysql / asyncpg (переключаются вместе с бэкендом хранилища), синхронной блокировки нет. Синхронные get/set KV-хранилища — это слой совместимости, к ORM отношения не имеющий.

Начиная с версии 2.9.0 во фреймворк встроен декларативный слой моделей данных: достаточно унаследовать Model и объявить поля через Field, чтобы получить автоматическое создание таблиц и полный набор CRUD-возможностей. Модели построены непосредственно на встроенном слое хранилища — SQLite / MySQL / PostgreSQL определяется конфигурацией ErisPulse.storage.backend; при переключении бэкенда код моделей менять не нужно.

Объявление моделей

from ErisPulse.Core.Bases import Model, Field

class User(Model):
    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0, ge=0, le=150)
    role: str = Field(default="user", choices=["user", "admin"])
    tags: list = Field(default_factory=list)          # JSON-столбец, сериализуется автоматически при чтении/записи
    bio: str = Field(default="", description={"i18n": "user.bio", "default": "О себе"})
  • Имя таблицы по умолчанию — snake_case от имени класса (UserProfile → user_profile); можно переопределить через __tablename__ = "xxx"
  • Набор ключей ограничений у Field совпадает с декларативными классами конфигурации (choices / ge / le / max_length; description тоже поддерживает i18n-словарь); движок валидации — тот же, что и у валидации конфигурации

Параметры полей

Параметр Описание
default Значение по умолчанию (если не задано и не автоинкремент → обязательное NOT NULL)
default_factory Фабрика изменяемого значения по умолчанию (например, list)
primary_key Первичный ключ (несколько полей — составной первичный ключ, сводится к табличному PRIMARY KEY (a, b))
autoincrement Автоинкрементный первичный ключ (подразумевает первичный ключ, после create значение проставляется автоматически; только для одноколоночного первичного ключа, несовместим с составным)
max_length Максимальная длина строки (генерирует VARCHAR(n), валидация при записи)
nullable Допускается ли NULL (по умолчанию False)
index Создаёт обычный индекс
unique Ограничение уникальности
choices / ge / le Перечисление / числовой диапазон (валидация при записи)
description Описание (i18n-словарь, тот же формат, что у классов конфигурации)
column_type Переопределяет SQL-определение типа столбца
foreign_key Ограничение внешнего ключа на уровне столбца ("таблица.столбец", генерирует REFERENCES)
on_delete Действие при удалении по внешнему ключу: CASCADE / SET NULL / RESTRICT / NO ACTION / SET DEFAULT
auto_now_add Автоматически записывает текущую метку времени при вставке (float-секунды с начала эпохи)
auto_now Записывается автоматически и при вставке, и при обновлении через save() экземпляра (массовый путь QuerySet.update не срабатывает)

Составной первичный ключ и совместная уникальность

Несколько полей с primary_key=True образуют составной первичный ключ; get / save / delete находят строку по всем столбцам первичного ключа; __unique_together__ объявляет группы совместной уникальности (их может быть несколько):

class Membership(Model):
    __tablename__ = "memberships"
    __unique_together__ = (("user_id", "group_id"),)

    user_id: int = Field(primary_key=True)
    group_id: int = Field(primary_key=True)
    role: str = Field(default="member")

m = await Membership.get(user_id=1, group_id=2)
  • autoincrement несовместим с составным первичным ключом; при их совместном использовании определение модели сразу приводит к ошибке
  • __unique_together__ реализуется через уникальный индекс (имена индексов с префиксом uq_): у новых таблиц создаётся вместе с таблицей, у уже существующих таблиц автоматически достраивается при вызове create_table(), пересоздание не требуется
  • Модели с составным первичным ключом пока не поддерживают связи между моделями (has-many / belongs-to); при обращении через экземпляр выдаётся явная ошибка

Создание таблиц и CRUD

await User.create_table()                      # идемпотентно (IF NOT EXISTS)

user = await User.create(name="Alice", age=20) # вставка (автоинкрементный первичный ключ проставляется автоматически)
got = await User.get(id=user.id)               # первая запись по условию равенства

users = await User.where(User.age > 18).order_by("-age").limit(10).all()
first = await User.where(User.name == "Alice").first()
total = await User.count(User.age > 18)

user.age = 21
await user.save()                              # обновление по первичному ключу (сначала валидация ограничений); при отсутствии первичного ключа деградирует до вставки (автоинкрементный ключ тоже проставляется в экземпляр)
await user.save(update_fields=["age"])         # частичное обновление столбцов (белый список, остальные столбцы не записываются)
await user.delete()                            # удаление по первичному ключу

user, created = await User.get_or_create({"age": 20}, name="Alice")      # если найдено — возвращает; если нет — создаёт
user, created = await User.update_or_create({"age": 21}, name="Alice")   # если найдено — обновляет defaults и сохраняет; если нет — создаёт

await User.update_all(User.age > 18, role="adult")  # массовое обновление
await User.delete_all(User.age > 100)               # массовое удаление

Note

В условиях конкурентной гонки две сопрограммы в get_or_create / update_or_create могут одновременно дойти до ветки создания — ограничение уникальности (первичный ключ / unique / __unique_together__) приведёт к тому, что «пришедшая позже» получит StorageOperationError; если нужна идемпотентная семантика, перехватите исключение и выполните повторный запрос.

Выражения запросов поддерживают > >= < <= == !=, а также комбинации через & (И) / | (ИЛИ); для условия IN используется where_in:

await User.where(User.age > 18).all()
await User.where_in("name", ["Alice", "Bob"]).all()                       # условие IN (дружелюбно к проверке типов)
await User.where((User.age > 18) & User.name.in_(["Alice", "Bob"])).all() # IN в комбинации с другими условиями (in_ — рантайм-возможность)

Tip

Дружелюбно к проверке типов: если поля объявлены с аннотациями типов значений (age: int = Field(...)), то сравнение через доступ к атрибуту класса (User.age > 18) с точки зрения mypy / pyright / ty является bool, хотя в рантайме реально создаётся объект условия — точки входа условий (where / count / delete_all / update_all) уже совместимы с такой формой, поэтому в местах вызова не требуется никаких комментариев ignore; настоящие булевы значения на входе (их невозможно скомпилировать в SQL) явно отклоняются в рантайме. Возвращаемые значения запросов статически типизированы: результат first() / all() / get() / create() — это экземпляры модели, доступ к полям снабжён полными подсказками типов.

Объекты условий нельзя использовать в булевом контексте (if User.age > 18: вызовет ошибку); для комбинирования нескольких условий используйте & / |, а не and / or. Для возвращаемого типа вспомогательных функций построения условий рекомендуется аннотация Condition | bool.

Транзакции

Чтение и запись ORM используют с уровнем хранилища фреймворка общий механизм маршрутизации транзакций: внутри объемлющей транзакции storage.atransaction() методы create / save / delete и запросы автоматически переиспользуют транзакционное соединение; фиксация или откат выполняются единообразно вместе с транзакцией, самостоятельного коммита не происходит.

async with storage.atransaction():
    await User.create(name="Alice")
    ...  # при исключении внутри блока выполненный выше INSERT тоже откатится

Связь с декларативными классами конфигурации

Объявления моделей и ConfigClass (@dataclass + field(metadata=...)) разделяют одну и ту же основу — набор ключей ограничений, движок валидации (validate_field_constraints), реестр категорий типов (python_type_category); однако базовые классы намеренно разделены: поля конфигурации — это обычные значения (TOML round-trip, горячее обновление после одноразовой загрузки), а поля моделей — дескрипторы столбцов (доступ к классу = выражение запроса, экземпляры построчные). Один синтаксис объявления — два фундамента, каждый со своей ролью.

Когда какое объявление использовать

Аспект Класс конфигурации field(metadata=...) Поле модели Field()
Сценарий применения Параметры поведения модуля (немногочисленные, человекочитаемые, требуют горячего обновления) Записи бизнес-данных (много строк, программная запись и чтение, требуют запросов)
Форма хранения config.toml (с сохранением комментариев, TOML round-trip) Таблица базы данных (автосоздание таблиц, SQL-диалекты)
Форма значений Обычные значения (прямое чтение атрибутов dataclass) Дескрипторы (доступ к классу = выражение столбца, доступ к экземпляру = значение строки)
Объявление ограничений metadata={"choices": ..., "min": ..., "max": ...} Field(choices=..., ge=..., le=..., max_length=...)
Общая основа Движок валидации + набор ключей ограничений + реестр категорий типов (единый набор) То же

Эмпирическое правило: «как работает модуль» — используйте класс конфигурации, «какие данные создал пользователь» — используйте модель.

Границы и важные замечания

  • Бэкенд определяется глобальной конфигурацией хранилища; модель может через атрибут класса __storage__ переопределить его на собственный экземпляр SQL-бэкенда хранилища (SQLStorageBase, используется для инъекции в тестах)
  • Поля list / dict (включая параметризованные дженерики вроде list[int], dict[str, int]) хранятся по категории контейнера в JSON-текстовых столбцах, сериализация при чтении/записи автоматическая
  • Перед записью (create / save) автоматически выполняется валидация ограничений; при неудаче выбрасывается ValueError (локализованное сообщение)
  • Автоматическая миграция покрывает сценарий добавления столбцов (см. ниже); изменение типа столбца и удаление столбцов требуют ручной обработки
  • Поведение при сбое соединения с хранилищем совпадает со слоем хранилища: фреймворк не падает, после периода cooldown выполняется автоматическое переподключение

Автоматическая миграция (этап 2)

create_table() при уже существующей таблице автоматически сравнивает её столбцы с полями модели: для новых полей автоматически выполняется ALTER TABLE ADD COLUMN (у мигрируемых столбцов ограничение NOT NULL убирается, существующие строки получают NULL), для новых полей с объявленным index=True синхронно создаётся индекс. Писать скрипты миграции вручную не нужно.

# эволюция модели после запуска v1: добавлены поля email / bio
class User(Model):
    __tablename__ = "orm_users"

    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)
    age: int = Field(default=0)
    email: str = Field(default="")     # новое: при следующем create_table() выполнится автоматический ADD COLUMN
    bio: str = Field(default="")

await User.create_table()              # идемпотентно: мигрируются только новые столбцы

Границы: поддерживается только добавление столбцов; изменение первичного ключа, изменение типа столбца и удаление столбцов требуют ручной обработки (во избежание случайных разрушительных операций ALTER).

Внешние ключи (основа связей между моделями)

foreign_key="таблица.столбец" объявляет ограничение внешнего ключа на уровне столбца, DDL генерирует предложение REFERENCES; on_delete объявляет действие при удалении (например, "CASCADE" — каскадное удаление ссылающихся строк):

class Post(Model):
    __tablename__ = "posts"

    id: int = Field(primary_key=True, autoincrement=True)
    author: int = Field(foreign_key="orm_users.id", on_delete="CASCADE")

    content: str = Field(max_length=255)

Связи между моделями (relationship)

relationship() объявляется как атрибут класса в теле класса модели; направление определяется автоматически в зависимости от того, в какой таблице объявлен столбец внешнего ключа:

from ErisPulse.Core.Bases import Model, Field, relationship

class User(Model):
    __tablename__ = "orm_users"

    id: int = Field(primary_key=True, autoincrement=True)
    name: str = Field(max_length=64)

    posts = relationship("Post", foreign_key="author")   # внешний ключ в таблице другой стороны → has-many

class Post(Model):
    __tablename__ = "posts"

    id: int = Field(primary_key=True, autoincrement=True)
    author: int = Field(foreign_key="orm_users.id")
    content: str = Field(max_length=255)

    writer = relationship("User", foreign_key="author")  # внешний ключ в собственной таблице → belongs-to

has-many: атрибут экземпляра возвращает queryset; доступны все цепочные возможности QuerySet, create автоматически проставляет первичный ключ этой таблицы в столбец внешнего ключа другой стороны:

alice = await User.get(name="Alice")

posts = await alice.posts.all()                          # все статьи этого пользователя
latest = await alice.posts.order_by("-id").first()
total = await alice.posts.count()
hot = await alice.posts.where(Post.content != "").all()  # добавление условия по полю таблицы другой стороны
await alice.posts.delete()                               # удаляются только статьи этого пользователя

new_post = await alice.posts.create(content="hi")        # author автоматически = alice.id

belongs-to: await напрямую возвращает экземпляр другой стороны (при отсутствии совпадения или NULL во внешнем ключе возвращается None):

post = await Post.get(id=1)
writer = await post.writer          # экземпляр User или None
await writer.posts.count()          # навигация работает в обе стороны

Ключевые моменты:

  • в related передаётся строка с именем класса (разрешается лениво через реестр имён классов моделей, порядок объявления сторон не важен) либо сам класс модели
  • запрос связи и модель другой стороны используют каждый свой бэкенд хранилища (JOIN между разными бэкендами не поддерживается — запрос связи выполняется как два независимых SQL)
  • запросы связей не кэшируются: каждое обращение — немедленный запрос; для произвольных пользовательских запросов по-прежнему можно использовать User.where(...)
