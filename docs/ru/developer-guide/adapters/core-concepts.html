Основные концепции адаптера

Tip

Когда читать эту статью: Обязательно для разработчиков адаптеров (полное описание основных механизмов: BaseAdapter, SendDSL, жизненного цикла). Если вы только начинаете, сначала прочитайте Введение в разработку адаптеров, вернитесь сюда, когда возникнут вопросы "почему так пишется".

Эта статья объясняет механизм работы адаптера: как Manager адаптеров регистрирует и распределяет события, что делает BaseAdapter при инициализации, как объявляются конфигурации и многоаккаунтность — когда возникают вопросы "почему так пишется", ищите ответы здесь.

Основная симметрия:

  • Прямое преобразование (Converter): платформа: оригинальные события → OneBot12: стандартные события, оригинальные данные сохраняются в {platform}_raw
  • Обратное преобразование (Raw_ob12): OneBot12: сообщение → платформа: API-вызовы, возвращается стандартный формат ответа

AdapterManager (менеджер адаптеров)

AdapterManager — основной компонент системы адаптеров ErisPulse, отвечает за управление всеми платформенными адаптерами, регистрацию, запуск, остановку и распределение событий.

Основные функции

  • Регистрация адаптеров: регистрация и управление несколькими платформенными адаптерами
  • Жизненный цикл: управление запуском и остановкой адаптеров
  • Распределение событий: распределение стандартных событий OneBot12 и оригинальных событий платформы
  • Управление конфигурацией: управление включением/отключением адаптеров
  • Поддержка промежуточных обработчиков: поддержка промежуточных обработчиков событий OneBot12

Основное использование

from ErisPulse import sdk

# Регистрация адаптера (обычно автоматически выполняется Loader)
sdk.adapter.register("myplatform", MyPlatformAdapter)

# Запуск всех адаптеров
await sdk.adapter.startup()

# Запуск указанного адаптера
await sdk.adapter.startup(["myplatform"])
# Запуск всех адаптеров
await sdk.adapter.startup()

# Получение экземпляра адаптера
my_adapter = sdk.adapter.get("myplatform")
# Или через атрибут
my_adapter = sdk.adapter.myplatform

# Остановка всех адаптеров
await sdk.adapter.shutdown()

Запуск и остановка

Запуск адаптера

# Запуск всех зарегистрированных адаптеров
await sdk.adapter.startup()

# Запуск указанной платформы
await sdk.adapter.startup(["platform1", "platform2"])

Процесс запуска:

  1. Выполнение события жизненного цикла adapter.start
  2. Выполнение события adapter.status.change (starting)
  3. Параллельный запуск каждого адаптера
  4. При неудаче автоматическая повторная попытка (стратегия экспоненциального отступления)
  5. При успешном запуске выполнение события adapter.status.change (started)

Механизм повторной попытки:

  • Первые 4 попытки: 60 секунд, 10 минут, 30 минут, 60 минут
  • С пятой попытки и далее: фиксированный интервал 3 часа

Остановка адаптера

# Остановка всех адаптеров
await sdk.adapter.shutdown()

Процесс остановки:

  1. Выполнение события жизненного цикла adapter.stop
  2. Вызов метода shutdown() всех адаптеров
  3. Остановка маршрутизатора
  4. Очистка обработчиков событий
  5. Выполнение события жизненного цикла adapter.stopped

Управление конфигурацией

Проверка статуса платформы

# Проверка, зарегистрирована ли платформа
exists = sdk.adapter.exists("myplatform")

# Проверка, включена ли платформа
enabled = sdk.adapter.is_enabled("myplatform")

Механизм распределения событий

При вызове adapter.emit(event_data):

  1. Обработка промежуточными обработчиками: сначала выполняются все промежуточные обработчики OneBot12
  2. Распределение стандартных событий: распределяются на соответствующие обработчики событий OneBot12
  3. Распределение оригинальных событий: если есть оригинальные данные, распределяются на обработчики оригинальных событий

Правила сопоставления:

  • Точное соответствие: @sdk.adapter.on("message") соответствует только событию message
  • Шаблон: @sdk.adapter.on("*") соответствует всем событиям
  • Фильтрация по платформе: platform="myplatform" распределяет только события указанной платформы

Добавление промежуточного обработчика

@sdk.adapter.middleware
async def logging_middleware(data):
    """Промежуточный обработчик для логирования"""
    print(f"Обработка события: {data.get('type')}")
    return data  # Обязательно возвращать данные

@sdk.adapter.middleware
async def filter_middleware(data):
    """Промежуточный обработчик для фильтрации"""
    # Фильтрация ненужных событий
    if data.get("type") == "notice":
        return None  # Возвращение None означает, что промежуточный обработчик пропускает результат, сохраняя исходные данные для передачи
    return data  # Обязательно возвращать данные для продолжения передачи

Соглашение о возвращаемых значениях промежуточного обработчика

Возвращаемое значение Поведение
dict Изменяет тело события (последующие обработчики получают изменённое событие)
None Пропуск, тело события не изменяется (вывод предупреждения — рекомендуется явно return data)
False Отклонение: событие отбрасывается, не проходит через обработчики, без побочных эффектов

Отклонение используется для брандмауэров, ограничения скорости, чёрных списков и других сценариев "отбрасывания на уровне событий" (ранее можно было реализовать только с помощью обработчиков высокого приоритета). При отклонении фреймворк выводит трассировку и вызывает хук жизненного цикла adapter.event.blocked (с именем промежуточного обработчика middleware, полным event, platform / event_type / detail_type), что полезно для отладки "почему событие не отвечает":

@sdk.adapter.middleware
async def rate_limit_middleware(data):
    """Промежуточный обработчик для ограничения скорости"""
    if _is_rate_limited(data):
        return False  # Отклонение: событие отбрасывается
    data["rate_marked"] = True
    return data

@sdk.lifecycle.on("adapter.event.blocked")
async def on_event_blocked(data):
    print(f"Событие отклонено {data['middleware']}: {data['event_type']}")

Порядок выполнения промежуточных обработчиков

Промежуточные обработчики выполняются в порядке регистрации, последние зарегистрированные обработчики выполняются первыми.

Важно: если промежуточный обработчик возвращает None (например, забыл return data), фреймворк игнорирует это возвращение, сохраняет исходные данные и продолжает передачу, при этом выводит предупреждение. Это гарантирует, что ошибка одного промежуточного обработчика не приведёт к прерыванию всей цепочки событий.

# Регистрация в порядке
sdk.adapter.middleware(middleware1)  # выполняется последним
sdk.adapter.middleware(middleware2)  # выполняется посередине
sdk.adapter.middleware(middleware3)  # выполняется первым

# Порядок выполнения: middleware3 -> middleware2 -> middleware1

Соглашение metadata

Поле metadata служит одновременно для генерации комментариев TOML и рендеринга формы веб-интерфейса:

metadata = {
    "description": str | dict,  # Описание поля (поддержка i18n)
    "required": bool,         # Обязательно ли поле (проверка + метка обязательного поля в веб-интерфейсе)
    "secret": bool,           # Является ли поле секретным (веб-интерфейс отображает как ***, в логах маскируется)
    "example": bool,          # Не сохранять в файле: не записывается в config.toml (исключается из значений по умолчанию и шаблона),
                              # только включается в config.full.example; метка "example": true в схеме,
                              # мастер конфигурации CLI по умолчанию пропускает; после ручного задания пользователем сохраняется нормально
    "min": number, "max": number,  # Проверка диапазона числовых значений
    "ui": {                   # Конфигурация элементов управления веб-интерфейса (старое имя "webui" также поддерживается)
        "widget": str,        # Тип элемента управления: "text" | "switch" | "select" | "number" | "password"
        "group": str,         # Группа: "basic" | "advanced" | "connection" и т.д.
        "order": int,         # Приоритет сортировки (чем меньше, тем ближе)
        "options": list,      # Доступные варианты для элемента select [{label, value}], label поддерживает i18n
        "placeholder": str | dict,  # Подсказка в поле ввода (поддержка i18n)
    },
    "extra": dict,            # Дополнительные расширенные поля (передаются в схему)
}

Все пользовательские видимые текстовые поля поддерживают i18n, используя единый формат {"i18n": "key", "default": "text"}, чистые строки прозрачно передаются (обратная совместимость). Поддерживаемые поля i18n:

Поле Позиция Описание
description metadata поля Описание поля
options[].label ui.options Метка варианта для элемента select
placeholder ui.placeholder Подсказка в поле ввода
group_labels _schema_meta Отображаемое имя группы (заголовок раздела на панели управления)

При использовании i18n необходимо заранее зарегистрировать ключи перевода в системе i18n (см. документацию по i18n).

Примеры description / placeholder / options label:

token: str = field(
    default="",
    metadata={
        "description": {"i18n": "my_adapter.token", "default": "Bot Token"},
        "ui": {
            "widget": "text",
            "placeholder": {"i18n": "my_adapter.token.ph", "default": "Введите Token"},
        },
    },
)
mode: str = field(
    default="a",
    metadata={
        "description": {"i18n": "my_adapter.mode", "default": "Режим"},
        "ui": {
            "widget": "select",
            "options": [
                {"label": {"i18n": "my_adapter.mode.a", "default": "Вариант A"}, "value": "a"},
                {"label": "Чистая строка метки", "value": "b"},  # Чистая строка прозрачно передается
            ],
        },

)

Пример group_labels (объявляется после объявления класса конфигурации):

Фреймворк resolve_config_schema() автоматически разрешает все перечисленные выше поля i18n в зависимости от текущего языка; get_config_schema() прозрачно передает словарь i18n, и интерфейс должен самостоятельно разрешить его.

Автоматическое создание docstring для описания полей (v2.8.0+)

Если в metadata не объявлено description, фреймворк автоматически извлекает описание поля из docstring класса конфигурации в качестве резервного варианта, поддерживая два распространенных стиля (можно использовать вместе):

@dataclass
class MyConfig(BaseConfig):
    """
    Конфигурация MyAdapter

    :ivar endpoint: Адрес API платформы        # Стиль reST
    :ivar timeout: Время ожидания запроса в секундах
    """

    endpoint: str = "https://api.example.com"   # Без metadata description → описание из docstring
    timeout: int = 30

    # Также поддерживается стиль Google (секция Attributes:):
    # Attributes:
    #     endpoint: Адрес API платформы

Приоритет: metadata description > описание поля в docstring > пусто. i18n-словари в description не затрагиваются (всегда имеют приоритет).

Вложенные конфигурации (v2.8.0+)

При типе поля вложенной dataclass фреймворк рекурсивно обрабатывает: схема с "type": "table" + дочерние "fields", веб-интерфейс рендерит как раскрываемую вложенную группу, TOML-шаблон рендерится как [подтаблица] секция, значения по умолчанию / заполнение / проверка / разрешение i18n применяются рекурсивно.

@dataclass
class RetryConfig(BaseConfig):
    """Стратегия повтора

    :ivar max_retries: Максимальное количество повторов
    """
    max_retries: int = 3
    backoff: float = 0.5

@dataclass
class MyConfig(BaseConfig):
    """Конфигурация MyAdapter"""
    endpoint: str = "https://api.example.com"
    retry: RetryConfig = field(default_factory=RetryConfig)   # Вложенный конфигурационный раздел

Сгенерированный TOML-шаблон:

endpoint = "https://api.example.com"

[retry]
# Максимальное количество повторов
max_retries = 3
backoff = 0.5

Вложенные типы рекомендуется использовать с прямым типом; строковые аннотации (для сценариев отложенного вычисления) должны гарантировать, что тип можно разрешить из модуля класса конфигурации, глобального пространства имен или свойства класса по имени.

Не сохраняемое поле example (v2.8.0+)

gc_interval: int = field(default=300, metadata={"example": True})

Поле с example: True:

  • Не записывается в config.toml (шаблон конфигурации адаптера/модуля и значения по умолчанию исключаются, используются значения по умолчанию кода)
  • Отображается только в config.full.example (для справки пользователя, по желанию копируется в config.toml)
  • В схеме помечено "example": true (панель может решить, как отображать), мастер конфигурации CLI по умолчанию пропускает
  • После ручного задания пользователем сохраняется нормально, нормально обновляется (приоритет явного намерения пользователя)

Подходит для "сложных, редко используемых" продвинутых настроек, чтобы сохранить минимальный размер config.toml пользователя.

⚠️ _schema_meta — это метаданные на уровне класса (не поле конфигурации). Если объявить внутри тела dataclass, необходимо добавить аннотацию ClassVar (_schema_meta: ClassVar[dict] = {...}), иначе dataclass будет рассматривать это как обычное поле. Фреймворк защищает поля с подчеркиванием от включения в схему / шаблон / значения по умолчанию / проверку, но рекомендуется соблюдать стандартное объявление.

Декларативные ключи перевода (v2.7.0+)

Адаптер может объявить ключи перевода, подобно ConfigClass, с помощью вложенного класса I18nClass, где можно централизованно объявить ключи перевода. Фреймворк автоматически зарегистрирует все объявленные ключи перевода на этапе __init__ (до генерации шаблона конфигурации), чтобы убедиться, что ключи перевода, используемые в описании конфигурации, доступны при генерации шаблона.

from ErisPulse.Core.Bases import BaseAdapter, BaseI18n, I18nKey

class MyAdapter(BaseAdapter):
    class I18nClass(BaseI18n):
        endpoint: I18nKey = I18nKey(
            default="API Endpoint",
            zh_CN="API адрес",
            zh_TW="API 位址",
            en="API Endpoint",
            ja="APIアドレス",
            ru="API адрес",
        )
        token: I18nKey = I18nKey(
            default="Platform Token",
            zh_CN="平台 Token",
            zh_TW="平台權杖",
            en="Platform Token",
            ja="プラットフォームトークン",
            ru="Токен платформы",
        )

I18nKey.default — это языкозависимый резервный текст, который не регистрируется ни в каком языке. Чтобы перевод заработал, необходимо явно передать хотя бы один параметр языка.

Подробное использование (правила путей ключей, явный параметр key и т.д.) смотрите в документации по i18n.

Декларативное расширение событий (v2.7.0+)

Адаптер может декларативно объявить платформенно-специфические методы расширения событий с помощью EventMixin, фреймворк автоматически регистрирует их в текущей платформе.

from ErisPulse.Core import BaseAdapter

class MyAdapter(BaseAdapter):
    class EventMixin:
        def get_chat_name(self):
            """Получить имя чата"""
            return self.get("myplatform_raw", {}).get("chat", {}).get("name", "")

        def is_official_message(self):
            """Определить, является ли сообщение официальным"""
            raw = self.get("myplatform_raw", {})
            return raw.get("sender", {}).get("is_official", False)

После регистрации методы расширения событий адаптера доступны в событии:

@message.on_group_message()
async def handler(event):
    if event.is_official_message():
        chat_name = event.get_chat_name()
        await event.reply(f"[{chat_name}] Официальное сообщение получено")

Методы расширения событий адаптера регистрируются в его платформе (self._platform). Модули, которым нужны расширения событий на разных платформах, должны использовать существующий API register_event_mixin().

Разрешение аккаунта

При реализации call_api адаптера, необходимо разрешить идентификатор аккаунта в конкретную конфигурацию аккаунта. Фреймворк передает идентификатор привязки аккаунта (результат Using() или автоматическая привязка в цепочке событий) в call_api в виде стандартного поля account_id и автоматически адаптирует его под фактическое потребление адаптера — три формы потребления доступны, фреймворк определяет по имени параметра и константам в теле функции, независимо от позиции параметров:

# Форма 1 (рекомендуемая): объявление стандартного имени в сигнатуре
async def call_api(self, endpoint: str, account_id: str | None = None, **params):
    name, account = self._resolve_account(account_id)
    # name: имя аккаунта, account: экземпляр конфигурации

# Форма 2 (совместимость с существующими): старое имя _account_id, фреймворк автоматически заменяет account_id на старое имя для передачи
async def call_api(self, endpoint: str, _account_id: str | None = None, **params):
    name, account = self._resolve_account(_account_id)

# Форма 3: внутри тела функции из params (обнаруживается константами)
async def call_api(self, endpoint: str, **params):
    account_id = params.pop("account_id", None)
    name, account = self._resolve_account(account_id)

Адаптер, не потребляющий поле аккаунта, фреймворк исключает это поле (чтобы не утекло в параметры платформы) и выводит предупреждение один раз; адаптер с одним аккаунтом может не потреблять (разрешение возвращается к первому включенному аккаунту).

Стратегия разрешения: сопоставление имени аккаунта → сопоставление поля bot_id → сопоставление других строковых полей → первый включенный аккаунт.

Разрешение времени выполнения и сохранение (2.12+): адаптер вызывает self.update_bot_id(account_name, bot_id) при установлении соединения / поступлении события — фреймворк поддерживает таблицу регистрации bot_id → аккаунт (первый приоритет в разрешении цепочки), и при изменении значения записывает accounts.<имя аккаунта>.bot_id в хранилище конфигурации: после перезапуска восстановление экземпляра аккаунта происходит с собственным bot_id, вторая учетная запись и т.д. сценарии разрешения больше не зависят от заполнения во время перезапуска (устранение окна перезапуска).

Повторный приём через разные аккаунты (поля, внедряемые фреймворком)

Когда несколько аккаунтов мультиаккаунтного адаптера находятся в одной группе/беседе, одно и то же физическое сообщение приходит поочерёдно через каждый аккаунт. При ErisPulse.framework.cross_account_policy != "off" фреймворк автоматически выполняет связывание на уровне содержимого (та же платформа + та же беседа + тот же отправитель + тот же alt_message в пределах короткого окна), участие адаптера не требуется:

  • mark: в последующие копии внедряется поле верхнего уровня "multi_receipt": {"event_id": id первого принятого события, "self_id": первый принявший аккаунт}, после чего они распределяются как обычно; модуль читает это поле и принимает решение самостоятельно
  • drop: последующие копии отбрасываются прямо на входе распределения
  • Льгота для at-упоминаний: копии, у которых цель mention в сегменте message совпадает с собственной идентичностью принимающего аккаунта (self.user_id / self.account_id), не участвуют в связывании (освобождаются как от mark, так и от drop) — упомянутый аккаунт гарантированно получает своё событие, и drop не заденет @-управляемые мультиаккаунтные модули; @-сообщение может быть распределено по одному разу через несколько аккаунтов, а @-управляемые модули с условием on_at_message естественно отвечают только один раз

Привязка бесед к аккаунтам (точное объявление принадлежности)

Связывание на уровне содержимого эвристически определяет «кто пришёл первым, тот и выиграл»; когда требуется точно объявить принадлежность беседы, используйте конфигурацию ErisPulse.framework.session_accounts, чтобы привязать беседу к единственному аккаунту:

[ErisPulse.framework.session_accounts.snowluma]
"group:643319481" = "1325859446"   # рекомендуемый префиксный ключ: тип_беседы:ID_беседы → bot_id аккаунта-владельца
"643319481" = "1325859446"         # совместимая запись с «голым» ключом: соответствует всем типам бесед с данным ID беседы

Префиксный ключ изолирует беседы разных типов с одинаковым числовым значением (группа group:123 и личный чат user:123 не влияют друг на друга); «голый» ключ — это совместимая запись, после привязки групповые чаты и личные чаты с данным ID беседы привязываются совместно.

  • Привязка действует независимо от cross_account_policy (настройка привязки равносильна включению дедупликации для этой беседы): события аккаунта-владельца распределяются как обычно, копии от других аккаунтов отбрасываются на входе распределения
  • Льгота для at-упоминаний также действует: копии не-владельческих аккаунтов, упомянутые через @, по-прежнему пропускаются
  • Привязка читает конфигурацию в реальном времени, горячее обновление вступает в силу; беседы без настроенной привязки полностью не затрагиваются
  • Подходит для развёртываний «одна беседа, несколько аккаунтов, отвечать должен только один аккаунт»: точнее связывания на уровне содержимого, без эвристических погрешностей 3-секундного окна и сравнения содержимого

multi_receipt — необязательное поле, внедряемое фреймворком; Converter адаптера его не создаёт и не потребляет; при политике по умолчанию off структура события полностью соответствует существующему контракту.

Разделение обязанностей трёх уровней дедупликации

Механизм Конфигурация Что перехватывает Критерий определения
Идемпотентная дедупликация событий ErisPulse.framework.event_dedupe (включена по умолчанию) Повторная отправка того же id события при переподключении (то же соединение) id события
Фильтрация эха собственного аккаунта ErisPulse.event.message.ignore_self (включена по умолчанию) Сообщения самого принимающего аккаунта (отправитель == принимающий аккаунт) self.user_id vs user_id
Повторный приём через разные аккаунты ErisPulse.framework.cross_account_policy (по умолчанию off, включается drop) Копии одного и того же физического сообщения через другие аккаунты — когда несколько аккаунтов в одной группе, bot A говорит, и bot B тоже получает копию (копии, где mention совпадает с данным аккаунтом, освобождены) Связывание на уровне содержимого (та же платформа + та же беседа + тот же отправитель + то же содержимое, короткое окно), ключ не содержит self_id

Типичный сценарий — повторение сообщения несколькими аккаунтами одной группы: bot A говорит, другие аккаунты той же группы (bot B) тоже получают копию, и модули повторения видят одно и то же содержимое дважды. После включения cross_account_policy = "drop" копии последующих аккаунтов отбрасываются на входе распределения, и любой модуль видит содержимое не более одного раза. Исключение: at-упоминания — копии упомянутых через @ аккаунтов всегда пропускаются (@-управляемые модули зависят от них для отклика), остальные копии аккаунтов дедуплицируются как обычно.

Семантика ignore_self ортогональна; комбинация обеих настроек определяет число видимых появлений:

Комбинация Сколько раз модуль повторения видит сообщение bot A
drop + ignore_self = true (по умолчанию) 0 или 1 раз (если первая прибывшая копия пришла через собственное соединение A, она перехватывается ignore_self) — никогда не 2 раза
drop + ignore_self = false Ровно 1 раз всегда

Не рекомендуется расширять семантику ignore_self до «исключать все аккаунты данной машины»: эта проверка зависит от self.user_id принимаемого события (в период окна, когда привязка ещё не установлена, она перестаёт работать — см. выше «Идентификация во время выполнения и персистентность»), тогда как связывание между аккаунтами — это проверка на уровне содержимого, не зависящая от информации self; кроме того, «приём по каждому аккаунту» — устоявшаяся зависимость модулей кросс-аккаунтных логов / синхронизации, а сужение семантики является неявным нарушением. Дедупликацию между аккаунтами оставьте cross_account_policy.

class MyPlatformConverter:
    def convert(self, raw_event):
        """Преобразует нативное событие платформы в стандартный формат OneBot12"""
        if not isinstance(raw_event, dict):
            return None
        
        # Генерация ID события
        event_id = raw_event.get("event_id") or str(uuid.uuid4())
        
        # Преобразование метки времени
        timestamp = raw_event.get("timestamp")
        if timestamp and timestamp > 10**12:
            timestamp = int(timestamp / 1000)
        else:
            timestamp = int(timestamp) if timestamp else int(time.time())
        
        # Преобразование типа события
        event_type = self._convert_type(raw_event.get("type"))
        detail_type = self._convert_detail_type(raw_event)
        
        # Построение стандартного события
        onebot_event = {
            "id": str(event_id),
            "time": timestamp,
            "type": event_type,
            "detail_type": detail_type,
            "platform": "myplatform",
            "self": {
                "platform": "myplatform",
                "user_id": str(raw_event.get("bot_id", ""))
            },
            "myplatform_raw": raw_event,
            "myplatform_raw_type": raw_event.get("type", "")
        }
        
        return onebot_event

Управление подключениями

Два правильных способа реализации start()

Адаптеры с клиентским режимом (WebSocket-клиент, HTTP-опрос и т.д.) должны запускать постоянный цикл подключения в start(). Фреймворк поддерживает два способа, оба правильны, но можно выбрать только один:

Способ 1: spawn-возвращающий (рекомендуется) — через spawn_client_loop() запускается цикл в фоновом режиме, связанный с платформой, start() немедленно возвращает:

class MyAdapter(BaseAdapter):
    async def start(self):
        # Задача цикла принадлежит self._platform: фреймворк автоматически отменяет при shutdown
        self.spawn_client_loop(self._connect_loop())
        # start() завершается здесь — "запуск успешен", подключение не удалось — цикл внутри повторяет

    async def _connect_loop(self):
        while True:
            try:
                await self._connect_and_receive()   # разрыв исключения → ниже задержка
            except asyncio.CancelledError:
                raise
            except Exception:
                await asyncio.sleep(5)              # цикл внутри сам обрабатывает задержку и повторное подключение

Способ 2: постоянный цикл — start() напрямую await цикл подключения, он никогда не возвращается:

class MyAdapter(BaseAdapter):
    async def start(self):
        await self._connect_loop()   # постоянный цикл не возвращается; исключение — ошибка start()

Различия и общие черты двух способов:

spawn-возвращающий Постоянный цикл
Время возврата start() После запуска цикла немедленно возвращается После выхода/ошибки цикла (фреймворк по стратегии повтора)
Обработка ошибок подключения Цикл внутри сам обрабатывает задержку Исключение всплывает, фреймворк обрабатывает цепочку повтора
Сценарии применения Нужно быстро вернуть подтверждение запуска (множественные подключения, регистрация маршрутов, затем запуск других задач) "Запуск = подключение" семантика простой реализации

spawn_client_loop(coro, *, name="client_loop") — это точка входа для способа 1: задача регистрируется с принадлежностью self._platform, фреймворк автоматически отменяет при shutdown() адаптера, без необходимости самостоятельно управлять дескрипторами задачи; неперехваченные исключения в цикле автоматически фиксируются (ожидаемые разрывы подключения и повторное подключение следует обрабатывать внутри цикла).

Единственный неправильный способ — смешивание: spawn после await того же цикла — это заставит start() потерять семантику немедленного возврата, путь отмены задачи станет непредсказуемым.

Базовые классы для режимов подключения

В дополнение к двум предыдущим способам, наиболее распространённые режимы подключения фреймворк предоставляет наполовину готовыми базовыми классами (в ErisPulse.Core.Bases.adapter_patterns, корневой пакет можно импортировать напрямую): start / shutdown жизненный цикл полностью реализован базовым классом, подкласс реализует только методы обратного вызова бизнес-логики.

PollingAdapter (HTTP-опрос)

Подходит для платформ, где клиент периодически запрашивает события (типа Telegram getUpdates). Базовый класс с помощью spawn-возвращающего запускает постоянный цикл опроса, неудача при получении данных автоматически фиксируется и экспоненциально отступает (база 1 секунда, максимум 60 секунд, после успеха сбрасывается; константы POLLING_ADAPTER_BACKOFF_BASE_SECS / POLLING_ADAPTER_BACKOFF_MAX_SECS можно настроить в Core/constants.py):

from ErisPulse import PollingAdapter

class MyAdapter(PollingAdapter):

    poll_interval = 5.0

    async def fetch_events(self):
        """Получить пакет оригинальных событий платформы (ошибки обрабатываются базовым классом, не нужно try/except)"""
        resp = await self.sdk.client.get(f"{self.cfg.endpoint}/getUpdates")
        data = await resp.json()
        return data.get("result", [])

    def convert_one(self, raw):
        """Преобразование одного оригинального события в OneBot12; возвращает None для пропуска"""
        return self.converter.convert(raw)

    async def call_api(self, endpoint: str, **params):
        ...  # Тот же, что и для обычного адаптера

Минимальный набор: fetch_events / convert_one / call_api. start() запускает цикл и немедленно возвращает; shutdown() не требует реализации в подклассе (цикл опроса автоматически отменяется по принадлежности).

WebhookAdapter (HTTP-вебхук)

Подходит для платформ, где платформа активно отправляет обратные вызовы. Базовый класс start() регистрирует в маршрутизаторе фреймворка маршрут приема (окончательный путь /{platform}/webhook, метод POST), регистрация происходит в owner_scope — адаптер при удалении автоматически удаляет маршрут, без ручного удаления:

from ErisPulse import WebhookAdapter

class MyAdapter(WebhookAdapter):
    def verify_request(self, request) -> bool:
        """Необязательный хук: проверка обратного вызова (по умолчанию разрешает; возвращает False, базовый класс возвращает 403)"""
        cfg = self.cfg
        if not cfg.token:
            return True
        auth = request.headers.get("authorization", "")
        return auth == f"Bearer {cfg.token}"

    def convert(self, payload):
        """Преобразование нагрузки обратного вызова в OneBot12; возвращает None для пропуска"""
        return self.converter.convert(payload)

    async def call_api(self, endpoint: str, **params):
        ...  # Тот же, что и для обычного адаптера

Минимальный набор: convert / call_api (необязательно verify_request). Адрес обратного вызова можно получить с помощью sdk.adapter.get_connection_info(platform) и заполнить в настройках платформы; запросы с ошибкой проверки возвращают 403, запросы с ошибкой разбора нагрузки возвращают 400, нормальные запросы возвращают {"status": "ok"}.

WebSocket-подключение

class MyAdapter(BaseAdapter):
    async def start(self):
        """Регистрация маршрута WebSocket"""
        router.register_websocket(
            module_name="myplatform",
            path="/ws",
            handler=self._ws_handler,
            auth_handler=self._auth_handler
        )
    
    async def _ws_handler(self, websocket):
        """Обработчик подключения WebSocket"""
        self.connection = websocket
        
        try:
            while True:
                data = await websocket.receive_text()
                onebot_event = self.convert(data)
                if onebot_event:
                    await self.adapter.emit(onebot_event)
        except WebSocketDisconnect:
            self.logger.info("Соединение разорвано")
        finally:
            self.connection = None
    
    async def _auth_handler(self, websocket) -> bool:
        """Аутентификация WebSocket"""
        token = websocket.query_params.get("token")
        return token == "valid_token"

WebHook-подключение

class MyAdapter(BaseAdapter):
    async def start(self):
        """Регистрация маршрута WebHook"""
        router.register_http_route(
            module_name="myplatform",
            path="/webhook",
            handler=self._webhook_handler,
            methods=["POST"]
        )
    
    async def _webhook_handler(self, request):
        """Обработчик запроса WebHook"""
        data = await request.json()
        onebot_event = self.convert(data)
        if onebot_event:
            await self.adapter.emit(onebot_event)
        return {"status": "ok"}

Идентификатор аккаунта в событии и связь с Using

Фреймворк автоматически извлекает идентификатор аккаунта из поля self события (приоритет account_id, в качестве резерва user_id), вставляя его в Using. Разработчику адаптера нужно убедиться, что Converter правильно устанавливает идентификатор аккаунта (имя аккаунта или поля bot_id и т.д.), чтобы он соответствовал конфигурации аккаунта.

Поведение вставки фреймворком:

# Логика фреймворка по извлечению идентификатора аккаунта (account_id имеет приоритет, user_id в качестве резерва)
account = self.get("self", {}).get("account_id", "") or self.get("self", {}).get("user_id", "")

# Вставляется Using только при непустом идентификаторе
if account:
    send_chain = send_chain.Using(account)

Ключевой момент: даже если адаптер использует только одну конфигурацию бота, если Converter правильно установил идентификатор аккаунта, фреймворк вставит его в Using. Адаптеру нужно убедиться, что этот идентификатор соответствует имени аккаунта или bot_id в AccountConfigClass, чтобы он правильно разрешался. Если идентификатор пуст, фреймворк не вставляет Using, и отправка происходит без указания аккаунта — возвращается первый включенный аккаунт.

Если явно переданный account_id не может быть разрешен, фреймворк записывает предупреждение и возвращает первый включенный аккаунт; в предупреждении platform / account_id / account можно использовать для локализации источника события, не привязанного к аккаунту.

Автоматическая привязка в цепочке событий: при вызове метода отправки в цепочке событий не нужно явно Using() — фреймворк в начале распределения события вставляет идентификатор аккаунта, запущенного события в контекст вызова, Send / Api / Request цепочка без явного указания аккаунта использует это по умолчанию (явный Using() всегда имеет приоритет; сценарии таймера / запуска задачи без контекста события сохраняют семантику аккаунта по умолчанию). Автоматическая привязка в цепочке событий требует ErisPulse 2.12+.

Соглашение о выдаче идентификатора self.user_id / self.account_id с приоритетом и резервной версией см. в стандарте преобразования событий; наличие этого поля обязательно для семантики резервного разрешения аккаунта — при его отсутствии возвращается первый включенный аккаунт, в сценариях с несколькими аккаунтами это означает "отправка от аккаунта по умолчанию".

Обработка ошибок

Повторное подключение

import asyncio

class MyAdapter(BaseAdapter):
    async def start(self):
        retry_count = 0
        max_retries = 5
        
        while retry_count < max_retries:
            try:
                await self._connect_to_platform()
                break
            except Exception as e:
                retry_count += 1
                if retry_count < max_retries:
                    wait_time = min(60 * (2 ** retry_count), 600)
                    self.logger.warning(f"Подключение не удалось, повтор через {wait_time} секунд")
                    await asyncio.sleep(wait_time)
                else:
                    raise

Обработка ошибок API

async def call_api(self, endpoint: str, **params):
    try:
        # Рекомендуется использовать встроенный клиент SDK
        from ErisPulse.Core import client
        from ErisPulse.Core.Bases.errors import ClientError, ClientTimeoutError
        resp = await client.post(
            f"https://api.platform.com/{endpoint}",
            json=params,
            max_retries=2,
        )
        response = await resp.json()
        return self._standardize_response(response)
    except ClientTimeoutError:
        self.logger.error(f"Таймаут запроса: {endpoint}")
        return self._error_response("Таймаут запроса", 32000)
    except ClientError as e:
        self.logger.error(f"Ошибка сети: {e}")
        return self._error_response("Ошибка сети", 33000)
    except Exception as e:
        self.logger.error(f"Неизвестная ошибка: {e}")
        return self._error_response(str(e), 34000)

Обратная совместимость: использование aiohttp.ClientSession в старых адаптерах не затрагивается, по-прежнему можно перехватывать aiohttp.ClientError. Оба способа могут сосуществовать. Рекомендуется новый код использовать sdk.client + систему исключений ErisPulse.

Управление статусом бота

AdapterManager встроен в систему отслеживания статуса бота, автоматически отслеживает онлайн-статус, время активности и метаданные всех зарегистрированных ботов.

Автоматическая обнаружение

При отправке события с помощью adapter.emit() фреймворк автоматически проверяет поле self события:

  • Мета-события: в зависимости от detail_type выполняются соответствующие действия (connect — регистрация, disconnect — отмечает как оффлайн, heartbeat — обновляет время активности)
  • Обычные события (message/notice/request): автоматически обнаруживаются боты и обновляется время активности
# Все события с полем self запускают автоматическую обнаружение
await self.adapter.emit({
    "type": "message",
    "platform": "myplatform",
    "self": {"platform": "myplatform", "user_id": "bot123"},
    # ...
})
# Бот "bot123" автоматически зарегистрирован (если впервые появился) и обновлено время активности
